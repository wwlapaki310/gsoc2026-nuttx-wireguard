# なぜ HTTPS ではなく WireGuard か

## HTTPS で十分なケース

```
NuttXデバイス → センサーデータを HTTPS POST → クラウドのAPIエンドポイント
```

これは HTTPS で十分。ESP32 + HTTPS でクラウド連携する製品は世の中に山ほどある。

---

## WireGuard が必要になるケース

### ① サーバー → デバイスへの通信

```
HTTPS の制約:
  デバイス → サーバー  ← クライアント起点のみ
  サーバー → デバイス  ← デバイスが NAT 内にいると不可能

WireGuard:
  トンネルが張られていれば双方向が自由
  → ファームウェア更新、設定変更、デバッグコマンド送信が可能
```

### ② 物理的にアクセスできない機器

```
宇宙機・人工衛星・深海センサー・無人基地
  → 物理メンテナンス不可能
  → ネットワーク越しの双方向通信が唯一の手段

宇宙機が NuttX を搭載している実例:
  - JAXA の小型衛星プロジェクト（NuttX ベースの検討）
  - CubeSat 向け RTOS として採用事例増加中

このような機器に対し VPN トンネルを張ることで:
  - 異常検知時の即時コマンド送信
  - ファームウェアの遠隔更新
  - 診断データの継続的な取得
  が可能になる
```

### ③ ルーターを置けない環境での直接接続

```
一般的な IoT 構成:
  デバイス → ルーター（VPN） → インターネット
  ↑ ルーター〜デバイス間は暗号化されていない

LTE/4G 直接接続構成（NuttX ターゲット）:
  デバイス（WireGuard） → インターネット
  ↑ エンドツーエンドで暗号化
  ↑ ルーターが存在しないのでデバイス自身が VPN クライアントになる必要がある
```

### ④ 任意プロトコルをまとめて暗号化

```
HTTPS: アプリが個別に TLS を実装する必要がある
       Telnet、独自バイナリプロトコル、UDP 通信は暗号化されない

WireGuard: トンネル内の通信はすべて暗号化
           既存の非暗号化プロトコルをそのまま安全に使える
```

### ⑤ デバイス間直接通信（クラウド不要）

```
HTTPS 構成:
  デバイス A → クラウド → デバイス B  （クラウド中継が必須）

WireGuard 構成:
  デバイス A ══ WireGuard ══ デバイス B  （直接通信）
  ↑ クラウドに依存しないデバイス間通信
  ↑ オフライン環境でも動作可能
```

---

## まとめ

| 要件 | HTTPS | WireGuard |
|------|-------|-----------|
| デバイス→クラウドのデータ送信 | ✅ 十分 | ✅ |
| サーバー→デバイスへの命令送信 | ⚠️ 難しい | ✅ |
| NAT 越えの双方向通信 | ⚠️ 難しい | ✅ |
| 宇宙機・衛星のリモートメンテナンス | ❌ | ✅ |
| 任意プロトコルの暗号化 | ❌ | ✅ |
| ルーターなし環境でのエンドツーエンド暗号化 | ❌ | ✅ |
| デバイス間直接通信 | ❌ | ✅ |

HTTPS は「デバイスがデータを送る」用途には最適解。  
WireGuard は「双方向・任意プロトコル・物理アクセス不能機器」に必要な解。
