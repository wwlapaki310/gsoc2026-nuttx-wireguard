01まず結論

この移植の要点は「WireGuard を実装した」ことではなく、 WireGuard の実装を一行も書かずに済ませたことにある。 暗号もハンドシェイクも既存のものをそのまま使い、 OS とネットワークスタックに接続する部分だけを書いた。

02wireguard-lwip は 3 層でできている

移植元の smartalock/wireguard-lwip (Copyright © 2021 Daniel Hope, BSD-3-Clause) は、 組み込み向け TCP/IP スタック lwIP のための WireGuard 実装である。 重要なのは、この実装が移植されることを想定した構造になっていること。

そのまま使う 4 関数だけ実装 書き直す

なぜこれが重要か

暗号ライブラリを自分で書くのは、組み込みではほぼ確実に事故になる。 鍵スケジュールを一箇所間違えれば、動いているように見えて安全ではない実装ができあがる。 しかも通信相手は本物の WireGuard なので、間違っていればそもそも繋がらない。 この構造のおかげで、移植作業は「暗号が正しいか」ではなく 「配線が正しいか」だけの問題に縮んだ。

044 関数の層 — ライブラリが要求してくる唯一の接点

wireguard-platform.h のコメントには 「Your platform integration needs to provide implementations of these functions」 と書かれている。つまりこのファイルは各移植先が埋める前提の空欄である。 埋めるべきものは 4 つしかない。

関数ライブラリが何に使うかNuttX での実装
wireguard_sys_now() ハンドシェイク期限・keepalive・rekey のタイマ判定。単調増加ミリ秒 clock_gettime(CLOCK_MONOTONIC)
wireguard_random_bytes() 一時鍵の生成。ここの品質が弱いと暗号ごと壊れる read("/dev/urandom")
wireguard_tai64n_now() ハンドシェイクに載せるタイムスタンプ。リプレイ攻撃の検出に使う clock_gettime(CLOCK_REALTIME)
wireguard_is_under_load() 高負荷時に cookie で応答して DoS を緩和するかの判定 return false

なぜ 4 番目は false でよいのか

cookie 機構は、大量のハンドシェイク要求で CPU を枯渇させる攻撃への対抗手段である。 これはインターネットに直接晒されたサーバのための機能で、 単一のピアに向けて発信する組み込み機器はその形をしていない。 実装しないのではなく、この用途では常に「負荷は高くない」が正しい答えだと 判断している。将来ゲートウェイ用途に広げるなら、ここを実装し直すことになる。

この 4 関数に OS 依存が閉じ込められていることが、移植性の全部である。 x86_64 の sim、ARM Cortex-A7 の QEMU、Xtensa LX7 の ESP32-S3、ARM Cortex-M4F の Spresense — 4 つのアーキテクチャすべてで、この層より下は一行も変わっていない。

05書き直した層 — なぜ流用できなかったか

upstream の wireguardif.c は「lwIP の仮想 NIC」として WireGuard を見せるコードである。 NuttX は lwIP を使わず独自の TCP/IP スタックを持つため、 このファイルは概念ごと置き換えになった。対応表は次のとおり。

やりたいことlwIP (upstream)NuttX (この移植)

NIC を登録するnetif_add()netdev_register()
パケットバッファpbuf_alloc() / pbuf_free()dev->d_buf (netdev のバッファ)

UDP ソケットudp_new() / udp_bind() / udp_recv()psock_socket() / psock_bind() / psock_recvfrom()
周期処理sys_timeout()専用タスク wg_rx の中でタイマを回す
リンク状態netif_set_link_up()netdev_carrier_on()

見落としやすい非対称

lwIP 版は「lwIP の中に住む netif」だが、NuttX 版は NuttX のネットワークスタックの利用者でもある。 受信したパケットを ipv4_input() でスタックに注入し返すため、 TCP スタックの呼び出し深度がまるごと wg_rx タスクのスタックに乗る。 これは設計の当然の帰結だが、スタックサイズの見積もりを難しくした (実測で 3,392 バイト、既定値 6144)。

06実際にどう呼んでいるか

「ライブラリを使った」と言うとき、具体的にどの関数を呼んでいるのか。 nuttx-wireguardif.c から vendored 側への呼び出しを数えると、 29 種類あった。役割ごとに整理する。

構図としては、自作側が「いつ・どの順番で」を決め、ライブラリ側が「何を計算するか」を担う。 パケットが届いたら種別を判定してもらい、検証してもらい、復号してもらう。 その結果をどこへ流すか、いつ再送するか、どのタスクで動かすかは、こちらの責任である。

07借りられなかった 4 つ

「OS 依存が隔離されている」構造でも、実際にやると綺麗に割り切れない箇所が出る。 この移植では 4 つあった。第三者に話すなら、ここは正直に話す価値がある。

必要だった機能upstream での状態どうしたか
wireguard_clamp_private_key() wireguard.c 内で static — 外から呼べない wg_clamp_private_key() を自前で実装
wireguard_generate_public_key() 同じく static wg_derive_public_key() を自前で実装
(公開されている wireguard_x25519 を使って基点との積を取る)
wireguard_start_handshake() wireguardif.c にしかない — 持ってこなかったファイル wg_start_handshake() として書き直し
peer_lookup_by_allowed_ip() 同じく wireguardif.c 側 宛先アドレスから送出先ピアを選ぶ処理として自前で実装

ここから読み取れること

前の 2 つは、ライブラリの作者が 「鍵の生成は netif グルー側でやるもの」と想定していたことを示している。 実際 upstream には wg genkey に相当する機能がない。 後の 2 つも同じで、プロトコルの外側にある判断はグルー側の仕事という設計になっている。 「4 関数を実装すれば移植完了」ではなく、 「グルーが担っていた責務を全部引き受ける」のが実際の作業量だった。

08NuttX の中に lwip/ があるのはなぜか

リポジトリを見た人が最初に引っかかる点。 NuttX は lwIP を使わないのに、lwip/ というディレクトリがある。

理由は単純で、無改変で取り込んだ wireguard.h が lwIP のヘッダを 4 つ include しているため。ただし使っているのは型だけである。

シム供給しているもの行
lwip/arch.hu8_t / u16_t / u32_t / s8_t / s16_t / s32_t21
lwip/ip_addr.hip_addr_t → struct in_addr の別名17
lwip/netif.hstruct netif の前方宣言のみ17
lwip/udp.hstruct udp_pcb の前方宣言のみ15

判断が割れる点 — レビューで相談する予定

代案は wireguard.h から include を消してしまうこと。 そうすればディレクトリ名の紛らわしさは無くなるが、 vendored ファイルが 1 つ upstream から乖離する。 いまは「プロトコルと暗号は upstream と完全一致させ、差分は再 diff で追える状態を保つ」ことを 優先してシムを選んだ。どちらが良いかは dev@nuttx.apache.org で問う。

10第三者に話すなら、何を言うか

この移植を紹介するとき、話す価値があるのは次の 4 点だと考えている。 「WireGuard を実装しました」と言ってしまうと、事実として正しくないうえに、 この仕事のいちばん良い判断が伝わらない。

  1. 暗号は書かなかった、というのが設計判断である。 借りられる形になっているライブラリを選び、そこを触らないと決めた。 結果として検証すべき対象が「配線が正しいか」だけに縮んだ。 相互運用性の担保も、本物の WireGuard 相手に通信できるかどうかで済む。
  2. 移植性は 4 関数への隔離が生んだ。 時刻・乱数・タイムスタンプ・負荷判定。この 4 つだけが OS を見ている。 だから 4 アーキテクチャで、そして NuttX 12.7.0 と master の両方で、 コードを変えずに動いた。設計の主張が実測で裏付けられた形になっている。
  3. 「4 関数を書けば移植完了」ではなかった。 lwIP netif グルーが担っていた責務 — 鍵生成、ピア選択、ハンドシェイク開始 — は全部こちらに来た。static だったヘルパは呼べず、書き直しになった。 移植の作業量はライブラリが公開していない部分の大きさで決まる。
  4. 難しかったのは暗号ではなく OS の前提だった。 SO_RCVTIMEO が効かない、detach したスレッドが消える、 fd がタスクグループにスコープされていて別タスクから使えない。 借りたコードは一度も壊れなかった。壊れたのは全部、自分で書いた接着剤の側である。

ひとことで言うなら

WireGuard を移植したのではなく、WireGuard が動く場所を NuttX の中に作った。
