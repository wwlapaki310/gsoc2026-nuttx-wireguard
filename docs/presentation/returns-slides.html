今日は、WireGuard という VPN を Apache NuttX に移植している話をします。 || ただ、最初に言いたいのはプロトコル名ではなくて、「置いたあと触れない機器に、どうやってもう一度手を伸ばすか」という問題です。組み込みの機器は、机の上で動いたあとに本番が始まります。天井、屋外、現場、あるいは宇宙。そこに行ったあと、ログを見たい、設定を変えたい、でも物理的には触れない。そこに VPN という普通の道を通したい、というのが今回の話です。

Motivation

困りごとは、だいたい現場のあとに来る

AITRIOS の AI カメラ

ESP32 + NuttX。天井や屋外に置かれ、異常の兆候だけで人を出すのは重い。

SPRESENSE と人工衛星

打ち上げ後は物理アクセスできない。ネットワーク越しの保守が前提になる。

開発中に一番ほしくなるのは、特別な魔法ではなく、あとから安全に入れる入口。

2 / 7
動機は、わりと自分の仕事や活動の実感に近いところにあります。AITRIOS というエッジ AI プラットフォームでは、AI カメラの中で ESP32 と NuttX が動いています。こういう機器は、実験室では近くにありますが、使われる場所は天井や屋外だったりします。 || もうひとつ、ボトムアップの活動で SPRESENSE を使った人工衛星のプロジェクトにも関わっていました。こちらはもっと極端で、一度打ち上げたら物理アクセスはできません。 || つまり、机の上で作っているときはシリアルケーブルでなんとかなりますが、現場に置いたあとに本当に困る。ログを見たい、設定を変えたい、簡単なコマンドを打ちたい。そういうときに「安全に入れる普通の入口」が必要になります。

What VPN Changes

欲しかったのは、専用の遠隔管理ではない

ケーブル前提VPN がある状態
場所機器の前に行くネットワーク越しに届く
経路平文か、個別に作り込む暗号化トンネルを使う
道具専用手順が増えるssh / telnet / HTTP がそのまま使える

wg0 が生えると、アプリからは普通のネットワークインターフェースに見える。

3 / 7
VPN があると何がうれしいか。ポイントは、専用の遠隔管理機能をひとつ増やすことではありません。 || WireGuard のトンネルが張れて、NuttX 側に wg0 という仮想ネットワークインターフェースが生えると、アプリからは普通の NIC に見えます。そうすると、既存の telnet、HTTP サーバ、将来的には ssh のような道具を、そのまま安全な経路に乗せられます。 || VPN がない場合は、グローバル IP を晒す、独自プロトコルを作る、ベンダークラウドに乗せる、といった選択になりがちです。それが悪いわけではないですが、NuttX 自体に普通の選択肢として VPN があると、設計の自由度がかなり変わります。

Gap

NuttX には、その道がまだなかった

GSoC のテーマ一覧で見つけたのは、この空白を埋める題目だった。

4 / 7
ところが、NuttX には VPN の選択肢がありませんでした。少なくとも、NuttX の標準的なネットワークスタックに乗る WireGuard 実装はありません。 || GSoC のテーマ一覧を見ていたときに、この空白を埋める題目を見つけました。これは単に「面白そうなプロトコルを移植する」だけではなく、自分が現場で感じていた困りごとにもかなり近い。だから取り組むことにしました。 || WireGuard を選ぶ意味もあります。OpenVPN や IPsec と比べると実装規模が小さく、暗号スイートも固定で、マイコンに載せる対象として現実的です。

Implementation

既存実装を活かし、NuttX の作法でつなぎ直す

部分方針規模
WireGuard のプロトコル・暗号wireguard-lwip から無改変で流用約 3,000 行
OS 依存の 4 関数NuttX の POSIX API で実装186 行
lwIP netif グルーNuttX の netdev として書き直し約 2,700 行

結果: x86_64 / Cortex-A7 / Xtensa LX7 / Cortex-M4F でコード変更ゼロ。

移植元: smartalock/wireguard-lwip。OS 依存が小さく分離されていたのが効いた。
5 / 7
実装は、ゼロから WireGuard を書いたわけではありません。smartalock/wireguard-lwip という lwIP 向けの実装を移植元にしています。 || この実装の良いところは、OS に依存する処理が 4 つの関数に分離されていることです。単調増加時刻、暗号乱数、TAI64N タイムスタンプ、負荷判定。そこは NuttX の POSIX API で実装しました。 || 一方で、NuttX は lwIP ではなく独自のネットワークスタックを持っています。なので lwIP の netif まわりはそのまま使えません。ここは NuttX の netdev として書き直しました。wg0 を netdev_register で登録し、その裏側を UDP ソケットで WireGuard のピアにつなぎます。 || この分け方にしたことで、x86_64、Cortex-A7、Xtensa LX7、Cortex-M4F の 4 アーキテクチャで、アプリ側のコード変更なしに動かせています。

Current Status

ESP32-S3 実機で、公式クライアントと話せた

確認できたこと

実 Wi-Fi、電源アダプタのみ、Windows 公式クライアントとの相互運用。

数字で見ると

トンネル越し TCP 約 260 KiB/s。最長連続動作は 4 時間 28 分。

6 / 7
現状です。ESP32-S3 の実機で、家庭用 Wi-Fi 越しに Windows の公式 WireGuard クライアントと通信できるところまで確認しました。 || デモでは、トンネル越しに telnet で入って、NuttX のボード上で Web サーバを起動して、ブラウザから http://10.10.0.2/ を開いています。このとき USB は未接続で、電源アダプタだけです。 || 性能は、ESP32-S3 実機でトンネル越し TCP が約 260 KiB/s。最長連続動作は 4 時間 28 分です。まだ「日単位で安定」とは言いませんが、止まった原因は WireGuard ではなく Wi-Fi ドライバ側と見ています。

Returns

7 / 7
これからやることは三つです。対応実機を広げること。Community Over Code グラスゴーに向けて、見てすぐ伝わるデモに磨くこと。そして upstream にマージすることです。 || Returns なので、最後に少しだけ Sechack365 に寄せて言うと、これは自分にとって「手元の違和感を、外に出せる形にする」活動です。現場で感じた困りごとを、コードにして、検証して、最終的には OSS に返す。そこまで行って初めて、次の誰かが普通に使える入口になると思っています。 || ご清聴ありがとうございました。
