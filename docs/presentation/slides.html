そもそもなぜ組み込みに VPN が要るのか。機器を現場に設置したあと、ファームウェアを更新したりログを取ったりデバッグしたりする必要が出てきます。そのときの現実的な選択肢が、この3つです。 || グローバル IP を晒すか、独自プロトコルを作り込むか、ベンダーのクラウドに繋ぐか。どれも嬉しくありません。本来なら VPN を張ればいい話なのに、NuttX にはその選択肢がありませんでした。そして WireGuard は小さいので載る。これが動機です。

Why it matters

NuttX が VPN を話せると、何が変わるか

やりたいことが変わるのではなく、やりたかったことが普通の方法でできるようになる。

  • 設置後の保守 — 現場の機器に ssh / telnet で入る。ログを取る。ファームを更新する。いつもの道具のまま。
  • センサの回収 — 機器がクラウドに合わせるのではなく、クラウドの側を機器のネットワークに引き込む。
  • ゼロトラストの末端まで — 認証済みの暗号トンネルが、MCU まで届く。境界の内側が LAN で終わらない。
  • 相互運用 — 相手は Linux でも Windows でも既存の WireGuard サーバでもいい。独自プロトコルではないことがそのまま価値になる。

方針

プロトコル・暗号コア (wireguard.c / crypto/) → 無改変で流用。upstream と cmp でバイト一致を確認。

lwIP netif グルー → NuttX 用に書き直し。

07
ゼロから書くのではなく、wireguard-lwip という lwIP 向けの実装をベースにしました。BSD ライセンスで、NuttX のライセンス方針とも相性がいいです。 || この実装の良いところは、OS 依存の部分が4つの関数に隔離されていることです。時刻、乱数、TAI64N のタイムスタンプ、そして負荷判定。これだけです。なので、プロトコルと暗号のコアはそのまま持ってきて、lwIP に依存しているネットワークインターフェース部分だけを書き直す、という方針にしました。 || 流用した部分は upstream から取ってきたままで、cmp コマンドでバイト一致を確認しています。差分が出ないことが、あとで upstream に出すときの説明のしやすさに直結します。

Design decision

lwIP netif ではなく、NuttX netdev として

lwIPNuttX
NIC 抽象struct netifstruct net_driver_s
バッファpbufiob
登録netif_add()netdev_register()
送出契機コールバックdevif_poll()

NuttX は lwIP を使っていない。独自のネットワークスタックを持っている。
→ wireguardif.c は使えない。drivers/net/tun.c を手本に書き直し。

この設計の要点

wg0 を NET_LL_TUN の netdev として登録する。 アプリから見れば、ただのネットワークインターフェース。ifconfig も既存アプリもそのまま動く。

ただし、この仮想 NIC の「配線」は物理イーサネットではなく——

UDP ソケット

この一点が、後で 3 つ目の落とし穴を生みます。

08
ここが最初の設計判断です。NuttX は lwIP を使っておらず、独自のネットワークスタックを持っています。NIC の抽象化も、バッファ管理も、登録 API も、送信の契機も全部違うので、既存の netif グルーはそのまま使えません。 || そこで NuttX の TUN ドライバを手本にして、wg0 を仮想 NIC として登録する形で書き直しました。アプリから見ればただのネットワークインターフェースなので、ifconfig も既存のアプリもそのまま動きます。 || ポイントは、この仮想 NIC の配線が、物理的なイーサネットではなく UDP ソケットだということです。当たり前のことを言っているようですが、この一点が後で3つ目の落とし穴を生みます。覚えておいてください。

Pitfall 1 / 5

戻り値は 0。でも効いていない

  • 設計: recvfrom() をタイムアウト付きでブロックし、タイムアウトのたびにタイマー処理を回す
  • setsockopt(SO_RCVTIMEO) は 成功を返す(ret = 0)
  • しかし recvfrom() は 永久にブロックする

結果 — 完全な鶏卵

タイマーが一度も回らない → 最初のハンドシェイクが送られない → 相手も何も送ってこない → recvfrom() が戻らない

setsockopt(sock, SOL_SOCKET,
           SO_RCVTIMEO, &tv, sizeof(tv));
/* → 0 (成功)  ...のはずだった */

recvfrom(sock, ...);
/* 永久にブロック */
poll(&fds, 1, timeout_ms);
if (fds.revents & POLLIN)
  recvfrom(sock, ...);

教訓: 戻り値が 0 でも、その機能が実装されているとは限らない。
設定したことではなく、期待した挙動を確認する。

14
1つ目。受信スレッドは、UDP をタイムアウト付きで待って、タイムアウトするたびにハンドシェイクや keepalive のタイマー処理を回す設計にしていました。 || setsockopt でタイムアウトを設定すると、戻り値は 0 で成功します。ところが recvfrom は永久にブロックしました。相手から何か来ない限り戻ってこない。でも、こちらからハンドシェイクを送らないと相手は何も送ってこない。完全な鶏と卵です。 || 教訓は、戻り値が 0 でもその機能が実装されているとは限らない、ということです。設定したことを確認するのではなく、期待した挙動を確認しないといけない。poll に変えて解決しました。

Pitfall 2 / 5

生成には成功する。でも生き残らない

  • wg コマンドが pthread_create() + pthread_detach() で受信スレッドを起動
  • wg コマンドが終了すると、スレッドも動かなくなる
    • ps にすら出てこない
  • 面白い挙動: pthread_create() の直後に usleep() を入れるとスレッド内の printf は出る
    → 生成自体はされている
  • POSIX の建前では、detach したスレッドは生成元と無関係に生き続けるはず
pthread_create(&tid, NULL, wg_rx, priv);
pthread_detach(tid);
return OK;   /* wg コマンド終了 → 消える */
task_create("wg_rx", prio, stack,
            wg_rx_task, NULL);

教訓

POSIX 準拠 ≠ Linux と同じ寿命モデル。
「生成に成功した」は「生き続ける」の保証ではない。
ps で存在を確認するまで信じない。

15
2つ目。受信スレッドを pthread_create して pthread_detach していたんですが、wg コマンドが終了した瞬間にスレッドが動かなくなりました。ps にも出てきません。 || 面白いのは、pthread_create の直後に usleep を入れるとスレッド内の printf が出ることです。つまり生成自体はされている。POSIX の建前では detach したスレッドは生成元と無関係に生き続けるはずなんですが、そうなりませんでした。 || task_create で独立したタスクにして解決しました。ここでも同じで、生成に成功したことは生き続けることの保証ではない。ps で存在を確認するまで信じない、という話です。

Pitfall 3 / 5  ·  犯人

送信経路にログを仕込んで実機で再現させたところ、sendto が errno=9、つまり EBADF、不正なファイルディスクリプタを返していました。 || そして成功する送信と失敗する送信が、きれいに分かれていました。成功するのは受信タスク自身のコンテキストから出るもの。ハンドシェイク応答、keepalive、ICMP の echo reply、そして TCP の SYN-ACK です。ping が通ったのも、3-way ハンドシェイクが成立したのも、全部これです。 || 失敗するのは LPWORK というワーカースレッドから出るもので、これが TCP のアプリケーションデータ全部に相当していました。同じソケット、同じコード、呼ぶタスクだけが違う。

Pitfall 3 / 5  ·  原因

fd は「プロセス」ではなくタスクグループに閉じている

18
原因はこうでした。NuttX のファイルディスクリプタは、タスクグループ単位でスコープされます。UDP ソケットの fd を持っているのは受信タスクとその子孫だけです。 || ところが LPWORK は起動時から存在する独立したシステムタスクで、受信タスクとは task_create の系譜が一切つながっていません。だから LPWORK の fd テーブルにはそのソケットが存在せず、EBADF になります。 || ping が通ったのは、ICMP の応答が ipv4_input の呼び出しの中で同期的に作られて、受信タスクのコンテキストのまま送り返されるからです。TCP の SYN-ACK も同じ。だからハンドシェイクまでは成立する。でもアプリケーションのデータは非同期にキューされて LPWORK から出るので、そこだけ無言で死ぬ。 || つまり「ping が通る」は、送信経路が正しいことの証明になっていませんでした。半分しか通っていなかったんです。

Pitfall 3 / 5  ·  修正

fd テーブルを経由しない

  • NuttX には fd を介さない内部 API がある
    psock_socket() / psock_bind() /
    psock_sendto() / psock_recvfrom()
  • 実体は struct socket —— ただのメモリ上の構造体
  • ポインタで触るだけなので、どのタスクからでも同じように使える
- int sock;              /* タスクグループに縛られる */
+ struct socket psock;   /* どこからでも OK */

- sendto(priv->sock, ...);
+ psock_sendto(&priv->psock, ...);

結果

トンネル越しの telnet と HTTP が動作。
さっきのデモの Web サーバは、この修正の産物です。

正直に言うと — これは借金でもある

upstream に出すときの論点として Issue に立ててある(#6)。隠さずに相談する。

19
