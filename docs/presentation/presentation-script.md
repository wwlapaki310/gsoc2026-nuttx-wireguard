## デモ

録画: <https://youtu.be/1kyX2av5WG4>

ライブでやる場合のコマンド:

```
nsh> uname -a      # 本物の NuttX が動いていることを示す
nsh> ifconfig      # wg0 = 10.10.0.2 が上がっている
nsh> wg show       # ハンドシェイク成立・転送バイト数
nsh> ps            # wg_rx タスクが動いている
nsh> webserver &   # Web サーバー起動
```
→ ブラウザで `http://10.10.0.2/`

> **収録・登壇時の注意**
> `.config` の中身、`kconfig-tweak` の実行画面、ビルドログを画面に出さないこと。
> Wi-Fi の SSID とパスフレーズが平文で入っている。
> 上のデモコマンドと `wg show` の出力にはこれらは出てこない。
> `wg showconf` は**秘密鍵を表示する**ので、画面に出さないこと。

## 想定質問と回答

**Q. なぜ lwIP をそのまま NuttX に載せなかったのか?**
NuttX は独自のネットワークスタックを持っていて、そちらが標準です。lwIP を別途載せると
二重にスタックを持つことになり、メモリ的にも保守的にも不利です。それに、NuttX ネイティブの
netdev として実装しておけば `ifconfig` や既存のアプリがそのまま使えます。

**Q. 性能は?**
ESP32-S3 実機・実 Wi-Fi 経由で、トンネル越しの TCP スループットが約 260 KiB/s です。
7 MB の連続転送を問題なく通せています。ただしこれは「明らかなボトルネックを 1 つ潰した」
段階の数字で、体系的なチューニングはしていません。暗号処理がソフトウェア実装のままなので、
そこがおそらく次のボトルネックです。

**Q. 暗号処理はソフトウェア? ハードウェアアクセラレータは?**
現状は wireguard-lwip 付属のソフトウェア実装をそのまま使っています。ESP32-S3 には暗号
アクセラレータがあるので、そこに載せ替えるのは将来的な最適化として有力です。

**Q. 複数ピアは?**
対応済みです。`CONFIG_NET_WIREGUARD_MAX_PEERS` で 1〜16 まで設定でき、シミュレータ上で
Linux カーネルの WireGuard を 2 本立てて、両方と同時にセッションを保持することを確認して
います。ピアは静的に確保されるので RAM と直接のトレードで、実測で 1 ピアあたり約 904 バイト。
その表を Kconfig の help に載せてあります。実機での複数ピア確認はまだです。

**Q. 鍵の管理は?**
実行時に設定できます。`wg genkey` で生成し、`wg set private-key` で設定、`wg saveconf` で
保存すると次回起動時に自動で読み込まれます。ビルド成果物に鍵を焼き込む必要はありません。
Kconfig の値は「一度も設定されていないボード」のフォールバックとして残してあります。

**Q. 設定ファイルの形式は独自?**
`wg(8)` と同じ INI 形式です(`[Interface]` / `[Peer]`、`PrivateKey` / `PublicKey` /
`AllowedIPs` / `Endpoint` / `PersistentKeepalive`)。デスクトップの `.conf` をそのまま
持ち込めます。

**Q. 内部 API (`psock_*()`) を使うのは問題にならないのか?**
なります。これで実装は FLAT ビルド前提になりました。PROTECTED / KERNEL ビルドでは
アドレス空間が分かれるので別の設計が要ります。upstream に出すときの論点として Issue #6 に
立ててあり、いきなり PR を投げるのではなく先に `dev@nuttx.apache.org` で相談する方針です。

**Q. なぜ ESP32-S3 を選んだのか?**
NuttX の Wi-Fi サポートがあることが第一です。手元の ESP32-WROOM-32 は書き込みに入れず
(GPIO0 のブートモード遷移まで切り分け済み)、Spresense は当初 USB が認識されませんでしたが、
これは CP210x ドライバが入っていなかっただけで、入れたあとは `wg0` の起動まで確認できました。

**Q. Raspberry Pi Pico 2 W は使えないのか?**
オンボードの Wi-Fi チップ (CYW43439) のドライバが、NuttX では RP2040 版にしか統合されて
いません。RP2350 側にも PIO/GPIO の対応関数は揃っているので移植自体は現実的ですが、別の
ドライバ開発タスクになるので今回はスコープ外としました(Issue #1, #2 に調査メモ)。

**Q. 長時間の安定性は?**
最長で 4 時間 28 分。そこで止まったときはクラッシュダンプが取れていて、原因は ESP32-S3 の
Wi-Fi ドライバ側(`start_rt_timer` が NULL リンクを辿っていた)で、WireGuard ではありません
でした。該当ファイルは upstream master では削除済みなので、NuttX を新しくするのが筋と
判断しています。2 回目は 3 時間 36 分で止まりましたが、シリアルログにパニックがなく、
ネットワークより先に USB ポートが消えているため、電源断と整合します。断定はできません。
「日単位で動く」ことはまだ言えない、というのが正直な現状です。

**Q. NuttX のバージョンは何に依存しているのか?**
していません。12.7.0 と master の両方でビルドが通ります(`--build-arg NUTTX_REF=<ref>`)。
ただし master では `CONFIG_NSH_LINELEN` が `CONFIG_LINE_MAX` に改名されており、古い名前を
指定してもエラーにならないまま `wg set peer` の行だけが切れる、という静かな壊れ方をしました。
どちらのバージョンを既定にするかは Issue #8 で検討中です。
