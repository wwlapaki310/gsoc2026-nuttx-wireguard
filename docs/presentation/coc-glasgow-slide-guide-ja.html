1. 全体像 — 5 分でわかるこのプロジェクト

1.1 一言でいうと

小さな組込み機器(NuttX が動くマイコン)に、普通の VPN(WireGuard)を入れて、遠くから安全にログインできるようにした。

具体的には、NuttX という OS に wg0(ダブリュージー・ゼロ)という「仮想のネットワークの口」を追加した。アプリから見ると Wi-Fi の口(wlan0)と同じように使えるが、そこを通るデータは自動的に暗号化され、インターネットの向こうの PC まで安全に届く。相手側は自作の特別なソフトではなく、Linux や Windows で普通に使われている WireGuard そのもの。

1.2 登場人物

1.3 パケットの「入れ子」— VPN の正体

VPN は魔法ではなく、パケット(データの小包)を暗号化し、別の小包に入れて送るだけ。この入れ子をカプセル化かぷせるか(encapsulation、エンキャプスレーション)と呼ぶ。手紙を、中身の見えない封筒に入れ、さらに宅配便の箱に入れて送るイメージ。宅配業者(インターネット)は箱のラベル(外側の宛先)しか読めない。

② 背景知識

VPN(Virtual Private Network)は、インターネットのような誰でも通れる道の上に、暗号で守った「自分たちだけの専用線」を仮想的に作る技術。図 1-2 のように、元のパケットを暗号化して別のパケットに包んで送る。

ネットワークデバイスは、OS から見た「ネットワークの口」1 つ分のこと。PC で ipconfig や ip addr を打つと「イーサネット」「Wi-Fi」が並ぶが、あの 1 行 1 行がネットワークデバイス。Linux では eth0(有線)、wlan0(無線)のような名前が付く。このプロジェクトは NuttX に wg0 という口を 1 つ増やした。物理的な線はなく、ソフトウェアだけでできた仮想の口。

5 — Overview: the project in one slide

This project adds WireGuard to NuttX as a network device.

画像:renders/glasgow/slide-05.png · スライド本体で開く

① 画面にあるもの

左に「NuttX RTOS」の箱。上から Application / NSH → NuttX network stack(BSD socket API)→ 横並びに eth0 / wlan0(物理の口)と wg0(この発表で作ったもの)→ wg0 の下に UDP socket(port 51820)。右へ Internet / LTE / satellite link を経て WireGuard peer(Linux, Windows, ...)。下に「wg0 に送られたパケットは暗号化されて UDP で出ていく。届いた UDP は復号され、wg0 から来たものとして渡される」。

② 背景知識

IP アドレスとポート

IP アドレスは機器の住所、ポート番号はその建物の「窓口番号」。1 台の機器で Web(80 番)、telnet(23 番)、WireGuard(51820 番)などが同時に動けるのは、窓口が分かれているから。

192.168.0.10:80     → Web サーバー
192.168.0.10:51820  → WireGuard
TCP と UDP
TCPUDP
たとえ書留郵便。届いたか確認し、届かなければ再送するはがき。出したら終わり
順序・再送保証する保証しない
例Web、telnet、SSHDNS、音声通話、ゲーム、VPN の外側

WireGuard は外側の運び方に UDP を使う。中に入る元のパケットは TCP でも UDP でもよい。TCP の確認や再送は、トンネルの中で端と端がやってくれるので、外側まで書留にする必要はない。

ソケットと BSD socket API

ソケットは、プログラムがネットワークを使うための「差込口」。socket() で作り、bind() で自分のポートに結び、sendto() で送り、recvfrom() で受け取る。この関数のそろいを BSD socket API と呼び、Linux・macOS・Windows でもほぼ同じ形。NuttX もこの形を持つので、既存のネットワークソフトや考え方をそのまま持ち込める。

ネットワークスタックとルーティング

アプリから受け取ったデータに宛先などのヘッダを付け、どの口から出すかを決める(ルーティング)OS の部品。下の図のように、wg0 は物理の口と同じ段に並んでいる。だからアプリは「送り先が VPN の中の住所なら wg0 から出る」ことを知らなくてよい。

③ このスライドの主張と根拠

主張:アプリからは wg0 が普通のネットワークインターフェースに見える。違うのはその下の「線」で、ケーブルではなく UDP ソケット。相手は普通の WireGuard なら何でもよい。根拠はスライド 14・17 の設計と、T1(Linux カーネル WireGuard との相互接続、sim)・T5(Windows 公式クライアント、実機)。

台本にある注意:「FreeRTOS や Zephyr では VPN が動かない」とは言っていない。「NuttX では VPN が自然に普通のネットワークデバイスになる」と言っている。

④ 話すときのポイント

Applications see a normal interface. Under it, the encrypted data travels over a UDP socket.

アプリには普通の口に見えます。その下で、暗号化されたデータが UDP ソケットで運ばれます。

I am not saying that FreeRTOS or Zephyr cannot run a VPN. I am saying that here, a VPN can become a normal network device very naturally.

FreeRTOS や Zephyr で VPN が動かないと言っているのではありません。NuttX では VPN がとても自然に普通のネットワークデバイスになる、ということです。

⑤ 聞かれそうな質問

なぜ lwIP をそのまま載せなかったのですか?
NuttX は自前のネットワークスタックを持っている。lwIP を足すとスタックが 2 つになり、メモリも保守も不利。ネイティブの netdev にすれば ifconfig も既存アプリもそのまま使える(Q&A)。

7 — Background: the OS behind this work

What is Apache NuttX?

画像:renders/glasgow/slide-07.png · スライド本体で開く

① 画面にあるもの

層の図(Applications → POSIX / ANSI & BSD socket APIs → Networking・VFS & filesystems・device drivers・NSH shell → NuttX kernel → MCU / MPU、8〜64 bit)と、特徴の札(RTOS、POSIX APIs、BSD sockets、Filesystem / VFS、NSH shell、Built-in networking、Device drivers、Apache top-level project)。

② 背景知識

OS は資源の管理者

OS は CPU の時間、メモリ、ファイル、ネットワーク、周辺機器を管理し、アプリに「共通の使い方」を提供する。アプリは「Wi-Fi チップのレジスタの何番地に書く」ではなく、「ソケットに送る」と書けばよい。

RTOS とは

Real-Time OS。「速い OS」という意味ではなく、「大事な処理が決まった時間内に動く」ことを予測しやすい OS。モーター制御やセンサー読み取りのように、遅れると困る処理を持つ機器で使う。メモリが数百 KB しかないマイコンでも動くよう、とても小さく作られている。

POSIX とは

Unix 系 OS の API(関数の名前と動き)をそろえるための標準。open()・read()・pthread_create()・socket() などが含まれる。NuttX はこれに沿っているので、Linux 向けに書かれたプログラムの考え方がほぼそのまま通じる。小さな RTOS でこれだけ Unix に近いものは珍しい。

VFS とファイルシステム

VFS(Virtual File System)は、フラッシュメモリ、SD カード、RAM ディスク、さらにはデバイスまで、いろいろなものを「ファイル」として同じ形で扱う仕組み。NuttX では /dev/urandom(乱数)や /data/wg0.conf(設定ファイル)のような名前でアクセスする。

Apache のトップレベルプロジェクト

Apache Software Foundation(ASF)で、独り立ちしたと認められたプロジェクト。重要なのは、開発が公開の場(メーリングリスト、GitHub)で行われ、コードだけでなく設計理由やライセンスまでレビューされること。これがスライド 40 の進め方につながる。

③ このスライドの主張と根拠

主張:NuttX は小さな RTOS だが、Unix のように書ける。だから後半のソケット、ネットワークデバイス、POSIX 流の移植が成り立つ。根拠は NuttX 公式の説明(nuttx.apache.org)。

④ 話すときのポイント

NuttX is a small RTOS, but you program it like Unix. That is rare.

NuttX は小さな RTOS ですが、Unix のように書けます。これは珍しいことです。

間
And that is why almost everything later in this talk is possible at all.

この後の話のほとんどが成り立つのは、そのおかげです。

⑤ 聞かれそうな質問

Linux を使えばいいのでは?
対象はメモリが数百 KB のマイコンで、Linux は載らない。NuttX は Linux 的な書き方を、Linux が動かない大きさの機器に持ち込む。
生成 AI の時代に、なぜ NuttX なのですか?
AI が持っている知識の量では FreeRTOS や Zephyr が上だが、NuttX は POSIX なので、AI がいちばんよく知っている Linux の書き方がそのまま効く。sim と QEMU で実機なしに「ビルド → 実行 → 確認」を回せ、設定も操作(NSH)もテキストなので、AI エージェントが自分で試して直せる。一方で、学習データが少ないぶん AI は NuttX にない機能をもっともらしく作ることがあるので、深い試験で確かめるのが前提。Zephyr にも native_sim と twister があるので、2 つ目の点は互角(Q&A)。"NuttX speaks POSIX — the language AI already knows best. ... But it also means the AI will sometimes invent things NuttX does not have, so you still need deep tests."

11 — Problem: Wi-Fi security stops too early

Reaching a device from far away is hard.

画像:renders/glasgow/slide-11.png · スライド本体で開く

① 画面にあるもの

上に「必要なもの:機器まで全部安全な通り道」。エンジニア → インターネット → ルーター / ネットワーク → Wi-Fi → NuttX 機器の一列で、WPA2 / WPA3 が守るのは最後の 1 区間だけ。下に、よくある 3 つの逃げ道(インターネットに公開する / 独自プロトコルを作る / ベンダーのクラウドを使う)。

② 背景知識

WPA2 / WPA3 は何を守るか

Wi-Fi のパスワードを入れてつなぐときの暗号方式。守るのは機器と無線ルーター(アクセスポイント)の間の電波だけ。ルーターから先、インターネットを渡る間は、Wi-Fi の暗号はもう外れている(図 1-1)。家の玄関に鍵をかけても、手紙を運ぶ道中は守られないのと同じ。

NAT と「外からつなげない」問題

家庭や会社のネットワークでは、何台もの機器が 1 つのグローバル IP アドレスを共有する。この住所の変換を NAT と呼ぶ。外から見えるのはルーターの住所だけなので、インターネットから中の機器に直接つなぐことは普通できない。逆に、中の機器から外へ出ていく通信はできる。

インターネット
     │ グローバル IP は 1 つ
 [ ルーター / NAT ]
     ├── PC       192.168.0.10
     ├── スマホ   192.168.0.20
     └── NuttX    192.168.0.115   ← 外から直接は届かない
3 つの逃げ道の問題
方法やり方問題
Open it to the Internet(公開)機器にグローバル IP を割り当てる、またはルーターのポートを開ける世界中から攻撃される。小さな機器の telnet や Web は、そのままさらす前提で作られていない
Make your own protocol(自作)独自の暗号通信を作る暗号は少しの間違いで全部が壊れる。作るのも保守し続けるのも大変
Use a vendor's cloud(クラウド)メーカーのクラウド経由でつなぐ自分の機器なのに他人のサービスに依存する。終了や障害の影響を受ける

③ このスライドの主張と根拠

主張:欠けていたのは、NuttX 機器まで標準的で安全な通り道を最後まで通すこと。これはエッジ AI、産業 IoT、遠隔システム全般に共通の問題。根拠は WPA2/3 の守備範囲という一般的な事実と、本人の運用経験(スライド 10)。

④ 話すときのポイント

Wi-Fi security is real, but it protects only one part of the path: the radio link between the device and the access point.

12 — Options: MQTT, HTTP, router VPN, ...

Other ways to reach a device — compared.

画像:renders/glasgow/slide-12.png · スライド本体で開く

② 背景知識

「つなぎに行く向き」が大事な理由

スライド 11 の NAT のせいで、外から中へは届かないが、中から外へは出られる。だから多くの IoT 機器は「機器のほうからサーバーへつなぎに行く」設計にする。これなら NAT の内側でも動く。

各方式の中身

メッシュ VPN(Tailscale、ZeroTier)は、多数の機器を自動で網の目のようにつなぐ VPN サービス。中で WireGuard を使うものもあるが、エージェントのソフトが大きく、普通は Linux くらいの OS を前提にする。

主張:MQTT と HTTPS はデータには最適。しかし、ログインして直すために、端から端まで、間にサーバーなしでつなぐなら、VPN は機器の上に必要。根拠:各方式の構造(一般的な事実)と、NuttX で今使えるクライアントの確認(nuttx-apps 13.0.1 の netutils/:mqttc、paho_mqtt、webclient、libcurl4nx、libwebsockets、dropbear、と crypto/mbedtls)。

HTTPS and MQTT are what most IoT products use. The device connects out to a server, so NAT is not a problem.

HTTPS と MQTT は多くの IoT 製品が使う方法です。機器からサーバーへつなぎに行くので、NAT は問題になりません。

But you only get the messages you designed — you cannot log in or open a web page on the device. And the security ends at the broker or the cloud.

13 — Solution: a VPN on the device

Why WireGuard is a good fit.

画像:renders/glasgow/slide-13.png · スライド本体で開く

① 画面にあるもの

左に「エンジニア・Linux・Windows(本物の既存 WireGuard ピア)」、右に「NuttX 機器 wg0」、間に WIREGUARD TUNNEL。下に 3 つの理由:現代的な IP 層の VPN(小さく単純、IPsec や OpenVPN よりずっと少ないコード)/ UDP で運び、相手は公開鍵で識別(証明書も複雑な接続手続きも不要)/ すでにどこにでもある(Linux カーネル内蔵、Windows 公式クライアント)。

② 背景知識

公開鍵と秘密鍵
鍵扱いたとえ
秘密鍵(private key)自分だけが持つ。絶対に漏らさない本人だけが持つ印鑑
公開鍵(public key)相手に渡してよい印鑑の印影。相手はこれで本人の判子か確かめる

秘密鍵から公開鍵は計算できるが、逆は現実的な時間では計算できない。WireGuard では、相手を公開鍵そのもので識別する。「この公開鍵の持ち主とだけ話す」と設定するだけでよい。

証明書がいらないとは

HTTPS や IPsec では、「この公開鍵は本当にこの会社のもの」と第三者(認証局、CA)が保証する証明書を使うことが多い。発行・更新・失効の管理が必要で、小さな機器には重い。WireGuard は、両端が相手の公開鍵をあらかじめ設定しておく方式なので、この仕組みが要らない。

handshake と session key

通信を始めるとき、両者は短いやり取り(handshake、握手)でお互いが正しい鍵の持ち主か確かめ、その場限りの暗号鍵(session key)を作る。以後のデータはこの鍵で暗号化する。session key は一定時間ごとに作り直す(rekey)。

IPsec と OpenVPN

WireGuard より前からある代表的な VPN。高機能だが、選べる暗号や設定が多く、コードも大きい。WireGuard はあえて選択肢を減らし、使う暗号を固定することで小さくしている。マイコンでは、この小ささがそのまま「載るかどうか」と「レビューできるかどうか」に効く。

正しい鍵がなければ何も答えない

WireGuard は、正しい鍵で作られていないパケットには一切返事をしない。ポートを調べに来た攻撃者には、そこに何かがあることすら分からない。これは WireGuard の設計上の性質。

③ このスライドの主張と根拠

主張:WireGuard は、自作のセキュリティ層やベンダーのクラウドではなく、標準のプロトコルでアクセスの問題を解決する。製品ではなく標準を選んだ。根拠:WireGuard の設計(公開鍵のピア、UDP、小さなコード)と、Linux カーネル・Windows 公式クライアントとの実際の相互接続(T1、T5、verification-matrix.md)。間違った鍵では接続しないことも試験済み(TN:相手の公開鍵違い・PSK 違いで不成立、sim)。

④ 話すときのポイント

It runs over plain UDP, and each peer is known by its public key, not by certificates or a long setup.

普通の UDP で動き、相手は証明書や長い手続きではなく、公開鍵で識別されます。

If a packet does not carry the right key, WireGuard does not answer at all — to everyone else, the device is just a brick wall.

正しい鍵を持たないパケットには、WireGuard は一切答えません。他の人から見れば、機器はただのレンガの壁です。

小ネタ(任意)

「brick wall」は『ハリー・ポッター』の 9¾ 番線(通れる人にだけ開くレンガの壁)へのオマージュ。知らない人には普通の比喩として聞こえ、外しても流れは変わらない。ただし中身は本当の事実(認証されないパケットに WireGuard は応答しない)なので、説明として言ってよい。

So I did not choose a product. I chose a standard protocol.

製品を選んだのではなく、標準のプロトコルを選びました。

⑤ 聞かれそうな質問

WireGuard の暗号は自分で実装したのですか?
していない。暗号とプロトコルは既存の wireguard-lwip のもの(apps 版)と NuttX 自身の crypto/(カーネル版)を使う(スライド 16・28)。
WireGuard の弱点は?
暗号を選べない(固定)、相手の公開鍵を手で配る必要がある、handshake が時刻に依存する(スライド 33)。

14 — Architecture: where wg0 sits

WireGuard on the NuttX network stack.

画像:renders/glasgow/slide-14.png · スライド本体で開く

① 画面にあるもの

縦の層:Application → TCP / UDP / IP → wg0(NET_LL_TUN netdev)→ WireGuard encrypt / decrypt → UDP socket → wlan0 / usrsock・物理ネットワーク。左に下向きの TX(送信)、右に上向きの RX(受信)の矢印。

② 背景知識

層(レイヤー)で考える

ネットワークは層に分けて作る。各層は「すぐ上と、すぐ下」とだけ話す。手紙で言えば、書く人(アプリ)、封筒に宛名を書く人(IP)、配達する人(物理の口)が分業していて、配達の人は手紙の中身を知らなくてよい。

TUN 型のデバイス

普通の Ethernet の口は、IP パケットの外に Ethernet のヘッダ(機器の物理アドレス MAC など)を付けて送る。TUN 型の口は IP パケットだけを扱い、Ethernet のヘッダを持たない。WireGuard が運ぶのは IP パケットそのものなので、TUN 型がちょうどよい。NuttX では NET_LL_TUN(LL は Link Layer)という種類で登録する。

usrsock とは

SPRESENSE の Wi-Fi は外付けモジュール GS2200M で、そのモジュール自身が TCP/IP の処理を持っている。NuttX は「ソケットの処理をこのモジュール(を操作するデーモン)に任せる」経路 usrsock を使う。ESP32-S3 は NuttX のネットワークスタックが直接 Wi-Fi を使う(native)。経路が違うので、2 つのボードで試す意味がある(スライド 31)。

③ このスライドの主張と根拠

主張:NuttX から見て wg0 は普通のネットワークデバイス。その下で WireGuard がパケットを暗号化した UDP に変える。ここから先の仕事は、上の層も下の層も変えずに、この真ん中を作ること。根拠は実装の構造(apps 版の nuttx-wireguardif.c、カーネル版の drivers/net/wireguard/wireguard.c、in-kernel-design.md)。

④ 話すときのポイント

This is one step more technical than the overview. Here the implementation starts.

概要より一段技術的な図です。ここから実装の話です。

From here on, the work is building this middle part — wg0 and the encryption — without changing the layers above or below it.

ここからの仕事は、上下の層を変えずに、この真ん中(wg0 と暗号化)を作ることです。

16 — Porting: four functions to write

Reusing wireguard-lwip without lwIP.

画像:renders/glasgow/slide-16.png · スライド本体で開く

① 画面にあるもの

3 段の箱。KEEP(そのまま使う):プロトコルと暗号(handshake、データ転送、BLAKE2s、ChaCha20-Poly1305、Curve25519)、OS に依存しない C。ADAPT(合わせる):OS 依存は wireguard-platform.h の 4 関数(時計、乱数、TAI64N 時刻、負荷の判定)。REPLACE(取り替える):wireguardif.c の lwIP 向けの登録とバッファ。NuttX には lwIP がないので、ここが本当の移植作業。

② 背景知識

移植(porting)とは

ある環境向けに書かれたプログラムを、別の環境(OS や CPU)で動くようにすること。全部を書き直すのではなく、環境に依存している部分だけを取り替えるのが上手な移植。そのためには、元のプログラムの中で「どこが環境に依存しているか」の境目がはっきりしている必要がある。

lwIP と wireguard-lwip

lwIP(lightweight IP)は、マイコン向けの小さな TCP/IP の部品。FreeRTOS などと組み合わせてよく使う。wireguard-lwip は、その lwIP の上で動くように書かれた WireGuard の実装(smartalock/wireguard-lwip)。NuttX は lwIP を使わず自前のネットワークスタックを持つので、lwIP に依存した部分は使えない。

wireguard_random_bytes()乱数。鍵や一時鍵に使う/dev/urandom から読む

MONOTONIC と REALTIME の違い:MONOTONIC は起動からの経過時間で、決して戻らない(ストップウォッチ)。REALTIME はカレンダーの日時で、設定し直すと進んだり戻ったりする(壁掛け時計)。タイマーにはストップウォッチ、相手に「今は何時」と伝えるには壁掛け時計を使う。この違いがスライド 33 の問題の根っこになる。

I did not have to rewrite anything, and that was not luck. That is what a clean line between the protocol and the OS gives you.

21 — Bug 1 / 7: A return code of 0 that did nothing

SO_RCVTIMEO

画像:renders/glasgow/slide-21.png · スライド本体で開く

① 画面にあるもの

setsockopt(SO_RCVTIMEO) は 0(成功)を返す。でも recvfrom() は永久に待つ。timeout は受け付けられ、そして無視された。完全なデッドロック:タイマーが動かない → handshake を送らない → 相手は黙ったまま → recvfrom() が戻らない。

② 背景知識

戻り値と errno

C の多くの関数は、成功すると 0、失敗すると -1 を返し、失敗の理由を errno という変数に入れる。プログラムは戻り値を見て「成功した」と判断する。ところが、成功を返したのに中身が働いていないことがある。今回はまさにそれ。

ブロッキングとタイムアウト

recvfrom() はデータが来るまで、そこで止まって待つ(ブロックする)。SO_RCVTIMEO は「最大○秒待ったらあきらめて戻ってこい」という設定。WireGuard は、受信待ちの合間に「しばらく何も来なければ、こちらから handshake を始める」というタイマー処理をする設計だった。

デッドロック

お互いが相手を待って、誰も進めなくなる状態。今回は 1 つの流れの中で起きた「鶏が先か卵が先か」。

エラーが出れば原因はすぐ分かる。しかしこの失敗は「何も起きない」という形で現れたので、ネットワークや相手側の設定を疑って時間を使った。

③ このスライドの主張と根拠

主張:setsockopt() が 0 を返しても、その設定が効いた証拠にはならない。対応していない設定は、分かりやすいエラーではなく、デッドロックとして現れることがある。根拠:apps 版sim(phase3-log.md「バグ1」)。wg show が latest handshake: (never) のまま、tcpdump でも送信パケットが 1 つも出ないところから、デバッグ出力で突き止めた。対応は SO_RCVTIMEO に頼るのをやめ、poll() の時間制限付き待ちに変えたこと(こちらは正しくタイムアウトした)。

④ 話すときのポイント

Setting a receive timeout returned zero, which means success. But recvfrom still waited forever.

受信のタイムアウトの設定は 0、つまり成功を返しました。でも recvfrom は永久に待ち続けました。

The option was accepted and then quietly ignored.

設定は受け付けられ、そして黙って無視されたのです。

⑤ 聞かれそうな質問

それは NuttX のバグですか?
当時の sim の構成で、recvfrom() に timeout が効かなかったという観察。作業記録では「NuttX 自体の制限の可能性があり、upstream で既知か確認する価値がある」とした段階で、本体のバグとして報告・修正したものではない。だから「NuttX のバグ」とは断言しない。教訓は「成功の戻り値を信じすぎない」。

22 — Bug 2 / 7: Created successfully. Did not survive.

pthread_detach

画像:renders/glasgow/slide-22.png · スライド本体で開く

① 画面にあるもの

受信スレッドは pthread_create() + pthread_detach() で起動した。wg コマンドが終わるとスレッドも止まった — ps にも出ない。作成直後に usleep() を入れるとスレッドの printf が出た — 作成はされていた。自分の思い違い:detach は「コマンドより長生きする」意味だと思っていた。実際はスレッドのメモリをいつ解放するかを決めるだけ。

② 背景知識

プロセス・タスク・スレッド

Linux では、実行中のプログラム 1 つをプロセスと呼び、その中に複数のスレッド(並行する実行の流れ)を持てる。NuttX では、プロセスに近い単位を task group(タスクグループ)と呼ぶ。NSH で wg up と打つと、wg のタスクグループができ、その中で受信スレッドを作った。

detach と join

スレッドが終わったとき、そのメモリ(戻り値など)を誰かが回収する必要がある。普通は親が pthread_join() で待って回収する。pthread_detach() は「待たなくていい、終わったら自動で片付けて」という指定。寿命を延ばす機能ではない。

usleep で見えたこと

作った直後に少し待つと、スレッドが動き出して printf を出した。つまり「作れていない」のではなく、「作れたが、コマンドが戻った瞬間に消えた」。この切り分けが原因の特定につながった。

③ このスライドの主張と根拠

主張:pthread_detach() はメモリの解放時期を決めるだけで、スレッドの寿命は決めない。detach したスレッドも、起動したタスクグループと一緒に死ぬ。だからカーネル版では、スレッドをドライバ自身が持つ(スライド 28)。根拠:apps 版sim(phase3-log.md「バグ2」:usleep(300000) を入れるとスレッドの printf が出る、入れないと 1 行も出ずに消える)。apps 版の対応は、pthread をやめて task_create() で独立したタスク wg_rx として起動すること。カーネル版 では受信スレッドはカーネルスレッド(wg_rx)で、wg_ifup で作り wg_ifdown で終わる(in-kernel-design.md)。

④ 話すときのポイント

My mistake was thinking that “detached” means “it lives longer than the command.”

私の間違いは、「detach したスレッドはコマンドより長生きする」と思っていたことです。

That is why, in the kernel version, the driver itself owns the thread.

だからカーネル版では、ドライバ自身がスレッドを持っています。

⑤ 聞かれそうな質問

apps 版ではどう直したのですか?
pthread ではなく task_create() で独立したタスクにした(ps にも独立したタスクとして出る)。根本的な解決は、カーネル版で「ソケットとスレッドはドライバが所有する」設計にしたこと。なお、プログラム(プロセス)が終わればその中のスレッドが全部終わるのは Linux でも同じで、detach はそれを変えない。

23 — Bug 3 / 7 · my favorite: ping works. TCP dies.

EBADF

画像:renders/glasgow/slide-23.png · スライド本体で開く

① 画面にあるもの

同じトンネルで ping は損失 0%。telnet の 3-way handshake まで成功するのに、その後に接続が死ぬ。ログ:wg_encrypt_and_send: psock_sendto ret=-1 errno=9 EBADF。成功した送信は全部 wg_rx タスクの中から。別タスクからの送信は EBADF。原因:fd は 1 つのタスクグループのもので、全体で共通ではない。修正:fd を使わない内部 API(struct socket に対する psock_*())で、どのタスクからも使える。

② 背景知識

fd(ファイルディスクリプタ)

ファイルやソケットを開くと、OS は小さな整数(3、4、5 …)を返す。これが fd。以後は「3 番に書く」のように番号で指定する。番号はタスクグループごとの表で引くので、同じ「3」でも、別のグループでは別のもの(またはなし)を指す。ホテルの部屋番号のようなもので、305 号室はホテルごとに別の部屋。

TCP の 3-way handshake

TCP は接続の最初に 3 回のやり取りをする:SYN(つないでいい?)→ SYN-ACK(いいよ)→ ACK(了解)。WireGuard の handshake とは別物。この 3 回が成功したので「TCP は動いている」と思えてしまった。

なぜ ping では見抜けなかったか

ping の返事、keepalive、WireGuard の handshake の返事、TCP の SYN-ACK は、どれも受信タスク自身が受け取ったその場で返していた。だから fd 3 が有効で、成功した。telnet で文字を打つと、そのデータは別のタスクから送られる。そこで初めて失敗した。

psock_*() と struct socket

NuttX の内部には、番号を経由せずにソケットの実体(struct socket、メモリ上のデータ)を直接扱う関数群 psock_*() がある。実体を指せば、どのタスクからでも同じソケットを使える。部屋番号ではなく、部屋そのものの住所を渡すイメージ。

③ このスライドの主張と根拠

主張:NuttX では fd は 1 つのタスクグループのもの。同じソケットを指していても、別のタスクはその番号を使えない。根拠:apps 版実機 ESP32-S3 でトンネル越し telnet をしたときに発見(phase4-log.md、DEVELOPMENT.md)。失敗していた「別のタスク」は、NuttX が起動時から持っている作業用タスク(LPWORK)で、wg_rx とは親子関係がないので fd 表を受け継いでいなかった。修正後、telnet でコマンド実行まで確認。カーネル版 はソケットを最初から struct socket として持つ。

ただし、psock_*() は「同じメモリ空間」でしか使えない内部 API なので、apps 版は FLAT ビルド専用になった。これがスライド 27 の「カーネルへ移す」理由になる。

② 背景知識

poll と polling

紛らわしいが別物。poll() は「データが来たら起こして」と OS に頼んで眠る関数(呼び鈴)。polling は自分で一定間隔ごとに見に行くこと(郵便受けを何度も覗きに行く)。poll() は fd を使う関数なので、fd をやめた修正(スライド 23)で使えなくなり、仕方なく polling にした。

なぜ 10 倍も遅くなるのか — TCP のやり取り

TCP は「受け取りました(ACK)」の返事が来るまで、次のデータをたくさんは送らない。1 往復ごとに最大 50 ms の余計な待ちが入ると、往復のたびにそれが積み重なり、全体の速度(スループット)が大きく落ちる。

コールバックとセマフォ

コールバックは「データが来たらこの関数を呼んで」と登録しておく仕組み。セマフォは「合図が来るまで眠り、合図で起きる」ための道具(駅のホームの発車ベル)。受信スレッドはセマフォで眠り、データが来るとコールバックがセマフォを鳴らして起こす。待つ時間は 0 で、暇なときは CPU も使わない。

③ このスライドの主張と根拠

主張:50 ms の polling は正しく動いたが、約 10 倍遅くした。測っていない応急処置は、タダに見えて 10 倍のコストを払っていることがある。根拠:apps 版 の開発記録(phase4-log.md:受信ループを psock_recvfrom(..., MSG_DONTWAIT) と usleep(50ms) の繰り返しにした経緯)。修正後の数字として、Q&A に ESP32-S3 実機・実 Wi-Fi でトンネル越し TCP 約 260 KiB/s、7 MB の連続転送(これも apps 版)。

注意:「約 10 倍」は約 1 桁という意味で、厳密に 10.0 倍と測った値として言わない。

stack size

画像:renders/glasgow/slide-25.png · スライド本体で開く

② 背景知識

シェルのリダイレクト

> は「コマンドの画面出力を、画面ではなくファイルに書く」というシェルの機能(リダイレクト)。NSH は wg のような組み込みアプリを別のタスクとして起動し、その出力をファイルにつなぎ替える。この組み合わせが ESP32-S3 の SPIFFS 相手だと固まった。原因はプラットフォーム側の相互作用と判断し、アプリ自身が fopen してファイルを書く wg saveconf を作って回り道した(wg setconf が自分でファイルを読むのと対称)。

スタックとは

関数を呼ぶたびに、その関数の作業メモリ(局所変数、戻り先)を積み上げる場所。関数から戻ると取り除く。皿を積み重ねるイメージ。スレッドごとに 1 本あり、大きさは作るときに決める。PC なら数 MB あるのが普通だが、マイコンでは数 KB しかない。

スタックがあふれると何が起きるか

上限を超えると、隣にある別のデータを上書きして壊す(スタックオーバーフロー)。すぐに止まるとは限らず、しばらくしてから関係ない場所で固まるので、原因を探しにくい。残り 176 B は、少し深い呼び出しが 1 つ増えれば越えてしまう幅。

なぜ sim では起きないか

sim は NuttX を PC のプログラムとして動かすので、スタックも PC 並みに大きく取られる(ある記録では約 72 KB)。3 KB で足りなくても、sim では余裕で収まってしまう。ファイルシステムも PC 側のものなので、SPIFFS の振る舞いも見えない。

stack coloration(スタックの塗り分け)

スタックを最初に決まった模様で塗っておき、後で「模様が消えた一番深いところ」を調べる。そこまでは実際に使われた、と分かる。この最大使用量を high-water mark(最高水位)と呼ぶ。洪水の後に壁に残る水の跡のようなもの。

③ このスライドの主張と根拠

主張:既定のスタックサイズは、本物のハードウェアで測るまではただの推測。sim の大きなスタックは問題を隠す。根拠:apps 版実機 ESP32-S3(code-review-2026-08.md)。

28 — The Kernel Design

A kernel netdev, an ioctl ABI, a write-only key.

画像:renders/glasgow/slide-28.png · スライド本体で開く

① 画面にあるもの

4 つの設計の札。Kernel netdev:netdev_lowerhalf で、自分の UDP ソケット・受信スレッド・タイマー・cookie を持つ — ドライバがソケットとスレッドを所有するので、起動したコマンドと一緒に死なない。ポインタのない単純な ioctl ABI:SIOCS/GWGIF、SIOCS/D/GWGPEER — PROTECTED / KERNEL ではカーネルが呼び出し元の構造体をそのままコピーするから。秘密鍵は書き込み専用:取得の ioctl は秘密鍵を返さない。カーネルの暗号は NuttX 自身のもの:crypto/ の BLAKE2s・ChaCha20-Poly1305・Curve25519。唯一のコピーしたコードは、オフラインの genkey 用にユーザー空間のコマンドに入れた MIT ライセンスの X25519。

② 背景知識

upper half と lower half

NuttX のドライバは 2 つに分けて作る。upper half は OS 共通の部分(ネットワークスタックとのやり取り)、lower half は機器ごとの部分(ここでは WireGuard の暗号化と UDP の送受信)。共通部分を毎回書かずに済む。netdev_lowerhalf はその新しい書き方。

所有権(誰が持ち、誰が片付けるか)

スライド 22・23 のバグは「スレッドやソケットを、いつ消えるか分からないコマンドが持っていた」ことが原因。カーネル版では、ドライバ自身がソケットと受信スレッド(wg_rx)を持ち、wg up で作り、wg down で片付ける。コマンドは「設定して」と頼んで終わるだけ。

ABI とポインタ

ABI(Application Binary Interface)は、アプリとカーネルが「どの番号の命令で、どんな並びのデータをやり取りするか」の約束。ポインタは「メモリの何番地にあるか」を表す値。PROTECTED や KERNEL では、アプリの「何番地」はカーネルから見ると別の場所か、見えない場所になる。だから構造体の中にポインタを入れると、カーネルはその先を正しく読めない。宅配便の箱に「中身は私の家の棚の 3 段目」と書いても、受け取る側はその棚を見られないのと同じ。中身そのものを箱に入れる(固定長でポインタなし)のが正解。

ioctl意味
SIOCSWGIF / SIOCGWGIFインターフェース(自分の鍵・待ち受けポート)を設定 / 取得
SIOCSWGPEER / SIOCDWGPEER / SIOCGWGPEER相手(peer)を設定 / 削除 / 取得

名前の規則:SIOC = Socket I/O Control、S = Set、G = Get、D = Delete、WG = WireGuard。

書き込み専用の秘密鍵

秘密鍵は wg から設定できるが、取得の ioctl は返さない。ただし、秘密鍵がどこにも残らないという意味ではない。再起動後に設定を戻すため、ユーザー側の設定ファイル(wg saveconf で保存)が秘密鍵を持っている(台本:"but it is still in the config file on the user side")。

なぜ X25519 だけコピーしたか

wg genkey はユーザー空間で鍵を作る。カーネルの Curve25519 を cryptodev(アプリからカーネルの暗号を使う窓口)経由で呼ぶこともできるが、そのためにはソフトウェア暗号の一式を丸ごと有効にする必要がある。鍵を 1 回作る掛け算のためにそれは重いので、小さな MIT ライセンスの X25519 だけをコマンド側に入れた。

図にはないが大事な設計:送信の行列

ロックは「この共有データを今触っているのは 1 人だけ」にする仕組み(トイレの鍵)。時間のかかる送信中ずっと鍵をかけたままだと、wg show や wg down まで待たされる。そこで、暗号化までを鍵の中で済ませ、出来上がった箱を行列に入れ、送るのは鍵の外で受信スレッドだけ、と分けた。

③ このスライドの主張と根拠

② 背景知識

nonce と counter

同じ鍵で何度も暗号化するとき、毎回違う値を混ぜないと暗号が破れる。この「1 回しか使わない値」を nonce(number used once)と呼ぶ。WireGuard では、パケットの通し番号(counter:0, 1, 2, …)を nonce に入れる。ChaCha20-Poly1305 の nonce は 12 バイトで、標準(RFC 8439)では「先頭 4 バイトは 0、後ろ 8 バイトに counter」。NuttX は counter を前の 8 バイトに置いていた。

境界値の落とし穴:0 は特別な値で、位置がずれていても「全部 0」で同じになる。0 だけで試すと、間違いが見えない。テストでは 0 だけでなく 1、2、大きな値も試す。

なぜ誰も気付かなかったか

NuttX の中に、この関数(64 ビットの counter を使う版)を呼ぶコードがなかった。使われていない関数のバグは、使われるまで見つからない。WireGuard が初めての利用者だった。

スタックとヒープ

スタックは関数ごとの小さな作業机(スライド 25)。ヒープは必要なときに確保して、使い終わったら返す大きな倉庫(malloc / free、カーネルでは kmm_malloc / kmm_free)。大きなデータは机ではなく倉庫に置く。6 KB の配列を 3 KB の机に置こうとして、机からあふれ、隣の倉庫の管理情報まで壊した(ヒープ破壊)。OS は続けられずに止まった(パニック)。

③ このスライドの主張と根拠

主張:handshake が動いても、データの経路やカーネルのコードが正しいとは限らない。どちらのバグも handshake の後で、本物のカーネルビルドで初めて出た。根拠:verification-matrix.md「Bugs found and fixed during verification」。

  • nonce:NuttX に以前からあったバグ(crypto/chachapoly.c)。sim の T1(最初のパケットより後のデータ)で発見。修正は memcpy(le_nonce_array + 4, ...)。既知の答えと比べる試験(TV、KAT)で counter 0/1/2 が pyca/cryptography と一致することを確認し、同じ修正で cookie の経路(XChaCha20-Poly1305)も直ることを確認。
  • 6 KB の配列:新しく書いたドライバ側のバグ(wg_set_if())。QEMU の T6(BUILD_KERNEL)だけで発見。sim の大きなスタックが隠していた。kmm_malloc / kmm_free に移して修正。

② 背景知識

乱数が弱いと何が起きるか

秘密鍵は乱数から作る。乱数が予測できれば、暗号がどれだけ強くても鍵が当てられる。コンピュータの乱数には 2 種類ある。

種類しくみたとえ
疑似乱数(xorshift128 など)「種」から計算で作る。種が同じなら毎回同じ列同じ順番に並べたトランプ
entropy pool割り込みのタイミングなど、予測しにくい出来事を集めて混ぜる毎回よく切ったトランプ

NuttX は構成によって /dev/urandom を xorshift128 で提供でき、その種がビルド時の値から来ることがある。そうすると、そのファームウェアを焼いたボードは毎回同じ秘密鍵を作る。handshake も ping もデモも動くのに、トンネルは無意味になる。

ゼロ化(zeroization)

使い終わった秘密をメモリ上で 0 に塗りつぶすこと。free() で返しただけでは、別の用途で上書きされるまで古いバイトが残る。紙の書類をゴミ箱に捨てるだけでなく、シュレッダーにかけるイメージ。

リークとソーク試験

リークは、確保したメモリやバッファを返し忘れて、少しずつ減っていくこと。すぐには壊れず、何時間・何日も経ってから足りなくなる。ソーク試験(soak test)は、長時間・多数回動かし続けて、資源が元に戻るかを見る試験。

rekey と鍵の寿命

33 — Design choice: trust the clock?

The timestamp problem has no easy answer.

画像:renders/glasgow/slide-33.png · スライド本体で開く

① 画面にあるもの

上に規則:相手は、これまで見た最新より新しくない時刻の handshake を捨てる。だから機器は、再起動の後でも、常にもっと新しい時刻を送らないといけない。4 つの案の表(フラッシュへの書き込み / RTC なしで動くか / 結果):実時刻 + この起動中の最大値(書き込みなし、動かない、採用)/ 毎回保存(毎回、動く、フラッシュが摩耗し handshake が遅くなる)/ フラッシュに範囲を予約(N 回に 1 回、動く、NuttX にないストレージの保証が要る)/ 追いつくまで待つ(なし、動かない、前回動いていた時間だけ待つ)。下に実機の結果:何も送らず、変えたのは 1 つだけ。時計未設定 → 75 秒で handshake なし、時計設定 → 4.1 秒。「Linux や wireguard-go と同じ規則を使い、それが救えない場合は警告を出すようにした」。

② 背景知識

リプレイ攻撃

攻撃者が、以前の正しいパケットを録画のように保存しておき、あとで送り直す攻撃。中身を解読できなくても、「同じ開始要求をもう一度受け付けさせる」ことができれば悪用できる。WireGuard は handshake の開始要求に時刻(TAI64N 形式、秒 8 バイト + ナノ秒 4 バイト)を入れ、相手(responder)は相手ごとに「今まで受け付けた最大の時刻」を覚えて、同じか古い時刻は捨てる。

今まで受け付けた最大: 1000
次が 1001 → 新しいので受け付ける
次が 1000 → 同じなので捨てる(録画かもしれない)
次が  500 → 古いので捨てる
RTC と再起動

RTC(Real-Time Clock)は、電池などで電源が切れても時刻を数え続ける時計の部品。PC やスマホには必ずある。小さなマイコンボードには付いていないか、電池がないことが多い。RTC がないと、再起動のたびに時計は決まった年(NuttX では 1970 年付近)から始まる。すると、再起動後に送る時刻は、相手が覚えている「前回の最大」より古くなり、捨てられる。

なぜ uptime(起動からの時間)ではだめか

最初の apps 版は、起動からの経過時間を時刻の代わりにしていた。再起動すると 0 付近に戻るので、前回の最大に追いつくまで、前回動いていたのと同じ時間だけ待つことになる。sim の再現実験(tai64n-reboot.md)では、回復に約 75 秒かかった。これは前回のセッションが短かったからで、1 か月動いていた機器は 1 か月つながらない。

フラッシュの摩耗と耐久性の保証

フラッシュメモリは書き込める回数に限りがあり、何度も同じ場所に書くと壊れる(摩耗、wear)。毎回の handshake(数分おき)に時刻を書き込むのは、それを一生続けることになる。もう 1 つの問題は、「書けた」と返ってきても、電源が切れた瞬間に本当に残っているか(耐久性の保証、durability contract)。sim の hostfs の sync は中身が空の関数を呼んで OK を返すだけなので、sim で書けても電源断について何も証明しない。

initiator と responder の非対称

時刻を送るのは handshake を始める側(initiator)だけ。応える側(responder)は自分の時刻を使わない。だから、PC から ping を送って PC 側が handshake を始めると、ボードは responder として答えるだけで、ボードの時計が狂っていても成功してしまう。

③ このスライドの主張と根拠

主張:時計がなければ新しい時刻は作れない。機器は自分からつなぎに行けないのに、ping の試験には合格してしまうことがある。採用したのは「実時刻 + この起動中の最大値」(Linux と wireguard-go と同じ規則。uptime には決して戻らない)。足したのは、デスクトップには要らなかった部分 — RTC のないボードで時計が一度も設定されていない(次の年より前を指している)なら、1 回だけ警告を出し、何が起きるかを言う。初めて会う相手は受け付けるので、時刻は送り続ける(拒否すると、まさにそういうボードで最初の組み合わせができなくなる)。

根拠:カーネル版実機 SPRESENSE の対照実験(TT、2026-09-28、evidence)。同じボード、同じ相手、同じイメージで、ボードには何も送らず、変えたのは時計だけ。

「75 秒」が 2 回出てくるので混ぜないこと。台本の "In my simulator test with the old uptime-based timestamp, recovery took seventy-five seconds" は、uptime を使っていた頃の sim の再現実験で「回復までにかかった時間」(tai64n-reboot.md:75.3 秒)。スライドの "no handshake in 75 s" は、実機 の対照実験で「75 秒見ていたが成立しなかった」(観測の打ち切り)。数字が同じなのは偶然なので、聞かれたらこの 2 つを分けて答える。

#14 が開いたままの理由:RTC のないボードを再起動後も救うには、時刻を電源断を越えて残す必要がある。正しい長期的な答え(フラッシュに範囲を予約し、RAM から使う)は設計済み(tai64n-design.md)だが、NuttX に耐久性の保証がないので意図的に実装していない。「解決したように見えて解決していない」ものを出さない、という判断。証拠が足りないからではない(tai64n-decision.md)。

② 背景知識

クライアント分離(AP isolation)

会場やホテルの Wi-Fi は、安全のため「同じ Wi-Fi につながった機器どうしは直接話せない」設定にしていることが多い。インターネットには出られるが、隣の PC やボードには届かない。今回の会場もそうで、PC からスタックちゃんへは ARP(同じネットワーク内で相手の機器を探す問い合わせ)すら通らなかった(stackchan-hardware-check §7)。

テザリング(ホットスポット)

スマホを小さな Wi-Fi ルーターにする機能。PC とスタックちゃんを両方スマホにつなげば、2 台だけの小さなネットワークができる。スマホを入れ直すとアドレスの範囲が変わることがあるので、スライドには wlan0 側の具体的なアドレスを載せていない(同 §9)。

2 種類のアドレス
物理のネットワーク(テザリング)   wlan0 = スマホが配るアドレス
VPN の中のネットワーク             wg0   = 10.10.0.1(PC側)/ 10.10.0.2(スタックちゃん)

telnet やブラウザは 10.10.0.2(トンネルの中の住所)に向ける。すると通信は wg0 を通り、暗号化された UDP としてテザリングを渡る。

Docker とコンテナ

Docker は、1 台の PC の中に独立した小さな Linux 環境(コンテナ)を作る道具。ラップトップは Windows だが、相手側にはコンテナの中の Linux カーネルの WireGuard を使う(Windows の公式クライアントではない)。トンネルは PC 側から張る:Windows のファイアウォールが受信を拒否するため、コンテナ側にスタックちゃんの宛先と 25 秒の keepalive を設定し、スタックちゃん側は最初の正しい handshake で相手の住所を覚える(同 §6)。

スタックちゃんの中身

M5Stack CoreS3(ESP32-S3)に、顔を描く画面、首を振る 2 つのサーボ、スピーカーを付けたもの。NuttX の上で、顔・まばたき・首振り・音声再生(stackchan アプリ)、telnet のサーバー(telnetd)、Web サーバーが動く。ボードの設定は esp32s3-devkit を流用している(CoreS3 専用の構成は NuttX にまだない)。

③ このスライドの主張と根拠

主張:スマホも会場も、見るのは暗号化された UDP だけ。間にサーバーもクラウドもない。根拠:stackchan-hardware-check-2026-10-08.md §6〜§9(PC 側コンテナからの handshake 成立、コンテナから ping 10.10.0.2 10/10、トンネル越し telnet と Web、再起動後に操作なしで全部上がる、会場の Wi-Fi の遮断、スマホでの構成、音声)。

② 背景知識

鍵をファームウェアに入れない理由

ファームウェアは機器に書き込むプログラムの塊。ビルド設定(Kconfig)に鍵を書くと、鍵がそのファイルに入る。ファイルを配ったり、ビルドのログが残ったりすると、鍵も一緒に漏れる。同じファイルを何台にも書けば、全部が同じ鍵になる。動作中に機器の上で鍵を作れば、鍵は機器の中(と保存した設定ファイル)にしかない。

層ごとに確かめる

「つながらない」には、いろいろな原因がある。1 つずつ切り分けると「どこが悪いか」が言える。

信号読み方確かめていること(台本より)たとえ
ROUTERルータールーター側が生きているか道路が通じているか
LANランボードがネットワーク上にいるか家に電気が来ているか
TUNタンWireGuard がトラフィックを運んでいるか専用線がつながっているか
TCPティーシーピーアプリのデータが流れているか会話が続いているか

たとえば ROUTER と LAN が生きていて TUN だけ止まれば WireGuard の問題、LAN から止まれば Wi-Fi やボードの問題、と言える。

③ このスライドの主張と根拠

主張:動作中の鍵設定と層ごとの確認が、「トンネルが落ちた」を「ルーター側が落ちた」に変える。それが、デモと「置いておけるもの」の違い。根拠:apps 版。動作中の鍵設定は wg コマンド(スライド 18)、設定の保存の不具合 2 件(#17)を修正済み(verification-matrix.md「Bugs found」)。長時間の運用では ESP32-S3 で 4 時間 28 分の連続稼働(1 分ごとの ping + telnet)の後、Wi-Fi ドライバ側のクラッシュで止まり、シリアルの記録で WireGuard とは無関係と特定できた(phase4-log.md)。4 つの信号の方針は coc-glasgow-outline.md にあり、検証マトリクスの試験項目ではない。

④ 話すときのポイント

Keys are no longer built into the firmware. You make them and set them at run time, and they never end up in the firmware image.

鍵はもうファームウェアに入っていません。動作中に作って設定し、ファームウェアのイメージには入りません。

40 — Giving back: sending it to NuttX

The Apache Way: small steps, in the open.

画像:renders/glasgow/slide-40.png · スライド本体で開く

① 画面にあるもの

4 つの段:小さな crypto: PR を先に(ChaCha20-Poly1305 の nonce の修正 — それだけで NuttX の役に立つ)→ 次にドライバの PR(net/wireguard — カーネルのデバイス、ABI、文書)→ 次にコマンドの PR(apps/system/wg)→ dev@nuttx.apache.org に出す準備ができた設計(checkpatch / nxstyle を通過、PR に分割、ライセンス確認済み — community over code)。下に状況:「作業は小さな PR に分割済みで、checkpatch を通り、1 コミットずつビルドできる。dev@ での議論と PR はこれから」。

② 背景知識

PR(Pull Request)と upstream

GitHub で「この変更を本家に取り込んでください」と頼む手続きが PR。本家(ここでは apache/nuttx と apache/nuttx-apps)を upstream、自分のアカウントに分岐したものを fork と呼ぶ。PR はメンテナーが読んでレビューし、直す点があればやり取りし、合意できれば取り込まれる(マージ)。

なぜ小さく分けるか

大きな PR は読むのが大変で、どこか 1 か所に問題があると全部が止まる。NuttX の CONTRIBUTING は「PR は小さく 1 機能」「PR の中のコミットは 1 つずつビルドと動作を壊さない」と定めている。だから「1 コミットずつビルドできる」ことを機械で確かめている。nonce の修正は WireGuard がなくても役に立つので、先に単独で出せば、ドライバが受け入れられるかどうかと関係なく本家が取り込める。

dev@ メーリングリスト

Apache のプロジェクトでは、大きな設計の相談はメーリングリスト(dev@nuttx.apache.org)で公開して行う。「コードを出す前に、設計を公開の場で話す」のが The Apache Way。

checkpatch / nxstyle と署名

NuttX のコードの書き方の規則を機械的に検査するツール。CI でも同じ検査が走る。署名(Signed-off-by)は「この変更は自分が出してよいものだ」と本人が証明する行で、本人が付ける。

③ このスライドの主張と根拠

主張:crypto の修正を単独の PR にすれば、ドライバが受け入れられなくても NuttX はそれを取り込める。根拠と現状(merge-strategy.md、submission-checklist.md):

  • 最新の upstream に載せ替え、CONTRIBUTING に合わせて PR に分けた。中心は 5 本(PR-C:crypto、PR-N:nxstyle の除外、PR-K1:ドライバ、PR-D:system/wg の文書、PR-A:apps のコマンド)で、任意で PR-K0 / K0'(SPRESENSE の起動回帰 #9 と usrsock の修正 #10)。スライドの 3 段は、このうちの大きな流れ(crypto → ドライバ → コマンド)。
  • 各コミットを 1 つずつ取り出して -Werror でビルド、checkpatch.sh -g も通過(submission-checklist §2)。
  • ブランチはまだローカルだけで、署名はこれから本人が付ける。fork への push、PR、dev@ への投稿はまだ何もしていない(同 §1)。

「もう PR を出した」「マージ可能」とは言わない。細かい分け方を聞かれたら「本家の規則に合わせて、文書と style の例外を別の PR にしている」と答える。

First, a small crypto PR for the nonce fix, because it is useful on its own and helps everyone.

The design discussion and the upstream PRs are the next step; they have not started yet.

間

Community over code とは、仕事が本当はどこまで来ているかを正直に言い、レビューに変えてもらうことです。

41 — Takeaways: what to take home

Three things to carry out.

画像:renders/glasgow/slide-41.png · スライド本体で開く

① 画面にあるもの

3 つの教訓。① 簡単な試験は通り、深い試験は落ちる — 深く試す:長いデータ、本物のハードウェア、本物のカーネルビルド。「handshake した」だけでなく。② きれいな OS の境界は報われる — 4 種類の CPU、3 つの NuttX のバージョン、変更なし。③ プロジェクトへの移植はプロジェクトを良くできる — 途中で NuttX に隠れていたバグを 2 つ見つけた:ChaCha20-Poly1305 の nonce と、このボードで素のリリースがシェルまで起動しない起動のバグ。

② 背景知識

2 つ目の NuttX のバグ(起動の回帰、#9)

回帰(regression)は、以前動いていたものが、変更によって動かなくなること。SPRESENSE(cxd56)で CONFIG_RTC_HIRES(高分解能の RTC)を有効にすると、NuttX 13.0.x と master の素のリリースがシェル(NSH)まで起動しなかった。

仕組み(台本と Dockerfile のコメントより):NuttX の時間を進める仕組み(watchdog、決めた時間後に関数を呼ぶタイマー)が、時刻を RTC から読むようになった。RTC が動き出す前は時刻が 0 のまま進まないので、「RTC の起動を最後まで終わらせる」はずの watchdog が永久に発火しない。鶏と卵で止まる(スライド 21 と同じ形)。

「クリーンなチェックアウト(手を加えていない取得)からボードのイメージを作れるようにしたい」と思ったから見つかった。本家にはまだ入っていない(merge-strategy では任意の小さな PR-K0 として出す候補)。

3 つ目(台本だけにある):自分のドライバのバグ

台本は最後に「3 つ目は自分のドライバの中にあり、本物のカーネルビルドだけがそれを見せた。sim では決して見えなかった」と付け加える。これはスライド 29 の 6 KB の配列のこと。スライドの「two hidden NuttX bugs」は NuttX 本体の 2 つで、3 つ目はドライバ側なので数え方が違う。
