## 03 Apache NuttX とは 〔51秒〕

**[スライド]** POSIX 準拠 / 数十 KB から / 対応アーキ / 「効いたところ」カード

**[話す]**
NuttX は Apache Software Foundation で開発されている組み込み向けの RTOS です。最大の特徴は POSIX 準拠であることで、`open` や `socket`、`pthread` といった Linux でおなじみの API がそのまま使えます。小さいけれど Linux っぽく書ける、というのが売りです。

実際これは効きました。OS 依存の部分をソケットとスレッドだけに寄せられたので、プラットフォーム層は 186 行で済んでいます。おかげで 4 つのアーキテクチャで無変更で動きました。

**[間]** ここで少しトーンを落として——

ただ、この「Linux っぽい」が後半で牙をむきます。

## 04 WireGuard とは 〔43秒〕

**[スライド]** Linux 5.6 でマージ / 暗号スイート固定 / 行数比較表(4,000 行)

**[話す]**
WireGuard は比較的新しい VPN プロトコルで、Linux カーネル 5.6 でマージされています。何が嬉しいかというと、とにかく実装が小さいことです。OpenVPN や IPsec が十万行から数十万行あるのに対し、WireGuard は約 4,000 行です。

なぜ小さいかというと、暗号スイートを固定してネゴシエーションをなくしたからです。実装が小さいということは、監査しやすいということであり、そして**組み込みに載る**、ということです。ここが今回の出発点です。

## 05 なぜ組み込みに VPN が要るのか 〔40秒〕

**[スライド]** 選択肢 A/B/C の 3 カード + 「本来の答え」

**[話す]**
そもそもなぜ組み込みに VPN が要るのか。機器を現場に設置したあと、ファームウェアを更新したりログを取ったりデバッグしたりする必要が出てきます。そのときの現実的な選択肢が、この 3 つです。

グローバル IP を晒すか、独自プロトコルを作り込むか、ベンダーのクラウドに繋ぐか。どれも嬉しくありません。本来なら VPN を張ればいい話なのに、NuttX にはその選択肢がありませんでした。そして WireGuard は小さいので載る。これが動機です。

## 06 NuttX が VPN を話せると何が変わるか 〔63秒〕 <sub>— 20分枠では落とす</sub>

**[スライド]** 4 つの効用 + デモの意味

**[話す]**
少し夢の話をさせてください。NuttX が VPN を話せるようになると何が変わるか。やりたいことが増えるというより、**やりたかったことが普通の方法でできるようになります**。

現場の機器に SSH で入る。ログを回収する。センサのデータを取りに行く。全部、いつものネットワークの道具のままできます。機器がクラウドに合わせるのではなく、クラウドを機器のネットワークに引き込める。そして相手は既存の WireGuard サーバでいい。独自プロトコルではないことが、そのまま価値になります。

このあとのデモで、ESP32 の上で Web サーバを起動してブラウザから開きます。特別なクライアントは要りません。トンネルの向こうのマイコンが、ただの LAN 上のホストとして振る舞っている。それが言いたいことです。

## 08 設計判断: netdev として実装する 〔61秒〕

**[スライド]** lwIP / NuttX 対比表 + 「配線は UDP ソケット」カード

**[話す]**
ここが最初の設計判断です。NuttX は lwIP を使っておらず、独自のネットワークスタックを持っています。NIC の抽象化も、バッファ管理も、登録 API も、送信の契機も全部違うので、既存の netif グルーはそのまま使えません。

そこで NuttX の TUN ドライバを手本にして、`wg0` を仮想 NIC として登録する形で書き直しました。アプリから見ればただのネットワークインターフェースなので、`ifconfig` も既存のアプリもそのまま動きます。

**[間]** ——ここが伏線。ゆっくり。

ポイントは、この仮想 NIC の「配線」が、物理的なイーサネットではなく **UDP ソケット** だということです。当たり前のことを言っているようですが、この一点が後で 3 つ目の落とし穴を生みます。覚えておいてください。

## 14 落とし穴 1: SO_RCVTIMEO 〔54秒〕

**[スライド]** setsockopt は 0 を返すが recvfrom が戻らない / 鶏卵カード / poll への修正

**[話す]**
1 つ目。受信スレッドは、UDP をタイムアウト付きで待って、タイムアウトするたびにハンドシェイクや keepalive のタイマー処理を回す設計にしていました。

`setsockopt` でタイムアウトを設定すると、戻り値は 0 で成功します。ところが `recvfrom` は永久にブロックしました。相手から何か来ない限り戻ってこない。でも、こちらからハンドシェイクを送らないと相手は何も送ってこない。完全な鶏と卵です。

**[間]** 右下の教訓を指す。

教訓は、戻り値が 0 でもその機能が実装されているとは限らない、ということです。**設定したことを確認するのではなく、期待した挙動を確認しないといけない。** `poll` に変えて解決しました。

## 15 落とし穴 2: detach した pthread 〔57秒〕 <sub>— 20分枠では落とす</sub>

**[スライド]** pthread_create + detach が生き残らない / usleep で printf は出る / task_create への修正

**[話す]**
2 つ目。受信スレッドを `pthread_create` して `pthread_detach` していたんですが、`wg` コマンドが終了した瞬間にスレッドが動かなくなりました。`ps` にも出てきません。

面白いのは、`pthread_create` の直後に `usleep` を入れるとスレッド内の `printf` が出ることです。つまり生成自体はされている。POSIX の建前では detach したスレッドは生成元と無関係に生き続けるはずなんですが、そうなりませんでした。

`task_create` で独立したタスクにして解決しました。ここでも同じで、**生成に成功したことは、生き続けることの保証ではない。** `ps` で存在を確認するまで信じない、という話です。

> **20分枠で落とす場合:** 14 の最後に「同じように、`pthread_detach` したスレッドがコマンド終了で消える、というのもありました」と一言だけ添えて 16 へ。

## 16 落とし穴 3(症状): ping は通るのに TCP だけ死ぬ 〔64秒〕

**[スライド]** 3 カード(ping 0% / telnet バナー届かず / LAN 直結は正常)+ 絞り込み

**[話す]**
3 つ目。これが一番厄介でした。実機で ping は完璧に通ります。0% パケットロスです。

ところが同じトンネルで telnet すると、TCP の 3-way ハンドシェイクまでは成立するのに、telnetd が出すバナーが 1 バイトも届かない。切り分けのために WireGuard を使わず同じ LAN で直接 telnet したら、正常に動きました。つまり telnetd も TCP スタックも悪くない。

`wg0` の実装の、**TCP のデータを送る経路だけ**が壊れている。暗号化もハンドシェイクも ICMP も SYN-ACK も動いているのに、です。

正直に言うと、ping が通っていたせいで「送信経路は大丈夫だろう」と思い込んで、しばらく別のところを探していました。これがいちばん時間を溶かしました。

## 17 落とし穴 3(犯人): EBADF 〔58秒〕

**[スライド]** ログ 2 行(errno=9)/ 成功する送信・失敗する送信の 2 カード

**[話す]**
送信経路にログを仕込んで実機で再現させたところ、`sendto` が `errno=9`、つまり `EBADF`、不正なファイルディスクリプタを返していました。

**[間]** 左右のカードを順に指す。

そして成功する送信と失敗する送信が、きれいに分かれていました。成功するのは受信タスク自身のコンテキストから出るもの。ハンドシェイク応答、keepalive、ICMP の echo reply、そして TCP の SYN-ACK です。**ping が通ったのも、3-way ハンドシェイクが成立したのも、全部これです。**

失敗するのは LPWORK というワーカースレッドから出るもので、これが TCP のアプリケーションデータ全部に相当していました。同じソケット、同じコード、**呼ぶタスクだけが違う。**

## 18 落とし穴 3(原因): fd はタスクグループに閉じている 〔76秒〕

**[スライド]** 2 つのタスクグループの図。真ん中に「親子関係なし」

**[話す]**
原因はこうでした。NuttX のファイルディスクリプタは、**タスクグループ単位でスコープされます**。UDP ソケットの fd を持っているのは受信タスクとその子孫だけです。

ところが LPWORK は起動時から存在する独立したシステムタスクで、受信タスクとは `task_create` の系譜が一切つながっていません。だから LPWORK の fd テーブルにはそのソケットが存在せず、`EBADF` になります。

**[間]** 図の左半分を指す。

ping が通ったのは、ICMP の応答が `ipv4_input` の呼び出しの中で同期的に作られて、受信タスクのコンテキストのまま送り返されるからです。TCP の SYN-ACK も同じ。だからハンドシェイクまでは成立する。でもアプリケーションのデータは非同期にキューされて LPWORK から出るので、そこだけ無言で死ぬ。

**[間]** ——今日いちばんの山。ゆっくり。

つまり「ping が通る」は、**送信経路が正しいことの証明になっていませんでした。半分しか通っていなかった**んです。

---

## 19 落とし穴 3(修正): psock_*() へ 〔63秒〕

**[スライド]** psock API / 差分 / 「これは借金でもある」カード

**[話す]**
修正は、fd テーブルを経由しない内部 API に切り替えることでした。`psock_sendto` などの API があって、これは `struct socket` という構造体を直接ポインタで受け取ります。ただのメモリ上の構造体なので、どのタスクから触っても問題ありません。

この修正で、さっきデモでお見せした telnet と Web サーバーが動くようになりました。

**[間]** 右下のカードへ。ここは言い訳せず、淡々と。

ただ、正直に言うとこれは**借金**でもあります。`psock` は内部 API なので、この実装は FLAT ビルド前提になりました。PROTECTED や KERNEL ビルドではアドレス空間が分かれるので、別の設計が要ります。ここは upstream に出すときの論点になるので、隠さずに Issue に立てて相談するつもりです。

## 20 代償と回収: 50ms が 10倍を隠していた 〔76秒〕

**[スライド]** 24 → 260 KiB/s の大きな数字 / RTT 表 / rekey の副産物

**[話す]**
実はさっきの修正には代償がありました。`sendto` を内部 API に変えたのはいいのですが、`poll` も同じく fd ベースなので使えなくなったんです。そこで暫定的に「50 ミリ秒ごとに覗きに行く」ポーリングにしました。

**[間]** ——ここが転換点。

このとき私は「アイドル時に CPU を無駄に起こすだけだろう」と思っていたんですが、これが間違いでした。パケットが届いてから最大 50 ミリ秒待たされるので、**スループット自体が律速されていた**んです。

`psock_poll` にコールバックを仕込んでセマフォで待つ形に直したところ、スループットが 24 KB/s から 260 KB/s へ、約 10 倍になりました。負荷時の ping も 1 秒近くかかっていたのが数十ミリ秒です。

**[間]** 右下のカード。

おまけに、7 MB を連続で流している最中に鍵の再ネゴシエーション、rekey が発生して成功することも確認できました。これは今まで一度も通っていなかった経路です。**長く流さないと出てこない挙動**でした。

## 21 落とし穴 4: sim では通るのに実機が固まる 〔87秒〕

**[スライド]** リダイレクトで固まるログ / saveconf への変更 / 検証値のカード

**[話す]**
4 つ目。設定の永続化を実装したとき、保存はシェルのリダイレクトで済ませるつもりでした。`wg showconf` の出力をファイルに流すだけです。

これが**ボードごと固まりました**。シミュレータでは通るのに、実機の SPIFFS 上でだけ固まる。原因は、NSH が builtin コマンドを別タスクとして spawn していて、その標準出力を SPIFFS 上のファイルに向けると詰まる、というものでした。

SPI フラッシュ操作タスクのスタックを増やしても直りませんでした。ただ、調べる過程で `ps` を見たらそのタスクのスタック使用率が 80% を超えていたので、その修正自体は残してあります。

最終的には、リダイレクトに頼らず `wg saveconf` が自分で `fopen` して書く形にしました。

**[間]** 右下のカード。ここは検証の作法の話なので、少し丁寧に。

それと、検証のときに気をつけたのが、**Kconfig のデフォルト値では絶対に出てこない値**を使うことです。keepalive を 33 と 44 にして、ピアを 2 つにして保存する。読み出せた値がビルド時の値なのか、本当にファイルから来たのか、区別できるようにしています。

## 22 実測が覆した数字: スタック 〔88秒〕

**[スライド]** 3 段階の計測表 / 3072 → 4096 → 6144

**[話す]**
5 つ目。受信タスクのスタックサイズが当初 3072 バイトだったんですが、これは誰も測っていない数字でした。

さっき話したとおり、このタスクは `ipv4_input` を自分のスタックで呼ぶので、TCP スタックの深さが丸ごと乗ります。しかも ping や TCP の ACK のように即座に返すパケットは、**返信の暗号化までこのスタックの上で走ります**。

実機で計測したら、7 MB の TCP と ping フラッドをかけたときのピークが 2960 バイトでした。それで 4096 にすれば約 38% の余裕がある、と結論しました。

**[間]** ——ここで一拍置いてから。

ところが、後日のクラッシュダンプで**この結論が否定されました**。数時間動かしたあとの高水位が 3392 バイトだったんです。私が測ったのは最悪ケースではありませんでした。深いパスは、パケットがどの状態の組み合わせで届くかに依存するので、短時間の負荷試験では出てこないんです。

今は 6144 にしています。そして、どうやって測ったかと、**短時間では足りないということ**を、Kconfig のヘルプに書きました。次に触る人が同じ穴に落ちないように。

## 23 実用に耐えるまで 〔65秒〕 <sub>— 20分枠では落とす</sub>

**[スライド]** Before / ランタイム設定 / 永続化+自動起動 の 3 カード + ピア数と RAM の表

**[話す]**
デモが動いたあと、運用できるものにする作業をしました。

まず、鍵が Kconfig にベタ書きだったのを、実行時に設定できるようにしました。ビルド成果物に鍵が焼き込まれるのは良くないですし、設定を変えるたびに再ビルドが必要でした。実際、デモの準備でここが一番面倒でした。

この表はそのまま Kconfig のヘルプに載せています。組み込みでは RAM が直接のコストなので、「1 から 16 まで選べます」とだけ書かれても選べないからです。

## 24 長時間動かして、犯人を探す 〔101秒〕 <sub>— 20分枠では後半のみ 50 秒に圧縮</sub>

**[スライド]** 4 項目の監視 / ログ 2 行 / 1 回目・2 回目のカード

**[話す]**
長時間動かす話です。ボードを置きっぱなしにして監視していたんですが、最初の版はトンネルしか見ていませんでした。だから止まったときに、ファームが落ちたのか、Wi-Fi が切れたのか、私の PC 側の問題なのか、**切り分けられませんでした**。

書き直して、1 分ごとに 4 つを独立にサンプルするようにしました。ルータ、ボードの LAN アドレス、トンネルのアドレス、そして TCP でログインしてコマンドが返るか。これで、止まったときにログが**診断**になります。

**[間]** 右上のカードへ。

1 回目は 4 時間 28 分で止まりました。クラッシュダンプが取れていて、Wi-Fi タスクの中で、タイマーのリストの NULL リンクを辿っていました。これは ESP32-S3 の **Wi-Fi ドライバ側のバグ**で、WireGuard ではありませんでした。しかも調べたら、該当のファイルは upstream の master では削除済みでした。報告するより NuttX を新しくするのが筋、ということになります。

**[間]** 右下のカードへ。ここは歯切れよく、言い訳せず。

2 回目は 3 時間 36 分で止まりましたが、こちらは**原因が言えません**。シリアルログにパニックが 1 件もなく、ネットワークより先に USB ポートが消えています。電源が落ちたか物理的に抜けたかと整合しますが、証明ではありません。分からないものは分からないと書きました。

> **圧縮版(50秒):** 冒頭の監視設計の説明を「止まったときに原因を切り分けられるよう、1 分ごとにルータ・LAN・トンネル・TCP の 4 つを独立に見る監視を書きました」の 1 文にして、1 回目・2 回目の話へ直行。

## 25 移植性の答え合わせ 〔73秒〕 <sub>— 20分枠では落とす</sub>
