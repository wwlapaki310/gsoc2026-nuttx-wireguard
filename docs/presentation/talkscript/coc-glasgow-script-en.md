## 5 — Project Overview (2:28 → 3:12)

**On slide:** The wg0 netdev picture: application / NSH, the NuttX network stack, wg0 next to eth0 / wlan0, a UDP socket underneath, the Internet, the peer.

**Say:**
- Here is the whole idea in one picture.
- Apache NuttX is an RTOS (real-time operating system) that follows POSIX (the Portable Operating System Interface) and has its own TCP/IP stack. It had no VPN. This project adds wg0 as a virtual network interface. Applications see a normal interface. Under it, the encrypted data travels over a UDP socket. The other side is a real WireGuard peer — Linux, Windows, or another gateway.
- Because NuttX follows POSIX and uses BSD sockets, it is a good fit for this work. FreeRTOS and Zephyr can run a VPN too. But on NuttX, a VPN can become a normal network device very naturally.

## 12 — Problem: Reaching a Device From Far Away (8:13 → 9:05)

**On slide:** Engineer → Internet → router → Wi-Fi → NuttX device, showing that WPA2/WPA3 covers only the Wi-Fi hop; cards: open it to the Internet / make your own protocol / use a vendor's cloud.

**Say:**
- Now, the problem itself.
- Wi-Fi security is real, but it protects only one part of the path: the radio link between the device and the access point. Everything before that — the engineer, the Internet, the router — is outside what WPA2 or WPA3 (Wi-Fi security) can protect. What I needed was a secure path for the whole way, from the engineer to the device, not just the last few meters.
- Without that, every choice has a problem. You can give the device a public IP and hope. You can make your own secure protocol and keep it working forever. Or you can hand the connection to a vendor's cloud. The same problem appears in edge AI, industrial IoT, and remote systems in general. It is not limited to this project.

## 13 — Options: Other Ways to Reach a Device (9:05 → 10:24)

**On slide:** A table of seven ways (open a port / HTTPS to a cloud API / MQTT broker / reverse tunnel or relay / VPN on the router / carrier closed network / VPN on the device) against: who connects, any service or not, server in the middle, where security ends, what NuttX already has.

**Say:**
- Before I chose WireGuard, I compared the usual ways to reach a device.
- Opening a port is easy, but then the whole Internet can reach the device. HTTPS and MQTT (a small messaging protocol) are what most IoT products use. The device connects out to a server, so NAT (network address translation) is not a problem, and NuttX already has clients for both. But you only get the messages you designed — you cannot log in or open a web page on the device. And the security ends at the broker or the cloud.
- A reverse tunnel gives you one port through a relay server. A VPN on the router is great when the router is yours. But the last part of the path, on the LAN, is not protected. And at a customer's site, the router is usually not yours. A carrier closed network works only over cellular, and you need a contract.
- A VPN on the device is the only row that has all three: any IP service, no server in the middle, and security all the way to the device. MQTT and HTTPS are still the right tools for data. This is for maintenance access.

**If asked about Tailscale or ZeroTier:** they are also a VPN on the device, but they usually need a bigger OS than a microcontroller has today (footnote on the slide).

## 14 — Solution: Why WireGuard (10:24 → 11:17)

**On slide:** Engineer / Linux / Windows ⟷ WireGuard tunnel ⟷ NuttX device; modern IP-layer VPN / UDP transport, public-key peers / already everywhere.

**Say:**
- So, why WireGuard?
- WireGuard is a modern VPN that works at the IP layer. It is small and simple by design, with much less code than IPsec or OpenVPN, and that matters a lot on a microcontroller. It runs over plain UDP, and each peer is known by its public key, not by certificates or a long setup. If a packet does not carry the right key, WireGuard does not answer at all — to everyone else, the device is just a brick wall. And most importantly, it is a standard. It has been in the Linux kernel for years, there is an official Windows client, and the other end can be any WireGuard peer.
- So I chose a standard protocol, instead of making my own or depending on a vendor's cloud.

## 15 — Architecture: WireGuard on the NuttX Network Stack (11:17 → 12:05)

**On slide:** Application → TCP/UDP/IP → wg0 (NET_LL_TUN netdev) → WireGuard encrypt/decrypt → UDP socket → wlan0 / usrsock → network, with TX and RX arrows.

**Say:**
- This is one step more technical than the overview. This is where the implementation starts.
- Going out, a packet comes down from the application through TCP or UDP and IP, and reaches wg0 like any other network device. WireGuard encrypts it, and it leaves as a UDP packet — through wlan0 on a board, or through usrsock when the Wi-Fi chip itself works through sockets. Coming in is the same path the other way: a UDP packet arrives, WireGuard decrypts it, and it is passed up to wg0 as if it came in on a normal interface.
- From here on, the work is building this middle part — wg0 and the encryption — without changing the layers above or below it.

## 17 — Porting Strategy: Reusing wireguard-lwip Without lwIP (12:15 → 13:18)

**On slide:** Three cards: protocol & crypto (KEEP) / platform hooks (ADAPT, the four functions in wireguard-platform.h) / lwIP network glue (REPLACE).

**Say:**
- Why I started from wireguard-lwip, an existing open-source WireGuard, and did not write the crypto myself.
- wireguard-lwip is cleanly split into three layers. The protocol and crypto — the handshake, the data transport, BLAKE2s, ChaCha20-Poly1305 and Curve25519 — are portable C that does not depend on any OS. I used the crypto without changes. The protocol core needed two small fixes later, after a review, and they are written down in PATCHES.md. Everything that depends on the OS was already kept behind one small header file, as four functions. I only had to replace the lwIP network glue — the part that registers an lwIP netif and handles lwIP buffers — because NuttX does not have lwIP at all.
- I did not have to rewrite the protocol or the crypto, and that was not luck. That is what a clean line between the protocol and the OS gives you. Because of it, this port took weeks, not months.

## 18 — Design: Mapping lwIP onto NuttX netdev (13:18 → 13:47)

**On slide:** netif → net_driver_s, pbuf → iob, netif_add() → netdev_register(), callbacks → devif_poll().

**Say:**
- This was the most important porting decision.
- Instead of bringing lwIP into NuttX, I matched each lwIP idea to NuttX's own. lwIP's network interface becomes a NuttX network driver, lwIP's packet buffers become NuttX's I/O buffers, adding an interface becomes registering a NuttX network device, and the send callback becomes NuttX's own poll. wg0 is registered as a TUN (tunnel) type network device, and the “wire” under it is a UDP socket.

## 21 — Where It Was Hard: Six Bugs (14:45 → 15:54)

## 22 — Bug 2/6: ping Works, TCP Dies (15:54 → 16:49) *(my favorite)*

**Say:**
- This is my favorite bug in the project.
- On the same tunnel, ping was perfect, and even a TCP handshake finished — and then the connection died. When I added logging to the send path, it showed EBADF: bad file descriptor. All the sends that worked happened inside the receive task itself — handshake replies, keepalives, ping replies, the SYN-ACK (the second step of a TCP connection). Sends from any other task failed.
- The reason: in NuttX, a file descriptor belongs to one task group. It is not shared by the whole system. The fix was to stop using file descriptors and use NuttX's internal socket API. It works on a struct socket, which is just memory, so any task can use it. That is exactly why the kernel version keeps the socket as a struct socket.

## 23 — Bug 3/6: "No Real Impact" Was 10× (16:49 → 17:30) *(cut candidate 3)*

**Say:**
- The third: something I never measured.
- The fix without file descriptors also broke poll, because poll works with file descriptors. So, as a quick fix, I checked the socket every fifty milliseconds. I thought the only cost was waking up the CPU when it was idle. I was wrong. Every packet that arrived waited up to fifty milliseconds, and that alone limited the speed — about ten times slower than it should have been. I thought it had no real cost, and it cost ten times. The real fix was a proper wait: the socket wakes the thread up when data arrives.

## 26 — Version 2: WireGuard as a NuttX Kernel Driver (18:06 → 18:53)

**On slide:** Two panels: Version 1, an app (in apps/, uses kernel internals, FLAT only, never an in-tree driver) / Version 2, a kernel driver (drivers/net/wireguard, set up by a small wg command through ioctl, made for FLAT, PROTECTED and KERNEL). One line on the three build modes.

**Say:**
- Why did I move it into the kernel?
- Version one is an app. It lives in apps and reaches into socket internals of the kernel. That works in a FLAT build, where everything shares one memory space. But it can never be a proper in-tree driver, and it cannot work in PROTECTED or KERNEL builds, where apps and the kernel are kept apart.
- So I moved the device into the kernel, with the other network drivers, and a small wg command sets it up through ioctl (input/output control). Version one showed that the protocol works on NuttX. Version two is about fitting NuttX itself: a normal device, in every build mode, in a shape the community can review.

## 27 — The Kernel Design: The Big Picture (18:53 → 19:39)

**On slide:** A picture: user space holds only the wg command; an ioctl (one flat struct, no pointers; the private key is write-only) crosses the user/kernel boundary to wg0 in the kernel, which owns its UDP socket and RX thread, keeps timers / peers / cookies and uses NuttX crypto, between the NuttX network stack and the encrypted UDP to the peer.

**Say:**
- This is the shape of the real driver.
- In user space, there is only a small wg command. It sends settings to the kernel through ioctl. Each ioctl carries one flat struct with no pointers inside, so in PROTECTED and KERNEL builds the kernel never has to follow a pointer into user memory. The private key is write-only: no ioctl ever gives it back.
- In the kernel, wg0 is a normal network device. It owns its UDP socket and its receive thread, so the thread and socket bugs from version one cannot happen, by design. The crypto is NuttX's own. The protocol core is still derived from wireguard-lwip under BSD-3-Clause, and the LICENSE file says so.

## 28 — Bugs 5 & 6/6: Two More Bugs, One in NuttX Itself (19:39 → 20:46) *(locked with the kernel design)*

**On slide:** Two panels: NuttX's own chacha20poly1305 nonce bug (handshake works, data after the first packet fails; two-line crypto: fix) / a BUILD_KERNEL-only crash (6 KB array on a 3 KB kernel stack, moved to the heap). One line: SPRESENSE did not boot with CONFIG_RTC_HIRES on 13.0.1 / master; fixed locally, report drafted, not sent.

**Say:**
- On the way into the kernel, two more bugs came, and one of them was in NuttX itself.
- First, NuttX's own ChaCha20-Poly1305 wrote the counter into the wrong bytes of the nonce. When the counter is zero, both layouts are the same, so the handshake works, and then data packets after the first one fail to decrypt. Nothing in NuttX had called this code before, so nobody had hit it. It is a two-line fix, kept as its own crypto change.
- Second, a crash only in a kernel build. Setting the peers put a six-kilobyte array on a three-kilobyte kernel stack. In the simulator, with big stacks, it never showed up. It is the same stack lesson as bug four, one level deeper. I moved the array to the heap.
- One more from the board side: on NuttX 13.0.1 and master, SPRESENSE did not boot with the high-resolution RTC (real-time clock) option. I found the cause and fixed it locally. The report is drafted, but not sent.

- Let me be exact about which version ran where. There are three build modes, and I keep them apart.
- FLAT, on real boards. On October twelfth, I ran the exact series I prepared for upstream on the ESP32-S3 inside the StackChan: a handshake with Linux WireGuard, and ping both ways, up to the full packet size. An earlier build of the driver ran on both boards over real Wi-Fi with the Windows client. On SPRESENSE I measured memory: after forty down-and-up cycles, it was exactly the same. The receive thread used fourteen hundred and seventy-two bytes of a six-kilobyte default. That default used to be a guess. Now it is a measurement.
- KERNEL, in QEMU. The wg command is a separate program that reaches the driver through system calls, and the tunnel reaches Linux. With four CPUs, I flooded it while changing the settings. No fault, but that is one scripted run, not a full search for race conditions.
- PROTECTED, also in QEMU. The tunnel works, and every ioctl crosses the memory boundary. Repeated runs sometimes faulted. The cause was a stack overflow in the wg command, because in this mode a system call runs on the caller's own stack. A bigger default fixed it: twenty out of twenty.
- What I have not shown is PROTECTED or KERNEL on real hardware. I tried PROTECTED on the CoreS3, but that board does not boot any bootloader-based image, and that is not a WireGuard problem. Version one, the app, also ran on both boards. The records are on GitHub.

## 30 — Testing: What Ping Misses (22:29 → 23:27) *(core — do not cut)*

**On slide:** Three cards: same key on every boot? (SPRESENSE, 3 resets, 3 keys) / keys left after down? (sim, all zero) / a leak after hours? (sim, 151 rekeys, 100 down/up, nothing lost).

**Say:**
- This slide is about what a working tunnel cannot tell you: three problems that ping would never notice.
- First, keys. NuttX can seed its random device from build-time settings. Then a board makes the same private key every time it starts, and everything still works. So I reset a SPRESENSE three times and got three different keys. That is a quick check, not a proof of good randomness.
- Second, I read the device's memory in the simulator. After down, the session keys were all zero. The static key stays on purpose, so that up works again.
- Third, a long test, also in the simulator: a hundred and fifty-one forced rekeys and a hundred down-and-up cycles. No buffer was lost, and memory went back to exactly the start-up number. I am not saying it ran for a week, or that the simulator acts like the board.

## 31 — A Design Choice: The Timestamp Problem Has No Easy Answer (23:27 → 24:50) *(core — do not cut)*

**On slide:** The rule (a newer timestamp, even after a reboot), Chosen (real-time clock + the highest value this boot, plus a warning) / Not chosen (save every time, reserve a range in flash, wait), and the measured pair: clock unset → no handshake in 75 s, clock set → 4.1 s.

**Say:**
- This is the one place where I had to decide, not test. And then I measured my decision.
- WireGuard's replay protection has a rule: every handshake needs a newer timestamp than the peer has seen, even after a reboot. The device is usually the side that starts the handshake, and it is also the side least likely to have a clock with a battery.
- Saving every timestamp wears out the flash. Reserving a range in flash is the right long-term answer, but it needs a write guarantee I could not verify on these file systems. And just waiting means a device that ran for a month cannot reconnect for a month. Here, the easy choice and the right choice were not the same.
- So I chose the real-time clock plus the highest value used in this boot, exactly what Linux and wireguard-go do. And the driver warns once if the clock was never set.
- Then I measured it on the board. I sent the board nothing at all, because a ping from the peer would start the handshake for it. With the clock as it boots: no handshake in a seventy-five-second watch. With the clock set: four point one seconds. That is why the driver prints a warning.
