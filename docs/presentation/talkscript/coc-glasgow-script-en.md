## 7 — Background: What Is NuttX (3:53 → 4:41)

**On slide:** Software stack (applications / POSIX, ANSI, BSD socket API / networking, VFS, file systems, device drivers, NSH / NuttX kernel / MCU, MPU) and tags: RTOS, POSIX-oriented, BSD sockets, VFS, NSH, native networking, device drivers, ASF top-level project.

**Say:**
- First, what is NuttX?
- NuttX is a real-time operating system that puts standards first. It follows the POSIX and ANSI APIs, it uses BSD sockets for networking, and it has a real file system, a shell called NSH, built-in networking and device drivers. All of this is made small enough to run on microcontrollers, from 8-bit to 64-bit. It is also a top-level project of the Apache Software Foundation, and its community develops it in the open.
- The one point I want you to remember: NuttX is a small RTOS, but you program it like Unix. That is rare. And that is why almost everything later in this talk — sockets, network devices, a POSIX-style port — is possible at all.

## 12 — Problem: Reaching a Device From Far Away (7:56 → 8:48)

**On slide:** Engineer → Internet → router → Wi-Fi → NuttX device, showing that WPA2/WPA3 covers only the Wi-Fi hop; cards: open it to the Internet / make your own protocol / use a vendor's cloud.

**Say:**
- Now, the problem itself.
- Wi-Fi security is real, but it protects only one part of the path: the radio link between the device and the access point. Everything before that — the engineer, the Internet, the router — is outside what WPA2 or WPA3 can protect. What I needed was a secure path for the whole way, from the engineer to the device, not just the last few meters.
- Without that, every choice has a problem. You can give the device a public IP and hope. You can make your own secure protocol and keep it working forever. Or you can hand the connection to a vendor's cloud. The same problem appears in edge AI, industrial IoT, and remote systems in general. It is not limited to this project.

## 13 — Options: Other Ways to Reach a Device (8:48 → 10:05)

**On slide:** A table of seven ways (open a port / HTTPS to a cloud API / MQTT broker / reverse tunnel or relay / VPN on the router / carrier closed network / VPN on the device) against: who connects, any service or not, server in the middle, where security ends, what NuttX already has.

**Say:**
- Before I chose WireGuard, I compared the usual ways to reach a device.
- Opening a port is easy, but then the whole Internet can reach the device. HTTPS and MQTT are what most IoT products use. The device connects out to a server, so NAT is not a problem, and NuttX already has clients for both. But you only get the messages you designed — you cannot log in or open a web page on the device. And the security ends at the broker or the cloud.
- A reverse tunnel gives you one port through a relay server. A VPN on the router is great when the router is yours — but the last part of the path, on the LAN, is not protected, and at a customer's site the router is usually not yours. A carrier closed network works only over cellular, and you need a contract.
- A VPN on the device is the only row that has all three: any IP service, no server in the middle, and security all the way to the device. MQTT and HTTPS are still the right tools for data. This is for maintenance access.

**If asked about Tailscale or ZeroTier:** they are also a VPN on the device, but they usually need a bigger OS than a microcontroller has today (footnote on the slide).

## 14 — Solution: Why WireGuard (10:05 → 10:58)

**On slide:** Engineer / Linux / Windows ⟷ WireGuard tunnel ⟷ NuttX device; modern IP-layer VPN / UDP transport, public-key peers / already everywhere.

**Say:**
- So, why WireGuard?
- WireGuard is a modern VPN that works at the IP layer. It is small and simple by design, with much less code than IPsec or OpenVPN, and that matters a lot on a microcontroller. It runs over plain UDP, and each peer is known by its public key, not by certificates or a long setup. If a packet does not carry the right key, WireGuard does not answer at all — to everyone else, the device is just a brick wall. And most importantly, it is a standard. It has been in the Linux kernel for years, there is an official Windows client, and the other end can be any WireGuard peer.
- So I chose a standard protocol, instead of making my own or depending on a vendor's cloud.

## 15 — Architecture: WireGuard on the NuttX Network Stack (10:58 → 11:46)

**On slide:** Application → TCP/UDP/IP → wg0 (NET_LL_TUN netdev) → WireGuard encrypt/decrypt → UDP socket → wlan0 / usrsock → network, with TX and RX arrows.

**Say:**
- This is one step more technical than the overview. This is where the implementation starts.
- Going out, a packet comes down from the application through TCP or UDP and IP, and reaches wg0 like any other network device. WireGuard encrypts it, and it leaves as a UDP packet — through wlan0 on a board, or through usrsock when the Wi-Fi chip itself works through sockets. Coming in is the same path the other way: a UDP packet arrives, WireGuard decrypts it, and it is passed up to wg0 as if it came in on a normal interface.
- From here on, the work is building this middle part — wg0 and the encryption — without changing the layers above or below it.

## 17 — Porting Strategy: Reusing wireguard-lwip Without lwIP (11:56 → 12:57)

**On slide:** Three cards: protocol & crypto (KEEP) / platform hooks (ADAPT, the four functions in wireguard-platform.h) / lwIP network glue (REPLACE).

**Say:**
- Why I started from smartalock/wireguard-lwip, and did not write the crypto myself.
- wireguard-lwip is cleanly split into three layers. The protocol and crypto — the handshake, the data transport, BLAKE2s, ChaCha20-Poly1305 and Curve25519 — are portable C that does not depend on any OS. I used the crypto without changes. The protocol core needed two small fixes later, after a review, and they are written down in PATCHES.md. Everything that depends on the OS was already kept behind one header, wireguard-platform.h, as four functions. I only had to replace the lwIP network glue — the part that registers an lwIP netif and handles lwIP buffers — because NuttX does not have lwIP at all.
- I did not have to rewrite the protocol or the crypto, and that was not luck. That is what a clean line between the protocol and the OS gives you. Because of it, this port took weeks, not months.

## 18 — Design: Mapping lwIP onto NuttX netdev (12:57 → 13:19)

**On slide:** netif → net_driver_s, pbuf → iob, netif_add() → netdev_register(), callbacks → devif_poll().

**Say:**
- This was the most important porting decision.
- Instead of bringing lwIP into NuttX, I matched each lwIP idea to NuttX's own. netif becomes net_driver_s, pbuf becomes iob, netif_add becomes netdev_register, and the send callback becomes NuttX's devif_poll. wg0 is registered as a TUN-type network device, and the “wire” under it is a UDP socket.

## 22 — Bug 1/6: The Detached pthread (First Symptom: recvfrom Never Returned) (14:42 → 15:48)

**Say:**
- The first one: something I believed about a thread's life that was not true.
- The first symptom was simple: recvfrom never returned, the timer never ran, and no handshake was sent. I blamed the receive timeout option and switched to poll, but still nothing was sent. The real cause was here. The receive thread was created as detached. When the command that started it finished, the thread stopped too — it did not even appear in ps. When I added a short sleep after creating it, its printf ran, so it really was created. My mistake was thinking that “detached” means “it lives longer than the command.” Detach only decides when the thread's memory is freed, not whether it keeps running after the command exits. So when the command ended, the thread ended with it. That is why, in the kernel version, the driver itself owns the thread. And NuttX's UDP code does use that timeout option; I simply never tested the old path again.

## 23 — Bug 2/6: ping Works, TCP Dies (15:48 → 16:40) *(my favorite)*

**Say:**
- This is my favorite bug in the project.
- On the same tunnel, ping was perfect, and even a TCP handshake finished — and then the connection died. When I added logging to the send path, it showed EBADF: bad file descriptor. All the sends that worked happened inside the receive task itself — handshake replies, keepalives, ping replies, the SYN-ACK. Sends from any other task failed.
- The reason: in NuttX, a file descriptor belongs to one task group. It is not shared by the whole system. The fix was to stop using file descriptors and use NuttX's internal socket API. It works on a struct socket, which is just memory, so any task can use it. That is exactly why the kernel version keeps the socket as a struct socket.

## 24 — Bug 3/6: "No Real Impact" Was 10× (16:40 → 17:20)

**Say:**
- The third: something I never measured.
- The fix without file descriptors also broke poll, because poll works with file descriptors. So, as a quick fix, I checked the socket every fifty milliseconds. I thought the only cost was waking up the CPU when it was idle. I was wrong. Every packet that arrived waited up to fifty milliseconds, and that alone limited the speed — about ten times slower than it should have been. I thought it had no real cost, and it cost ten times. The real fix was a proper wait: a callback on psock_poll and a semaphore.

## 25 — Bug 4/6: sim Passes, Real Hardware Is Different (17:20 → 18:14)

**Say:**
- The fourth, and it will come back later: stack sizes nobody had measured.
- Two things only real hardware showed me. First, saving the config into a file through the shell froze the board — but only on the flash file system of real hardware, never in sim. I fixed it with a wg saveconf command that writes the file itself.
- Second, the receive task's stack. That task calls into the IP stack on its own stack, so the whole TCP call chain sits on it, and for packets it answers right away, so does encrypting the reply. The default size, 3072 bytes, was a number nobody had measured. When I measured it on the board with stack coloration and ps, it was ninety-four percent full — only 176 bytes left. Please remember this one.

## 28 — Part 5: Into the Kernel (18:50 → 19:26)

**Say:**
- This is the work I did after the first version, and it is the part that NuttX needs before this can go upstream.
- Version one lives in apps and uses socket internals. That is fine for a FLAT build. But it can never be a proper in-tree driver, and it does not work in PROTECTED and KERNEL builds, where user space and the kernel are kept apart. So I moved the device into the kernel, under drivers/net/wireguard, and I control it from a small user-space wg command through ioctl.

## 29 — The Kernel Design (19:26 → 20:23)

**Say:**
- This is the shape of the real driver.
- wg0 is now a lower-half network device in the kernel. It owns its UDP socket and its receive thread, so the socket and thread problems from version one cannot happen, by design. The settings go through a simple ioctl ABI with no pointers. No pointers: the kernel reads the one struct the caller passed, during the call, and never has to follow a pointer into user memory. The private key is write-only: no ioctl ever gives it back — but it is still in the config file on the user side. The crypto in the kernel is NuttX's own. The protocol core is still derived from wireguard-lwip, under BSD-3-Clause, so the driver needs ALLOW_BSD_COMPONENTS, and I say so in the LICENSE file. The user command also has a small MIT-licensed X25519, for making keys offline.

## 30 — Bugs 5 & 6/6: Same Shape, One Level Deeper (20:23 → 21:28) *(locked with the kernel design)*

**Say:**
- And the same pattern came back in the kernel — twice.
- First, a bug in NuttX's own ChaCha20-Poly1305: the counter was written into the wrong bytes of the nonce. When the counter is zero, both layouts are the same, so the handshake works, and then every data packet after the first one fails to decrypt. Simple test passes, deep test fails. Nothing in NuttX had called this code before, so nobody had hit it. It is a two-line fix, and it goes upstream as its own crypto PR. So porting to NuttX found a hidden bug in NuttX itself.
- Second, a crash that happened only in a kernel build. Setting the key copied the peers into a six-kilobyte array on the stack, but the kernel stack is only three kilobytes. Overflow, a broken heap, panic. In sim, with big task stacks, it never showed up. It was the same stack lesson as before, one level deeper. I moved the array to the heap.

## 31 — Testing: Seven Places It Must Work (21:28 → 23:35) *(core — do not cut)*

**On slide:** Table (where / version / what I checked): sim / rv-virt knetnsh64 (BUILD_KERNEL, QEMU) / rv-virt pnsh64 (BUILD_PROTECTED, QEMU) / rv-virt knetnsh64_smp (4 CPUs, QEMU) / SPRESENSE measured (FLAT) / ESP32-S3 + SPRESENSE over real Wi-Fi (FLAT; both board rows before the final rebase) / Version 1 (app), v0.1.1 on both boards.

**Say:**
- Let me be exact about which version was checked where.
- The kernel driver builds with no errors in the sim config — the driver series adds that config. It also runs a full tunnel in a kernel build in QEMU, rv-virt knetnsh64, to WireGuard in the Linux kernel. The wg command is a separate program, and it reaches the driver through system calls.
- Next, PROTECTED, also in QEMU. The ioctl ABI has no pointers inside, so the kernel only touches the one struct the caller passed. With the memory split on, every ioctl crosses the boundary, and the tunnel reaches Linux. But in repeated runs, two out of eight hit a fault in user space. I have not found the cause yet, so it is an open problem, not a pass.
- Then, locking: four CPUs in QEMU, a flood of packets, while another CPU changes the settings and does down and up. No fault, and the tunnel came back. But this is one scripted run, not a full search for race conditions.
- The SPRESENSE row is the one I would show a reviewer first. The simulator's memory numbers do not apply to a board, so I measured the board itself: two minutes of traffic, then forty down-and-up cycles over real Wi-Fi. Heap, buffers and every stack: exactly the same before and after. The receive thread used one thousand four hundred and seventy-two bytes, out of a six-kilobyte default. That default used to be a guess. Now it is a measurement.
- The kernel driver also runs on both boards over real Wi-Fi, with the official Windows client: native Wi-Fi on the ESP32-S3, and usrsock on SPRESENSE. These are normal FLAT builds, from the version before the final rebase. KERNEL and PROTECTED ran only in QEMU, and the KERNEL and SMP tunnels were run again after the rebase. ## 32 — Testing: A Working Tunnel Does Not Prove Enough (23:35 → 25:07) *(core — do not cut)*

**On slide:** Three rows (same private key every boot / session keys that outlive the tunnel / a leak that shows after hours), each with "would ping notice?" → no, and where it was measured (SPRESENSE / sim / sim).

**Say:**
- The last slide was about where it runs. This one is about what a working tunnel cannot tell you.
- First, keys. NuttX can give /dev/urandom an xorshift128 backend, with a seed from build-time settings. Then a board gives out the same private key every time it starts, and the handshake, the ping and the demo all still work. So I reset a SPRESENSE three times — resets, not power cycles — and got three different keys. That is a quick check, not a proof of good randomness.
- Second, in the simulator: I read the device's memory while the tunnel was up, and again after down. The session keys were all zero after down. The static key stays, on purpose, so that up works again. There is exactly one copy of it, and that is written in the driver's documentation.
- Third, the long test, also in the simulator: a hundred and fifty-one forced rekeys past the key lifetime, ten endpoint changes, and a hundred down-and-up cycles. The buffers all came back, and the live allocations went back to exactly the start-up number. The receive thread's stack peak was two and a half kilobytes in the simulator — one and a half on the board — against a six-kilobyte default. What I am not saying is that it ran for a week, or that the simulator's memory acts like the board.

## 33 — A Design Choice: The Timestamp Problem Has No Easy Answer (25:07 → 27:03) *(core — do not cut)*

**On slide:** What replay protection obliges, the four options (real-time clock + in-boot high-water mark / persist every time / durable range reservation / wait to catch up), and the measured pair: clock unset → no handshake in a 75 s watch, clock set → 4.1 s.

**Say:**
- This is the one place where I had to decide, not test. And then I measured my decision.
- WireGuard's replay protection gives the side that starts the handshake a rule: every handshake needs a newer timestamp than the peer has seen — even after a reboot. The device is usually the side that starts, and it is also the side least likely to have a clock with a battery.
- Doing nothing does not work. With an uptime-based timestamp, a device is cut off for as long as it ran last time: a device that ran for a month cannot reconnect for a month. Saving every timestamp wears out the flash. Reserving a range in flash is the right long-term answer, but it needs a write guarantee I could not verify on these file systems. Shipping that would look solved without being solved. Here, the easy choice and the right choice were not the same.
- So I chose the real-time clock plus the highest value used in this boot — exactly what Linux and wireguard-go do. What I added: if the clock was never set, the driver prints a warning once, and says what will happen.
- And I measured it on the board. The obvious test passes: reset the board, ping it, and the tunnel is back — because your ping made the peer start the handshake. So I sent the board nothing at all. Same board, one change. With the clock as it boots: a warning, and no handshake in a seventy-five-second watch. With the clock set: a handshake in four point one seconds. Without a clock, the device may not reconnect by itself, and a ping test will not show it. That is why the driver prints a warning.
