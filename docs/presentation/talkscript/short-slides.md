## 02 SUMMARY 〔80 秒〕

**[スライド]** 上に NuttX 上の構成図(`wg0` → UDP 51820 → 既存の WireGuard ピア)、下に "What is WireGuard?" の見出し + 説明カード 4 枚

**[話す]**
まず、このリポジトリに何が入っているか。

Apache NuttX は POSIX 準拠の RTOS で、独自の TCP/IP スタックと BSD ソケット API を持っていますが、VPN 機能がありません。そこで WireGuard を NuttX のネットワークデバイス `wg0` として実装しました。アプリから見れば普通のネットワークインターフェースです。暗号化された中身を運んでいるのは UDP ポート 51820 のソケットで、相手は既存の WireGuard エンドポイントで構いません。

**[間]** ——下のカードへ。

では、その WireGuard とは何か。Linux 向けに開発された軽量な VPN プロトコルで、組み込みや IoT でも採用が広がっています。UDP の上で暗号化トンネルを張り、暗号は Curve25519、ChaCha20-Poly1305、BLAKE2s。実装が約 4,000 行とコンパクトなので、マイコンにも載ります。

意外と新しくて、大企業のプロダクトでもありません。作者は Jason Donenfeld という独立したセキュリティ研究者で、2015 年に作り始めて 2016 年に公開。4 年間 out-of-tree のモジュールとして使われて、Linux カーネルに入ったのは 2020 年 3 月の 5.6 です。Tailscale を使っている人は、すでに WireGuard を使っています。Tailscale はこのプロトコルの上に作られているので。

## 04 WHY THIS TOPIC 〔85 秒〕

**[スライド]** 2 つの現場(AITRIOS の AI カメラ = ESP32 + NuttX / SPRESENSE の衛星プロジェクト)/ VPN が無いときの 3 つの選択肢 / 下段に小さく GSoC の注記

**[話す]**
なぜこのテーマなのか。理由は一覧から選んだのではなく、自分の仕事の側にありました。

ソニーセミコンダクタソリューションズでエッジ AI エンジニアをしていて、NuttX はアプリケーション側から使う立場です。1 つは AITRIOS というエッジ AI プラットフォーム。そこで使っている AI カメラが ESP32 で、その OS が NuttX です。もう 1 つはボトムアップの活動で、SPRESENSE を使った人工衛星のプロジェクト。SPRESENSE はソニーの小型・低消費電力ボードで、衛星や海洋モニタリングでの採用実績があります。

**[間]** ——一拍。

どちらも、リモートから安全に触りたいのに触れない NuttX 機器でした。VPN が無いときの選択肢は、グローバル IP を晒すか、独自プロトコルを作り込むか、ベンダーのクラウドに乗るか。どれも嬉しくありません。

WireGuard は Tailscale が使っているプロトコルで、自分は Tailscale のヘビーユーザーでもあります。コンパクトな実装とシンプルな鍵モデルなので、こういう制約のある環境に向いています。

おまけとして小さく。テーマ自体は Google Summer of Code のテーマ一覧で見つけたもので、そのプロポーザルは不採択でした。それでも作業は続けました。

## 05 THE PLAN 〔70 秒〕

**[スライド]** smartalock/wireguard-lwip の 3 層(プロトコル + 暗号 / 4 関数のプラットフォーム層 / lwIP netif グルー)/ 置き換え表(`struct netif` → `struct net_driver_s`、`pbuf_alloc()` → `iob_alloc()`、lwIP UDP → BSD ソケット)

**[話す]**
ここから技術の話です。まず計画から。ゼロから WireGuard を書いたわけではありません。参考実装があります。

`smartalock/wireguard-lwip` は WireGuard を lwIP の `netif`、つまり仮想 NIC として実装したものです。`eth0` や `wlan0` と対等に扱われるので、上位のスタックからは普通のインターフェースに見えて、ルーティングもそのまま働きます。この実装の良いところは、OS 依存の処理が 4 つの関数に隔離されていること。プロトコルのコアと暗号は OS 非依存のポータブル C です。

問題は、NuttX が lwIP を使わないこと。NuttX は独自の TCP/IP スタックを持っていて、lwIP のヘッダは include パスにすら無い。だから netif のグルーはそのままではコンパイルできません。

そこで計画はこうなりました。プラットフォーム層の 4 関数を NuttX 向けに実装し、lwIP の API 呼び出しを 1 つずつ NuttX の等価物に置き換える。これがプロポーザルに書いた計画で、実際の作業もその通りになりました。

## 06 HOW IT WAS BUILT 〔55 秒〕

**[スライド]** 3 層と行数(3,079 行 byte-identical / 186 行 / 2,157 行)/ 4 アーキテクチャ(x86_64、Cortex-A7、Xtensa LX7、Cortex-M4F)

**[話す]**
では実際どうだったか。移植元を 3 層に分けると、層ごとの移植コストがまったく違います。

プロトコルと暗号は移植コストゼロ。ポータブル C なのでそのまま持ってきました。3,079 行、upstream とバイト単位で一致しています。OS 依存の 4 関数は低コスト。NuttX の POSIX API で書いて 186 行。lwIP の netif グルーは全損。流用が一切できず、ここは書き直しです。それが NuttX 向けに書いた 2,157 行。

**[間]** ——右下の 4 アーキテクチャを指す。

そして、OS 依存をこの小さい 1 ファイルに隔離したことが効きました。結果として 4 つのアーキテクチャ、x86_64、ARM Cortex-A7、Xtensa LX7、ARM Cortex-M4F で、コードを 1 行も変えずに動いています。

## 07 THE DETAILS 〔80 秒〕

**[スライド]** `wg0` = `netdev_register()` で登録した netdev、配線は UDP ソケット / 送信・受信のデータパス / OS フック 4 関数 / 「計画が生き残らなかった 1 点」= `psock_*()` と FLAT ビルド

**[話す]**
もう一段細かい話です。

NuttX は独自の TCP/IP スタックを持つので、`wg0` は `netdev_register()` で登録します。手本にしたのは NuttX の TUN ドライバです。下で「配線」の役をしているのは UDP ソケット。送信は `devif_poll` から暗号化して `psock_sendto`。受信はバックグラウンドタスクが `psock_poll` でブロックして待ち、復号して `ipv4_input` でスタックに注入します。

OS フックの 4 関数はこれだけです。単調増加時刻、暗号乱数、TAI64N タイムスタンプ、負荷判定。負荷判定は単に false を返します。

**[間]** ——一拍。ここが本題。

最後に、計画が生き残らなかった 1 点。プロポーザルには「BSD の `socket()` と `bind()`」と書いていましたが、実際にはソケットを fd ではなく `struct socket` として保持して、内部 API の `psock` 系を使うことになりました。NuttX が fd をタスクグループ単位でスコープする一方、送信経路が無関係なワーカースレッドの上で走るからです。この都合で現状の実装は FLAT ビルド前提になっていて、upstream に出す前の未解決の論点の 1 つです。

## 08 VERIFIED ON 〔85 秒〕

**[スライド]** 右上に 2 枚の実機の写真 / 3 行のテーブル(sim / QEMU、ESP32-S3、SPRESENSE — アーキ・Wi-Fi 方式・ピア・確認内容)/ claim: 13.0.1・master・12.7.0 で同一ソース、両ボードで検証 / 「3 つの本物のバグ」

**[話す]**
どこで本当に動いているか。

シミュレータと QEMU は Linux カーネルの WireGuard が相手です。実機 2 枚は、家庭用のアクセスポイント越しに Windows の公式クライアントと通信しています。

**[間]** ——SPRESENSE の行を指す。

SPRESENSE の結果は新しい方です。Wi-Fi アドオンの GS2200M というモジュールは、TCP/IP スタックがモジュールの中にあって、カーネルからはソケットの代理、usrsock として見えます。ESP32-S3 のカーネル内 netdev とはまったく違う裏側で、同じ `wg0` のコードがどちらでも動いています。ここに至るまでに本物のバグを 3 つ踏んで、全部直しました。

**[間]** ——下の claim へ。

そして同じソースが、NuttX の最新リリース 13.0.1、upstream への提出で基準になる master、以前の 12.7.0 の 3 つでビルドできて、両方のボードを 3 つ全部で確認し直しています。13.0.1 と master では、SPRESENSE で見つけたスケジューラの起動不良を 1 箇所直す必要があって、これは upstream に報告する形でまとめてあります。ESP32-S3 側は defconfig の変化、init システムの入れ替えとデフォルトのスタック縮小への追従だけでした。

最後に、実際どう見えるかを。

左が Windows の公式 WireGuard クライアントで、ハンドシェイクと転送量が出ています。右が ESP32-S3 へトンネル越しに入った telnet セッション。`ifconfig` で `wlan0` と `wg0` が並んでいて、`wg show` でハンドシェイクが見えて、`ps` でタスクも見えます。
