## 1 — タイトル (0:00 → 0:47)

**画面:** "WireGuard for Apache NuttX"。ESP32-S3 と SPRESENSE が実 Wi-Fi でトンネル /
実際の WireGuard ピア(Linux kernel, Windows クライアント) / 実カーネルビルドで動作
(BUILD_KERNEL) / NuttX 13.0.1・master・12.7.0 が同一ソース。

**話す:**
- 今日は WireGuard を Apache NuttX に持ち込む話をします。
- これは `wg0` というネットワークデバイスとして実装した WireGuard VPN です。
  ESP32-S3 と SPRESENSE、両方とも実 Wi-Fi 経由でトンネルが立っています。ピアは
  常に本物の WireGuard 実装 — Linux カーネルモジュールと公式 Windows クライアント
  — で、同じソースが NuttX の3バージョンでビルドできます。話の後半では、これが
  実際のカーネルビルドの中でも動きます。ここが今日の話の、より難しく、より
  面白い半分です。
- ただ、この話の主眼は「動いた」ことではありません。「動く」が何を隠していたか、
  そしてカーネルに押し込んだことで何が表に出たか、という話です。

## 2 — 概要 (0:47 → 1:14)

**画面:** `wg0` netdev の図 — アプリケーション/NSH、NuttX ネットワークスタック、
`eth0`/`wlan0` の隣に `wg0`、その下に UDP ソケット、インターネット、ピア。

**話す:**
- 全体像を1枚の絵にするとこうなります。
- Apache NuttX は独自の TCP/IP スタックを持つ POSIX 準拠の RTOS です。VPN は
  ありませんでした。このプロジェクトは `wg0` を仮想ネットワークインターフェース
  として追加します — アプリケーションからは普通のインターフェースに見え、
  その下では暗号化された伝送路が UDP ソケットです。反対側のピアは本物の
  WireGuard エンドポイント — Linux、Windows、あるいは別のゲートウェイです。

## 3 — ASF と Community Over Code (1:14 → 1:47) *(削る候補)*

**話す:**
- この話の行き先について一言。
- ASF は「公共の利益のためにソフトウェアを提供する」ために存在する非営利団体で、
  何百ものプロジェクトをボランティアが運営しています。NuttX もその一つです。
  Community Over Code は ASF の公式カンファレンスで、Glasgow では NuttX
  International Workshop が併催されます。
- これを話すのは、「完成」の意味が変わるからです。目標は自分のデスクで動く
  デモではありません。このコミュニティがマージし、保守できるコードです —
  community over code。

## 4 — なぜこのテーマか (1:47 → 2:26)

**話す:**
- そもそもなぜこれに取り組んだか。
- 私は、設置済みの NuttX デバイスに安全にアクセスしたいと思っていました。
  今の選択肢は、グローバル IP を晒してスキャンされるか、独自プロトコルを
  作ってそのバグを一生抱えるか、ベンダーのクラウドを受け入れるかです。
  どれも良くありません。そしてこれはニッチな問題ではなく、エッジ AI カメラ、
  産業用 IoT、遠隔地や衛星回線の設備に共通する問題です。

## 5 — なぜ重要か (2:26 → 2:57)

**話す:**
- 新しいことができるようになる、という話ではありません。すでにやりたかった
  ことが、当たり前にできるようになる、という話です。
- いつものツールでの保守。クラウドをデバイス側のネットワークに引き込む、
  その逆ではなく。ゲートウェイで止まらず MCU まで届くゼロトラスト。そして
  標準の WireGuard である以上、相手側は何でもよい — その相互運用性自体に
  価値があります。

## 6 — 方針 (2:57 → 3:28)

**話す:**
- 暗号スタックをゼロから書くのは間違いです。なので既存実装から始めました。
- `wireguard-lwip` は WireGuard を lwIP の netif として実装していて、重要なのは
  OS 依存な部分を1つのヘッダー、4つの関数の裏に隔離している点です。プロトコルと
  暗号処理は移植可能な C です。ただし NuttX は lwIP を使っていません — 独自の
  スタックを持っています。だからやるべきことは単純です: プロトコルの核心は
  そのまま残し、ネットワークのつなぎ込みだけを差し替える。

## 7 — 設計判断 (3:28 → 3:49)

**画面:** lwIP → NuttX の対応表(`netif`→`net_driver_s`、`pbuf`→`iob`、
`netif_add()`→`netdev_register()`、コールバック→`devif_poll()`)。

**話す:**
- 移植の中で最も重要な判断です。
- lwIP を NuttX に引きずり込むのではなく、抽象化を NuttX 自身のものに写像
  しました。`netif` は `net_driver_s` に、`pbuf` は `iob` に、`netif_add` は
  `netdev_register` に、送信コールバックは NuttX の `devif_poll` になります。
  `wg0` は TUN 型の netdev として登録され、その下の「配線」は UDP ソケットです。

## 8 — どう作ったか (3:49 → 4:19)

**話す:**
- 最初のバージョンの結果です。
- プロトコルと暗号処理はバイト単位で同一のまま移りました — 3000行以上、
  無変更です。4つの OS フックは小さなものです。本当の作業はネットワークの
  つなぎ込みでした。そして動きました: 鍵の生成、ピアの設定、設定ファイルの
  読み込み、すべて実行時に、再ビルドなしで。ここまでは成功譚です。この後の
  話は、その成功が何を隠していたか、です。

## 9 — 第2部: パターン (4:19 → 4:41)

**話す:**
- ここがこの話の核心です。
- このプロジェクトの難しいバグは、すべて同じ形をしていました。浅い試験は通る。
  深い試験は落ちる。さらに悪いことに、浅い試験が通ったことでその領域は
  大丈夫だと信じ込み、何時間も他の場所を探し回ることになります。次のスライド
  はそのパターンの実例です — apps版で5つ、そしてカーネルに押し込んでからさらに
  2つ。

## 10 — 落とし穴 1/7: `SO_RCVTIMEO` (4:41 → 5:07)

**話す:**
- 最初の一撃: 成功を返すのに何も効かない。
- 受信タイムアウトの設定は 0、成功を返しました。しかし `recvfrom` は
  それでも永遠にブロックしました — オプションは受理されて、黙って無視
  されていたのです。これが完璧なデッドロックを生みました: タイマーが
  発火しない → 開始要求が送られない → ピアが応答しない → `recvfrom` が
  戻らずタイマーを発火させられない。

## 11 — 落とし穴 2/7: detach された pthread (5:07 → 5:47)

**話す:**
- 2つ目: 成り立たなかったライフサイクルの前提。
- 受信スレッドは detach 付きで作られていました。起動したコマンドが終了すると、
  スレッドも止まりました — `ps` にすら出てきません。作成直後に短い sleep を
  挟むと `printf` が実行されたので、作成自体はされていました。私の勘違いは
  detach を「コマンドより長生きする」と読んだことです — detach が制御するのは
  スレッドのリソースがいつ回収されるかだけで、起動元が終了しても生き残るか
  どうかではありません。だからコマンドが終了すると、スレッドも道連れに
  なりました。カーネル版でスレッドをドライバ側が所有しているのは、まさに
  これが理由です。

## 12 — 落とし穴 3/7: ping は通るのに TCP が死ぬ (5:47 → 6:47) *(お気に入り)*

**話す:**
- このプロジェクトで一番好きなバグです。
- 同じトンネルの上で、ping は完璧に通り、TCP の 3-way ハンドシェイクすら
  完了する — それなのに接続は死にました。送信経路を計装すると `EBADF`、
  不正なファイルディスクリプタが出ていました。成功していた送信はすべて
  受信タスク自身のコンテキストで行われたものでした — ハンドシェイクの
  応答、キープアライブ、ping の応答、SYN-ACK。他のタスクからの送信はすべて
  失敗していました。
- 原因: NuttX ではファイルディスクリプタはタスクグループ単位にスコープされ
  ていて、システム全体でもグローバルでもありません。修正は fd を経由する
  こと自体をやめ、NuttX の内部ソケット API を使うことでした — これは
  `struct socket` に対して動作する、ただのメモリなので、どのタスクからでも
  使えます。カーネル版がソケットを `struct socket` として保持しているのは、
  まさにこの理由です。

## 13 — 落とし穴 4/7: 「実害なし」が実は10倍 (6:47 → 7:37)

**話す:**
- 4つ目: 測定しなかった前提。
- fd を使わない修正は `poll` も壊しました。`poll` は fd ベースだからです。
  応急処置として 50ミリ秒ごとにソケットをポーリングしました。コストは
  アイドル時に CPU を起こすことだけだと思っていました。間違いでした。
  届いたパケットはすべて最大 50ミリ秒待たされ、それだけでスループットの
  上限になっていました — 本来より約10倍遅い。「実害なし」と測ったものが
  実は10倍でした。本当の修正は正しいブロッキング待ち — `psock_poll` への
  コールバックとセマフォです。

## 14 — 落とし穴 5/7: sim は通るのに実機が固まる (7:37 → 8:23)

**話す:**
- 5つ目、そして後で戻ってきます: 誰も測っていなかったスタック。
- 設定をファイルにリダイレクトして永続化すると、実機の flash ファイル
  システムでのみボードが固まりました — sim では一度も再現しません。
  原因は受信タスクのスタックでした。IP スタックへの呼び出しは自分自身の
  スタックの上で行われるので、TCP の呼び出し深さ全体がそこに乗り、
  即座に応答するパケットについては返信の暗号化もそこに乗ります。既定値の
  3072バイトは、誰も測ったことのない数字でした。スタックカラーレーション
  と `ps` でこれを見つけました。この話は後で戻ってきます。

## 15 — 第3部: カーネルへ (8:23 → 8:58)

**話す:**
- ここからが最初のバージョン以降の追加作業で、マージ可能にする部分です。
- バージョン1は `apps` に住み、ソケットの内部実装に踏み込んでいます。
  FLAT ビルドなら問題ありませんが、正式な in-tree ドライバには決してなれず、
  ユーザー空間とカーネルが分離される PROTECTED / KERNEL ビルドにも合いません。
  そこでデバイスを `drivers/net/wireguard` としてカーネルに移し、小さな
  ユーザー空間の `wg` コマンドから ioctl 経由で操作する形にしました。

## 16 — カーネル側の設計 (8:58 → 9:30)

**話す:**
- 実際のドライバの形です。
- `wg0` は今やカーネル内の lower-half netdev で、UDP ソケットと受信カーネル
  スレッドを自分で所有します — なので第2部の「ソケットの所有権」と「起動元の
  寿命」の問題は設計上そもそも起きません。設定は平坦でポインタを含まない
  ioctl ABI です。ポインタを含まないのは、カーネルが呼び出し元の構造体を
  そのままコピーするからです。秘密鍵は write-only — get の ioctl は決して
  それを返しません。ただしユーザー側の設定ファイルには残っています。
  カーネル側の暗号処理は NuttX 自身のもので、vendor しているコードは
  ユーザー空間コマンド内のオフライン鍵生成用の小さな MIT ライセンスの
  X25519 だけです。

## 17 — もう2つのバグ・同じ形 (9:30 → 10:37) *(16と一体)*

**話す:**
- そしてカーネルの深さでも同じパターンが2回起きました。
- 1つ目は NuttX 自身の ChaCha20-Poly1305 のバグです: カウンタがナンスの
  誤ったバイト位置に入っていました。カウンタ0の場合は両方のレイアウトが
  一致するので、ハンドシェイクは成功し、その後の最初のデータパケット以降
  すべてが復号に失敗します。浅い試験は通り、深い試験は落ちる。in-tree の
  呼び出し元が一度もなかったので、これまで一度も踏まれていませんでした。
  修正は2行で、独立した `crypto:` PR として upstream に出します — この
  プロジェクトへの移植作業が、このプロジェクト自身の潜在バグを見つけました。
- 2つ目は、カーネルビルドでしか起きないクラッシュです。鍵の設定がピアを
  6キロバイトの配列としてスタック上にスナップショットしていて、カーネルの
  スタックは3キロバイトしかありません — オーバーフロー、ヒープ破壊、
  パニック。タスクスタックが大きい sim では一度も現れませんでした。
  まさに第2部のスタックの教訓が、もう一段深いところで再現したものです。
  ヒープに移しました。

## 18 — 検証: 成り立つべき7つの場所 (10:37 → 14:48) *(核心・削らない)*

**画面:** sim / rv-virt knetnsh64 (BUILD_KERNEL) / rv-virt pnsh64
(BUILD_PROTECTED) / rv-virt knetnsh64_smp (4 CPU) / SPRESENSE 実測 /
ESP32-S3 + SPRESENSE 実 Wi-Fi / 両ボードでの apps v0.1.1、の表。

**話す:**
- どの実装がどこで検証されたか、正確に話します。
- カーネルドライバは sim 構成でクリーンにビルドでき — この構成の CI が
  コンパイルを通し — 実カーネルビルドの中で完全なトンネルとして動きます:
  QEMU 上の rv-virt の `knetnsh64`、virtio-net 経由で Linux カーネルの
  WireGuard と接続し、`wg` コマンドは別 ELF としてロードされ、ドライバへは
  システムコール境界を越えて到達します。
- そしてもう一方の権限モデルです。ioctl ABI はポインタを一切含まない
  固定構造体です — カーネルがユーザーメモリに手を伸ばす必要が絶対に
  ないように。そしてこの前提が破れるときは、コンパイルエラーではなく、
  最初の呼び出しで起きる MPU 例外です。PROTECTED はこれまでビルドされた
  ことしかなく、しかもエミュレータのないボード上でした。そこで rv-virt の
  protected 構成で立ち上げました: 分割された状態で起動し、`wg` コマンドは
  ユーザー側の blob に住み、すべての設定 ioctl が境界を越え、例外もアサート
  もパニックもなく Linux カーネルの WireGuard までトンネルが届きます。
  メモリマップは既定のままです — カーネル側が8割、ユーザーコマンド側が
  残りの8%を取ります。
- そしてロッキングです。ドライバはプロトコルの状態をデバイスロックの
  下に置いていて、CPU が1つしかないことを前提にはしていません — そして
  今週までは、これはコードから読み取れる主張であって、実際に争ったこと
  のある主張ではありませんでした。そこで: 4 CPU、2000パケットのフラッド
  を、別の CPU が設定 ioctl と down/up サイクルを回している最中に流し
  ました。例外もアサートもなく、トンネルは復帰しました。エミュレータ上の
  1つのスクリプト化されたインターリーブはレース探索ではないので、特定の
  タイミング窓が必要なレースはまだ隠れているかもしれません。ですが、この
  主張はもう机上だけのものではありません。
- 最後の行、そして査読者に最初に見せたい行です。sim のソーク試験は、
  リソースが開始時点にぴったり戻ると言いました。悪くありませんが、
  シミュレータのアロケータはホストのもので、フレームは64ビットです。
  ヒープの数値は一切ボードに転用できません。そこでボードを測りました:
  120秒の負荷、その後40回の down/up サイクル — それぞれが Wi-Fi モジュール
  に属するソケットを usrsock 経由で開閉し直し、実 Wi-Fi 上で再ハンドシェイク
  します。ヒープ、アロケーション数、バッファプール、すべてのスタック高
  水位: 前後で完全に一致。そして本当に欲しかった数字、受信スレッドの実測
  された最大使用量は、既定6キロバイトに対して1472バイトです。この既定値は
  かつては推測でした。今は実測値です。
- そして今、実機の両方のボードで動いています。カーネルドライバは
  ESP32-S3 に書き込まれ、実 Wi-Fi 経由で公式 Windows WireGuard クライアント
  にトンネルしています。SPRESENSE では GS2200M の Wi-Fi が usrsock デバイス
  なので、ドライバの送信は実際に usrsock を通って実機上で外に出ます。
  そしてこの設計が存在する理由そのものである障害ケースを、そのボードで
  強制しました: 実際の usrsock バックエンドにデータグラムが滞留している
  最中に制御操作が到着する、という状況です。問い合わせには応答があり、
  ピアの更新は受理され、停止操作はハングする代わりにタイムアウトを報告し、
  滞留していた暗号文には手が付かず、down を繰り返すことでそれを回収して
  インターフェースが復帰しました。まだカバーしていないのは IOB 枯渇、
  送信中の Wi-Fi 喪失、持続的な負荷です。両ボードでの旧 apps 版 —
  telnet、HTTP、7メガバイトの転送、再鍵化、電源断からの復旧 — はその下に
  そのまま立っています。

## 19 — 検証: 動くトンネルは証拠にならない (14:48 → 17:18) *(核心・削らない)*

**画面:** 3行の表 — 毎回同じ秘密鍵 / トンネルより長生きするセッション鍵 /
数時間経たないと現れないリーク — それぞれ「pingが通れば気づくか」に「気づかない」。

**話す:**
- 前のスライドはどこで動くかでした。このスライドは、動くトンネルが何を
  教えてくれないか、です。
- 鍵生成を例にします。NuttX の既定の `/dev/urandom` はコンパイル時定数で
  シードされる xorshift の疑似乱数です。この経路のままのボードは、起動
  するたびに同じ秘密鍵を配ります。ハンドシェイクは通ります。ping も通ります。
  デモも動きます。トンネルは無価値なのに、ここまで見せてきたものは何一つ
  気づきません。そこで: ボードを3回リセットし、そのたびに鍵を1つ読んで
  比較する — 3つとも異なる鍵で、設定はエントロピープール側にあり、定数
  シードではないと確認できます。安価な確認で、省略していい理由は
  「思いつかなかった」以外にありません。
- 2つ目、インターフェースを down にしても何が生き残るか。ここではコードを
  読むのをやめて、メモリを読みました: 実行中のプロセスの中から、設定した
  鍵に一致するものを探してデバイスを見つけ、ドライバ自身のヘッダーから
  計算したオフセットで、秘密のフィールドを名前で確認します。トランスポート
  鍵はトンネルが up の間は完全に埋まっていて、down の後はすべてのバイトが
  ゼロです。ハンドシェイク状態は up の間ですらすでに消えています — 鍵が
  導出された瞬間に消去されるからです。静的鍵はそのまま残っています —
  意図的に、up をもう一度成功させる必要があるからです。そして書き込み
  可能なアドレス空間全体の中に、前後を通じてその複製はちょうど1つしか
  ありません。この非対称性は設計判断なので、査読者に推測させるのではなく、
  今はドライバのドキュメントに書いてあります。
- 3つ目、ソーク試験です。セッションが失効する時点を過ぎて強制した
  151回の再鍵化、10回のエンドポイント変更、100回の down/up サイクル、
  その間ずっとリソースをサンプリングしました: バッファプールは丸ごと
  戻り、生きているアロケーション数は起動時とちょうど同じに戻ります —
  近いのではなく、同じです。受信スレッドのスタック高水位は2.5キロバイトで、
  最初のサンプル以降動きません。この最後の数字はそれ単体で価値があります:
  そのスレッドの既定スタックは6キロバイトなので、余裕は想定ではなく
  実在するものです。主張していないのは、1週間の連続稼働や、シミュレータの
  アロケータと64ビットフレームがボードと同じように振る舞う、ということです。

## 20 — 設計判断: タイムスタンプ問題には無料の答えがない (17:18 → 21:04) *(核心・削らない)*

**画面:** リプレイ防御が課す義務、4つの選択肢の表(リアルタイム+起動内
高水位 / 毎回永続化 / 耐久性のある範囲予約 / 追いつくのを待つ)、実測の
ペア(時計未設定 → 75秒ハンドシェイクなし、時計設定 → 4.1秒)。

**話す:**
- ここは試験ではなく、判断が必要だった場所です。そして、その判断を
  実際に測りました。
- WireGuard のリプレイ防御は、開始側にある義務を課します: すべての
  ハンドシェイクは、そのピアがこれまでに受理したどのタイムスタンプより
  大きい値を持たなければならず、それは再起動をまたいで成り立たなければ
  なりません。デバイスは通常、発信する側であり、バッテリーバックアップ
  付きの時計を持つ可能性が最も低い側でもあります。
- 再現実験では復旧に75秒かかると出ましたが、この数字は誤解を招きます。
  デバイスは前回のセッションの最後のハンドシェイクを追い越さなければ
  ならないので、通信不能な時間は前回の稼働時間と同じ長さになります。
  75秒なのは、そのセッションが短かったからにすぎません。1か月動いていた
  ものは1か月再接続できません。これだけで「何もしない」という選択肢は
  完全に成立しません。
- 毎回のハンドシェイクでタイムスタンプを書き込むということは、最も
  速さが必要な経路で、数分おきに永遠に flash 書き込みが発生するという
  ことです。範囲を耐久性を持って予約し、RAM から消費していくのが正しい
  長期的な答えで、設計はすでに書いてあります — ただしそれには、順序性と
  耐久性の保証を明言するストレージバックエンドが必要で、それを手に入れる
  ことができませんでした。手元では hostfs の sync は void 関数を呼んで
  OK を返すだけなので、シミュレータでの書き込み成功は電源断について
  何も証明しません。それを出荷すれば、解決したように見えて解決して
  いないことになります。
- そこで: リアルタイムクロック+起動内の高水位マーク、これはまさに
  Linux と wireguard-go がやっていることで、稼働時間へのフォールバックは
  しません。私が付け加えたのは、デスクトップが一度も必要としなかった
  部分です。デスクトップには常に時計があるからです。RTC がない場合、
  NuttX は設定された年から時計をシードします。なので時計がその翌年より
  小さいままなら、一度も設定されていないと分かります — ドライバは
  それを一度だけ警告し、結果まで名指しします。それでもタイムスタンプは
  発行します。この鍵に初めて出会うピアはそれを受理するはずで、拒否すれば
  まさにそうしたボードでの初回ペアリングが壊れるからです。1行のコンソール
  出力に変えているこの失敗は、クラッシュではありません。デスクにない
  デバイス上で、静かに二度と戻ってこないトンネルです。
- そして実機で実際に測りました。実演できない設計論は単なる意見だから
  です。落とし穴は、素朴な試験が通ってしまうことです。ボードをリセット
  して ping すると、16秒でトンネルが戻ります — あなたの ping が「ピア」
  側に発信させたからで、responder は自分のタイムスタンプを必要としません。
  デバイスが完全に発信不能でも、その試験は緑になります。
- そこで: ボードには何も送らず、その自分自身のセッションの見え方を
  観察しました。2回の実行、同じボード、同じピア、同じイメージ、変数は
  1つだけです。起動時のままの時計: ドライバは警告を出し、75秒経っても
  ハンドシェイクは成立しません。私のラップトップから設定した時計:
  警告は止まり、ハンドシェイクは4.1秒で成立します。これで両方が同時に
  立ちます — 未解決のケースはシミュレータだけでなく実機で実在し、時計が
  存在する環境では設計は正しく動きます。#14 がオープンのままなのは、
  証拠が尽きたからではなく、私がそう判断したからです。

## 21 — デモ (21:04 → 21:39)

**話す:**
- デモの要点は、特別なことが何も起きていない、ということです。
- トンネル越しにボードへ telnet してコマンドを実行し、ボード上で
  Web サーバーを起動してブラウザで開きます。USB ケーブルは外してあり、
  ボードは電源アダプタだけで動いています。ピアは家庭の Wi-Fi 越しの

**ライブでやる場合:** `uname -a` / `ifconfig`(wg0 = 10.10.0.2) /
`wg show`(ハンドシェイク成立・転送バイト数) / `ps`(wg_rx 稼働中) /
`webserver &` の後にブラウザで `http://10.10.0.2/`。**画面に出さない:**
`.config` の中身、`kconfig-tweak` の実行画面、ビルドログ、`wg showconf`
(秘密鍵を表示する) — これらの場所には SSID とパスフレーズが平文で
入っている。**フォールバック:** 録画 youtu.be/1kyX2av5WG4。

## 23 — 移植性 (22:00 → 22:24) *(削る候補)*

## 25 — 持ち帰ってほしいこと (22:48 → 23:54)

**話す:**
- 持ち帰ってほしいことを3つ。
- 1つ目、浅い試験は通り、深い試験は落ちる — だから試験は深さのために
  設計してください: 持続的なトラフィック、実機、実カーネルビルド。
  ハンドシェイクが通っただけでは足りません。2つ目、きれいな OS 抽象化
  の境界は苦労するだけの価値があります — 4アーキテクチャ、3バージョン、
  変更ゼロ。3つ目、あるプロジェクトに移植する作業は、そのプロジェクト
  自体を改善する機会になります。1つのバグは NuttX 自身の暗号処理に
  あり、その修正は単独で upstream に出ます。2つ目は、自分のボード
  イメージがクリーンなチェックアウトから再現できることにこだわった
  ことで初めて見つかりました: 素の release タグはこのボードでシェル
  まで起動しません — RTC が立ち上がる前は時計が0を読み、RTC の
  立ち上げを完了させるはずのウォッチドッグが一度も発火しないからです。
  3つ目は自分自身のドライバの中にあり、実カーネルビルドだけがそれを
  表に出しました。sim では絶対に見つかりませんでした。
