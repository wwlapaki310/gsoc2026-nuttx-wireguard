## 5 — プロジェクト概要 (2:28 → 3:12)

**画面:** `wg0` netdev の図 — アプリケーション/NSH、NuttX ネットワークスタック、
`eth0`/`wlan0` の隣に `wg0`、その下に UDP ソケット、インターネット、ピア。

**話す:**
- 全体像を1枚の絵にするとこうなります。
- Apache NuttX は独自の TCP/IP スタックを持つ POSIX 準拠の RTOS です。VPN は
  ありませんでした。このプロジェクトは `wg0` を仮想ネットワークインターフェース
  として追加します — アプリケーションからは普通のインターフェースに見え、
  その下では暗号化された伝送路が UDP ソケットです。反対側のピアは本物の
  WireGuard エンドポイント — Linux、Windows、あるいは別のゲートウェイです。

## 7 — Background: NuttX とは何か (4:04 → 4:53)

**画面:** ソフトウェアスタック図(Applications / POSIX・ANSI・BSD socket API /
Networking・VFS・filesystems・device drivers・NSH shell / NuttX kernel / MCU・MPU)。
下にタグ: RTOS, POSIX-oriented, BSD sockets, Filesystem/VFS, NSH shell,
Native networking, Device drivers, Apache Software Foundation TLP。

**話す:**
- 本題に入る前に、NuttX そのものを説明します。
- NuttX は、標準準拠を第一に置いたリアルタイム OS です。POSIX・ANSI API に準拠し、
  ネットワークは BSD socket で話し、本物のファイルシステムと VFS 層を持ち、
  NSH というシェルがあり、ネイティブなネットワーキングとデバイスドライバのモデルを
  持ちます — これら全部を、8 ビットから 64 ビットのマイクロコントローラで動く
  サイズまで縮めています。NuttX は Apache Software Foundation の top-level project
  でもあり、kernel も applications も documentation も、contributor community に
  よって公開の場で開発されています。
- ここで言いたいことは一つに絞ります: NuttX は小さな RTOS でありながら、Unix 的な
  プログラミングモデルを持っている。この組み合わせは珍しく、この後出てくる
  socket、netdev、POSIX の形をした porting が可能なのは、すべてこれのおかげです。

## 12 — Problem: 遠隔アクセスの隙間 (8:08 → 9:00)

**画面:** Engineer → Internet → Router/network → Wi-Fi → NuttX device の図。
WPA2/WPA3 が守る範囲(Wi-Fi の一区間のみ)と、必要な認証済み end-to-end パスの
対比。下に3枚のカード: open it to the Internet / make your own protocol / use a vendor's cloud。

**話す:**
- ここからは課題そのものを、率直に話します。
- Wi-Fi のセキュリティは本物ですが、守っているのは一区間だけです: デバイスと
  アクセスポイントの間の無線リンク。それより手前 — 技術者、インターネット、
  ルーター — は、WPA2 や WPA3 が約束できる範囲の外です。私が必要としていたのは、
  経路全体 — 技術者からデバイスまで — の認証と暗号化で、最後の数メートルだけ
  ではありません。
- それがないと、実務的な選択肢はどれも今より悪くなります: デバイスにグローバル
  IP を公開して祈る、独自のセキュアプロトコルを発明して保守し続ける、あるいは
  接続をベンダーのクラウドに委ねる。同じ隙間は、edge AI や産業用 IoT、遠隔
  インフラ全般にも現れます — このプロジェクト固有の話ではありません。

## 13 — 他の手段との比較 (9:00 → 10:19)

**画面:** 7つの手段(インターネットにポートを開ける / クラウド API への HTTPS /
MQTT ブローカー / リバーストンネル・リレー / ルーターに VPN / キャリアの閉域網 /
機器に VPN)を、誰から接続するか・任意のサービスに届くか・間にサーバーが要るか・
どこまで守られるか・NuttX に今あるもの、で比べた表。最後の行(機器に VPN)が今回の話。

**話す:**
- WireGuard を選ぶ前に、機器に届くための一般的な方法を比べました。
- ポートを開けるのは簡単ですが、インターネット全体から届いてしまいます。HTTPS と
  MQTT は多くの IoT 製品が使っている方法です。機器からサーバーへ接続しに行くので
  NAT は問題にならず、NuttX にも両方のクライアントがすでにあります。ただし届くのは
  自分で設計したメッセージだけで、機器にログインしたり Web ページを開いたりは
  できません。暗号化もブローカーやクラウドで終わります。
- リバーストンネルは、リレーサーバー経由でポートを1つ通します。ルーターの VPN は
  ルーターが自分のものなら良い方法ですが、LAN の最後の一区間は守られず、顧客の
  現場ではルーターは普通こちらのものではありません。キャリアの閉域網はセルラー
  回線だけで、契約が要ります。
- 機器の上の VPN だけが全部を満たします: 任意の IP サービス、間にサーバーなし、
  機器までの暗号化。データのやり取りには今でも MQTT や HTTPS が正しい道具で、
  これは保守のためのアクセスです。

**Tailscale や ZeroTier について聞かれたら:** これらも機器上の VPN だが、今のところ
マイコンより大きな OS が要ることが多い(スライドの脚注)。

## 14 — Solution: なぜ WireGuard なのか (10:19 → 11:12)

**画面:** Engineer/Linux/Windows ⟷ WireGuard トンネル ⟷ NuttX device の図。
下に3点: modern IP-layer VPN / UDP transport, public-key peers / already
everywhere。

**話す:**
- その課題に対して、なぜ WireGuard なのか、です。
- WireGuard はモダンな IP 層の VPN です: 設計上小さくシンプルで、IPsec や
  OpenVPN に比べてコードサイズがごく一部です — これはマイクロコントローラの
  上では大きな意味を持ちます。素の UDP の上で動き、ピアは証明書や交渉された
  セッションではなく公開鍵で識別されます。正しい鍵を持たないパケットには
  一切返事をしません — 外から見れば、ただのレンガの壁です
  *(9¾番線へのオマージュ。知らなくても普通の比喩として通じる)*。そして重要なのは、特殊なものでは
  ないということです: 何年も前から Linux カーネルに mainline で入っていて、
  公式の Windows クライアントがあり、トンネルの反対側は既存のどんな WireGuard
  ピアでも構いません。
- つまり選んだのは「製品」ではなく、「独自プロトコルを発明する、あるいは
  ベンダーのクラウドに頼る代わりに、標準プロトコルを採用する」という選択です。
  これが、この特定の課題に WireGuard が合う理由です。

メモリに残る?(sim: セッション鍵は down の後すべてゼロ。静的鍵は up をやり直すために意図的に残す)/
数時間後に出るリーク?(sim: 151回の再鍵化、100回の down/up、何も失われない。メモリは起動時の数に戻る。
1週間の試験ではない)。

**話す:**
- このスライドは、動くトンネルが教えてくれないことです: ping では決して気づかない3つの問題。
- まず鍵です。NuttX は `/dev/urandom` の seed をビルド時の設定から取ることができます。
  そうするとボードは起動のたびに同じ秘密鍵を作り、それでもすべて動きます。そこで
  SPRESENSE を3回リセットし、3つの違う鍵を得ました。簡単な確認であって、乱数の質の
  証明ではありません。
- 2つ目、シミュレータでデバイスのメモリを読みました。down の後、セッション鍵は
  すべてゼロでした。静的鍵は、もう一度 up できるように、意図的に残しています。
- 3つ目、長い試験で、これもシミュレータです: 151回の強制的な再鍵化と、100回の
  down/up。バッファは1つも失われず、メモリは起動時とちょうど同じ数に戻りました。
  1週間動いたとか、シミュレータがボードと同じように振る舞う、とは言っていません。

## 31 — 設計判断: タイムスタンプ問題には楽な答えがない (23:19 → 24:42) *(核心・削らない)*

**画面:** 規則(再起動の後でも、相手が見たものより新しいタイムスタンプが要る)。Chosen(リアルタイム
クロック + この起動で使った最大値。Linux・wireguard-go と同じ規則 + 時計が未設定なら警告)/ Not chosen
(毎回保存: flash が摩耗 / flash に範囲を予約: 確かめられなかった書き込み保証が要る / 待つ: 前回動いて
いた時間だけ)。実測のペア(時計未設定 → 75秒でハンドシェイクなし、時計設定 → 4.1秒)。

**話す:**
- ここは試験ではなく、判断が必要だった唯一の場所です。そして、その判断を測りました。
- WireGuard のリプレイ防御には規則があります: すべてのハンドシェイクは、相手が
  これまでに見たものより新しいタイムスタンプを持たなければならない — 再起動の
  後でもです。デバイスは普通ハンドシェイクを始める側で、しかもバッテリー付きの
  時計を持っていない可能性が最も高い側です。
- 毎回のタイムスタンプを保存すると flash が摩耗します。flash に範囲を予約するのが
  長期的には正しい答えですが、それには、これらのファイルシステムで確かめられなかった
  書き込みの保証が必要です。そしてただ待つなら、1か月動いていたデバイスは、1か月
  再接続できません。ここでは、楽な選択と正しい選択が一致しませんでした
  *(ダンブルドアの「正しいことと楽なこと」)*。
- そこで、リアルタイムクロックと、この起動の中で使った最大値を選びました — Linux と
  wireguard-go とまったく同じです。そして時計が一度も設定されていなければ、ドライバが
  一度だけ警告を出します。
- それから実機で測りました。ボードには何も送りませんでした。相手からの ping は、
  ボードの代わりにハンドシェイクを始めてしまうからです。起動時のままの時計: 75秒
  見ていてもハンドシェイクなし。時計を設定すると: 4.1秒。だからドライバは警告を出します。
