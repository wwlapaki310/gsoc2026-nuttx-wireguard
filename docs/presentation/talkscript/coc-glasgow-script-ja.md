## 5 — プロジェクト概要 (2:20 → 2:47)

## 6 — Background: NuttX とは何か (2:47 → 3:32)

**画面:** ソフトウェアスタック図(Applications / POSIX・ANSI・BSD socket API /
Networking・VFS・filesystems・device drivers・NSH shell / NuttX kernel / MCU・MPU)。
下にタグ: RTOS, POSIX-oriented, BSD sockets, Filesystem/VFS, NSH shell,
Native networking, Device drivers, Apache Software Foundation TLP。

**話す:**
- 本題に入る前に、NuttX そのものを説明します。
- NuttX は、標準準拠を第一に置いたリアルタイム OS です。POSIX・ANSI API に準拠し、
  ネットワークは BSD socket で話し、本物のファイルシステムと VFS 層を持ち、
  NSH というシェルがあり、ネイティブなネットワーキングとデバイスドライバのモデルを
  持ちます — これら全部を、8 ビットから 64 ビットのマイクロコントローラで動く
  サイズまで縮めています。NuttX は Apache Software Foundation の top-level project
  でもあり、kernel も applications も documentation も、contributor community に
  よって公開の場で開発されています。
- ここで言いたいことは一つに絞ります: NuttX は小さな RTOS でありながら、Unix 的な
  プログラミングモデルを持っている。この組み合わせは珍しく、この後出てくる
  socket、netdev、POSIX の形をした porting が可能なのは、すべてこれのおかげです。

## 10 — Problem: 遠隔アクセスの隙間 (5:52 → 6:32)

**画面:** Engineer → Internet → Router/network → Wi-Fi → NuttX device の図。
WPA2/WPA3 が守る範囲(Wi-Fi の一区間のみ)と、必要な認証済み end-to-end パスの
対比。下に3枚のカード: public exposure / bespoke protocol / vendor cloud。

**話す:**
- ここからは課題そのものを、率直に話します。
- Wi-Fi のセキュリティは本物ですが、守っているのは一区間だけです: デバイスと
  アクセスポイントの間の無線リンク。それより手前 — 技術者、インターネット、
  ルーター — は、WPA2 や WPA3 が約束できる範囲の外です。私が必要としていたのは、
  経路全体 — 技術者からデバイスまで — の認証と暗号化で、最後の数メートルだけ
  ではありません。
- それがないと、実務的な選択肢はどれも今より悪くなります: デバイスにグローバル
  IP を公開して祈る、独自のセキュアプロトコルを発明して保守し続ける、あるいは
  接続をベンダーのクラウドに委ねる。同じ隙間は、edge AI や産業用 IoT、遠隔
  インフラ全般にも現れます — このプロジェクト固有の話ではありません。

## 11 — Solution: なぜ WireGuard なのか (6:32 → 7:12)

**画面:** Engineer/Linux/Windows ⟷ WireGuard トンネル ⟷ NuttX device の図。
下に3点: modern IP-layer VPN / UDP transport, public-key peers / already
everywhere。

**話す:**
- その課題に対して、なぜ WireGuard なのか、です。
- WireGuard はモダンな IP 層の VPN です: 設計上小さくシンプルで、IPsec や
  OpenVPN に比べてコードサイズがごく一部です — これはマイクロコントローラの
  上では大きな意味を持ちます。素の UDP の上で動き、ピアは証明書や交渉された
  セッションではなく公開鍵で識別されます。そして重要なのは、特殊なものでは
  ないということです: 何年も前から Linux カーネルに mainline で入っていて、
  公式の Windows クライアントがあり、トンネルの反対側は既存のどんな WireGuard
  ピアでも構いません。
- つまり選んだのは「製品」ではなく、「独自プロトコルを発明する、あるいは
  ベンダーのクラウドに頼る代わりに、標準プロトコルを採用する」という選択です。
  これが、この特定の課題に WireGuard が合う理由です。

## 12 — Architecture: NuttX ネットワークスタック上の WireGuard (7:12 → 7:47)

**画面:** Application → TCP/UDP/IP → wg0 (NET_LL_TUN netdev) → WireGuard
encrypt/decrypt → UDP socket → wlan0/usrsock・物理ネットワーク、の層状図。
左右に TX/RX 両方向の矢印。

**話す:**
- 概要図より一段技術的になります。ここから実装の話が始まります。
- 送信方向では、アプリケーションから TCP または UDP・IP を通って降りてきた
  パケットが、他の netdev と同じように `wg0` に届き、WireGuard によって
  暗号化され、ボード上では `wlan0` を通る、あるいは Wi-Fi そのものがソケット
  ベースの周辺機器である `usrsock` を通る UDP データグラムとして出ていきます。
  受信方向はこの逆です: UDP データグラムが届き、WireGuard が復号し、普通の
  インターフェースに届いたかのように `wg0` へ渡されます。
- ここから先はすべて、この真ん中の部分 — `wg0` と暗号化のステップ — を、
  上下の層に触れずに作る話です。

## 14 — Porting Strategy: wireguard-lwip を lwIP なしで再利用する (7:57 → 8:28)

**画面:** 3段カード — Protocol & crypto(KEEP、緑)/ Platform hooks(ADAPT、金、
`wireguard-platform.h` の4関数)/ lwIP network glue(REPLACE、赤)。

**話す:**
- ゼロから暗号スタックを書くのは間違いです。なので `smartalock/wireguard-lwip`
  という既存実装から始めました、その理由です。
- `wireguard-lwip` はきれいに3層に分かれています。プロトコルと暗号 —
  ハンドシェイク、トランスポート、BLAKE2s、ChaCha20-Poly1305、Curve25519 — は
  OS 依存のない移植可能な C なので、無変更のまま持ってこられます。OS 依存の
  振る舞いはすべて、すでに1つのヘッダー、`wireguard-platform.h` の裏に、
  4つの関数として隔離されていました。置き換えが必要だったのは lwIP の
  ネットワークグルーの部分だけです — lwIP の netif を登録し、lwIP のバッファを
  管理する部分です。NuttX には lwIP がそもそも存在しないからです。
- 何も書き直さずに済んだのは運ではなく、きれいなプラットフォーム境界が
  もたらすものです。その境界があったからこそ、最初の移植作業は書き直し
  ではなく差し替えで済み、作業量そのものが桁違いに小さくなりました。

## 15 — Design: lwIP を NuttX netdev へ写像する (8:28 → 8:49)

**画面:** lwIP → NuttX の対応表(`netif`→`net_driver_s`、`pbuf`→`iob`、
`netif_add()`→`netdev_register()`、コールバック→`devif_poll()`)。

**話す:**
- 移植の中で最も重要な判断です。
- lwIP を NuttX に引きずり込むのではなく、抽象化を NuttX 自身のものに写像
  しました。`netif` は `net_driver_s` に、`pbuf` は `iob` に、`netif_add` は
  `netdev_register` に、送信コールバックは NuttX の `devif_poll` になります。
  `wg0` は TUN 型の netdev として登録され、その下の「配線」は UDP ソケットです。

## 16 — Result: 動くトンネルは始まりにすぎない (8:49 → 9:19)

**画面:** 表(Protocol & crypto: 3,079行無変更 / OS hooks: 4関数 / Network glue:
実際の作業)。`wg genkey / set / setconf` が実行時に可能、という claim。

**話す:**
- 最初のバージョンの結果です。
- プロトコルと暗号処理はバイト単位で同一のまま移りました — 3000行以上、
  無変更です。4つの OS フックは小さなものです。本当の作業はネットワークの

- ここまでは成功譚に見えます。そしてこのスライドの本当の役割は、そこです

## 18 — The Testing Pattern: 浅い試験は通り、深い試験は落ちる (9:29 → 9:51)

**画面:** フロー図 — SHALLOW TEST(handshake/ping、✓PASS)→ ASSUMPTION
(「そこは正しいはず」)→ DEEPER TEST(TCP/real HW/kernel/security、✗FAIL)。

**話す:**
- ここがこの話の核心です。
- このプロジェクトの難しいバグは、すべて同じ形をしていました。浅い試験は通る。
  深い試験は落ちる。さらに悪いことに、浅い試験が通ったことでその領域は
  大丈夫だと信じ込み、何時間も他の場所を探し回ることになります。次のスライド
  はそのパターンの実例です — apps版で5つ、そしてカーネルに押し込んでからさらに

## 35 — 運用性 (28:24 → 28:45) *(削る候補2)*

**話す:**
- 「デモで動く」から「運用できる」への移行です。
- 鍵はもうビルドに焼き込まれていません — 実行時に生成・設定でき、

## 36 — 移植性 (28:45 → 29:09) *(削る候補3)*

**話す:**
- 最初からの設計判断を、検証した結果です。
- OS 依存部分を数個の関数の裏に隔離するのは賭けでした。これがその
  検算です。apps の FLAT 実装で: x86、ARM Cortex-A7、ESP32 上の
  Xtensa、SPRESENSE 上の Cortex-M4F という4つのアーキテクチャの
  間を、コード変更なしで移動できます。カーネルドライバはそこに
  sim と rv-virt のカーネルビルドを積み増します。賭けは報われました。

## 38 — 持ち帰ってほしいこと (29:33 → 30:39)

**話す:**
- 持ち帰ってほしいことを3つ。
- 1つ目、浅い試験は通り、深い試験は落ちる — だから試験は深さのために
  設計してください: 持続的なトラフィック、実機、実カーネルビルド。
  ハンドシェイクが通っただけでは足りません。2つ目、きれいな OS 抽象化
  の境界は苦労するだけの価値があります — 4アーキテクチャ、3バージョン、
  変更ゼロ。3つ目、あるプロジェクトに移植する作業は、そのプロジェクト
  自体を改善する機会になります。1つのバグは NuttX 自身の暗号処理に
  あり、その修正は単独で upstream に出ます。2つ目は、自分のボード
  イメージがクリーンなチェックアウトから再現できることにこだわった
  ことで初めて見つかりました: 素の release タグはこのボードでシェル
  まで起動しません — RTC が立ち上がる前は時計が0を読み、RTC の
  立ち上げを完了させるはずのウォッチドッグが一度も発火しないからです。
  3つ目は自分自身のドライバの中にあり、実カーネルビルドだけがそれを
  表に出しました。通常の sim 構成では見つかりませんでした。
