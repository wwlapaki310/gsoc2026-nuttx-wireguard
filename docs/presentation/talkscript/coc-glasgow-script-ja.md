## 7 — Background: NuttX とは何か (3:45 → 4:33)

**画面:** ソフトウェアスタック図(Applications / POSIX・ANSI・BSD socket API /
Networking・VFS・filesystems・device drivers・NSH shell / NuttX kernel / MCU・MPU)。
下にタグ: RTOS, POSIX-oriented, BSD sockets, Filesystem/VFS, NSH shell,
Native networking, Device drivers, Apache Software Foundation TLP。

**話す:**
- 本題に入る前に、NuttX そのものを説明します。
- NuttX は、標準準拠を第一に置いたリアルタイム OS です。POSIX・ANSI API に準拠し、
  ネットワークは BSD socket で話し、本物のファイルシステムと VFS 層を持ち、
  NSH というシェルがあり、ネイティブなネットワーキングとデバイスドライバのモデルを
  持ちます — これら全部を、8 ビットから 64 ビットのマイクロコントローラで動く
  サイズまで縮めています。NuttX は Apache Software Foundation の top-level project
  でもあり、kernel も applications も documentation も、contributor community に
  よって公開の場で開発されています。
- ここで言いたいことは一つに絞ります: NuttX は小さな RTOS でありながら、Unix 的な
  プログラミングモデルを持っている。この組み合わせは珍しく、この後出てくる
  socket、netdev、POSIX の形をした porting が可能なのは、すべてこれのおかげです。

## 12 — Problem: 遠隔アクセスの隙間 (7:48 → 8:40)

**画面:** Engineer → Internet → Router/network → Wi-Fi → NuttX device の図。
WPA2/WPA3 が守る範囲(Wi-Fi の一区間のみ)と、必要な認証済み end-to-end パスの
対比。下に3枚のカード: open it to the Internet / make your own protocol / use a vendor's cloud。

**話す:**
- ここからは課題そのものを、率直に話します。
- Wi-Fi のセキュリティは本物ですが、守っているのは一区間だけです: デバイスと
  アクセスポイントの間の無線リンク。それより手前 — 技術者、インターネット、
  ルーター — は、WPA2 や WPA3 が約束できる範囲の外です。私が必要としていたのは、
  経路全体 — 技術者からデバイスまで — の認証と暗号化で、最後の数メートルだけ
  ではありません。
- それがないと、実務的な選択肢はどれも今より悪くなります: デバイスにグローバル
  IP を公開して祈る、独自のセキュアプロトコルを発明して保守し続ける、あるいは
  接続をベンダーのクラウドに委ねる。同じ隙間は、edge AI や産業用 IoT、遠隔
  インフラ全般にも現れます — このプロジェクト固有の話ではありません。

## 13 — 他の手段との比較 (8:40 → 9:57)

**画面:** 7つの手段(インターネットにポートを開ける / クラウド API への HTTPS /
MQTT ブローカー / リバーストンネル・リレー / ルーターに VPN / キャリアの閉域網 /
機器に VPN)を、誰から接続するか・任意のサービスに届くか・間にサーバーが要るか・
どこまで守られるか・NuttX に今あるもの、で比べた表。最後の行(機器に VPN)が今回の話。

**話す:**
- WireGuard を選ぶ前に、機器に届くための一般的な方法を比べました。
- ポートを開けるのは簡単ですが、インターネット全体から届いてしまいます。HTTPS と
  MQTT は多くの IoT 製品が使っている方法です。機器からサーバーへ接続しに行くので
  NAT は問題にならず、NuttX にも両方のクライアントがすでにあります。ただし届くのは
  自分で設計したメッセージだけで、機器にログインしたり Web ページを開いたりは
  できません。暗号化もブローカーやクラウドで終わります。
- リバーストンネルは、リレーサーバー経由でポートを1つ通します。ルーターの VPN は
  ルーターが自分のものなら良い方法ですが、LAN の最後の一区間は守られず、顧客の
  現場ではルーターは普通こちらのものではありません。キャリアの閉域網はセルラー
  回線だけで、契約が要ります。
- 機器の上の VPN だけが全部を満たします: 任意の IP サービス、間にサーバーなし、
  機器までの暗号化。データのやり取りには今でも MQTT や HTTPS が正しい道具で、
  これは保守のためのアクセスです。

**Tailscale や ZeroTier について聞かれたら:** これらも機器上の VPN だが、今のところ
マイコンより大きな OS が要ることが多い(スライドの脚注)。

## 14 — Solution: なぜ WireGuard なのか (9:57 → 10:50)

**画面:** Engineer/Linux/Windows ⟷ WireGuard トンネル ⟷ NuttX device の図。
下に3点: modern IP-layer VPN / UDP transport, public-key peers / already
everywhere。

**話す:**
- その課題に対して、なぜ WireGuard なのか、です。
- WireGuard はモダンな IP 層の VPN です: 設計上小さくシンプルで、IPsec や
  OpenVPN に比べてコードサイズがごく一部です — これはマイクロコントローラの
  上では大きな意味を持ちます。素の UDP の上で動き、ピアは証明書や交渉された
  セッションではなく公開鍵で識別されます。正しい鍵を持たないパケットには
  一切返事をしません — 外から見れば、ただのレンガの壁です
  *(9¾番線へのオマージュ。知らなくても普通の比喩として通じる)*。そして重要なのは、特殊なものでは
  ないということです: 何年も前から Linux カーネルに mainline で入っていて、
  公式の Windows クライアントがあり、トンネルの反対側は既存のどんな WireGuard
  ピアでも構いません。
- つまり選んだのは「製品」ではなく、「独自プロトコルを発明する、あるいは
  ベンダーのクラウドに頼る代わりに、標準プロトコルを採用する」という選択です。
  これが、この特定の課題に WireGuard が合う理由です。

## 15 — Architecture: NuttX ネットワークスタック上の WireGuard (10:50 → 11:38)

**画面:** Application → TCP/UDP/IP → wg0 (NET_LL_TUN netdev) → WireGuard
encrypt/decrypt → UDP socket → wlan0/usrsock・物理ネットワーク、の層状図。
左右に TX/RX 両方向の矢印。

  計算したオフセットで、秘密のフィールドを名前で確認します。トランスポート
  鍵はトンネルが up の間は完全に埋まっていて、down の後はすべてのバイトが
  ゼロです。ハンドシェイクと次世代鍵の材料についても、意図的に制御した
  状態で up の間は非ゼロであることを確認した上で、down の後はすべて
  ゼロになることを確認しました。静的鍵はそのまま残っています —
  意図的に、up をもう一度成功させる必要があるからです。そして書き込み
  可能なアドレス空間全体の中に、前後を通じてその複製はちょうど1つしか
  ありません。この非対称性は設計判断なので、査読者に推測させるのではなく、
  今はドライバのドキュメントに書いてあります。
- 3つ目、ソーク試験です。セッションが失効する時点を過ぎて強制した
  151回の再鍵化、10回のエンドポイント変更、100回の down/up サイクル、
  その間ずっとリソースをサンプリングしました: バッファプールは丸ごと
  戻り、生きているアロケーション数は起動時とちょうど同じに戻ります —
  近いのではなく、同じです。受信スレッドのスタック高水位は2.5キロバイトで、
  最初のサンプル以降動きません。この最後の数字はそれ単体で価値があります:
  そのスレッドの既定スタックは6キロバイトなので、余裕は想定ではなく
  実在するものです。主張していないのは、1週間の連続稼働や、シミュレータの
  アロケータと64ビットフレームがボードと同じように振る舞う、ということです。

## 34 — 設計判断: タイムスタンプ問題には無料の答えがない (27:54 → 31:42) *(核心・削らない)*

**画面:** リプレイ防御が課す義務、4つの選択肢の表(リアルタイム+起動内
高水位 / 毎回永続化 / 耐久性のある範囲予約 / 追いつくのを待つ)、実測の
ペア(時計未設定 → 75秒ハンドシェイクなし、時計設定 → 4.1秒)。

**話す:**
- ここは試験ではなく、判断が必要だった場所です。そして、その判断を
  実際に測りました。
- WireGuard のリプレイ防御は、開始側にある義務を課します: すべての
  ハンドシェイクは、そのピアがこれまでに受理したどのタイムスタンプより
  大きい値を持たなければならず、それは再起動をまたいで成り立たなければ
  なりません。デバイスは通常、発信する側であり、バッテリーバックアップ
  付きの時計を持つ可能性が最も低い側でもあります。
- 稼働時間を使っていた古い timestamp でのシミュレータ実験では、復旧に75秒かかりましたが、この数字は誤解を招きます。
  デバイスは前回のセッションの最後のハンドシェイクを追い越さなければ
  ならないので、通信不能な時間は前回の稼働時間と同じ長さになります。
  75秒なのは、そのセッションが短かったからにすぎません。1か月動いていた
  ものは1か月再接続できません。これだけで「何もしない」という選択肢は
  完全に成立しません。
- 毎回のハンドシェイクでタイムスタンプを書き込むということは、最も
  速さが必要な経路で、数分おきに永遠に flash 書き込みが発生するという
  ことです。範囲を耐久性を持って予約し、RAM から消費していくのが正しい
  長期的な答えで、設計はすでに書いてあります — ただしそれには、順序性と
  耐久性の保証を明言するストレージバックエンドが必要で、それを手に入れる
  ことができませんでした。手元では hostfs の sync は void 関数を呼んで
  OK を返すだけなので、シミュレータでの書き込み成功は電源断について
  何も証明しません。それを出荷すれば、解決したように見えて解決して
  いないことになります。ここでは、楽な選択と正しい選択が一致しませんでした
  *(ダンブルドアの「正しいことと楽なこと」)*。
- そこで: リアルタイムクロック+起動内の高水位マーク、これはまさに
  Linux と wireguard-go がやっていることで、稼働時間へのフォールバックは
  しません。私が付け加えたのは、デスクトップが一度も必要としなかった
  部分です。デスクトップには常に時計があるからです。RTC がない場合、
  NuttX は設定された年から時計をシードします。なので時計がその翌年より
  小さいままなら、一度も設定されていないと分かります — ドライバは
  それを一度だけ警告し、結果まで名指しします。それでもタイムスタンプは
  発行します。この鍵に初めて出会うピアはそれを受理するはずで、拒否すれば
  まさにそうしたボードでの初回ペアリングが壊れるからです。1行のコンソール
  出力に変えているこの失敗は、クラッシュではありません。デスクにない
  デバイス上で、静かに二度と戻ってこないトンネルです。
- そして実機で実際に測りました。実演できない設計論は単なる意見だから
  です。落とし穴は、素朴な試験が通ってしまうことです。ボードをリセット
  して ping すると、16秒でトンネルが戻ります — あなたの ping が「ピア」
  側に発信させたからで、responder は自分のタイムスタンプを必要としません。
  デバイスが完全に発信不能でも、その試験は緑になります。
- そこで: ボードには何も送らず、その自分自身のセッションの見え方を
  観察しました。2回の実行、同じボード、同じピア、同じイメージ、変数は
  1つだけです。起動時のままの時計: ドライバは警告を出し、75秒経っても
  ハンドシェイクは成立しません。私のラップトップから設定した時計:
  警告は止まり、ハンドシェイクは4.1秒で成立します。これで両方が同時に
  立ちます — 未解決のケースはシミュレータだけでなく実機で実在し、時計が
  存在する環境では設計は正しく動きます。#14 がオープンのままなのは、
  証拠が尽きたからではなく、私がそう判断したからです。

## 37 — デモ (32:50 → 34:20)

**画面:** 7つの手順 — wg show / telnet 10.10.0.2 / ifconfig /
stackchan face happy / stackchan say hello.wav / tcpdump の外と内 /

**話す:**

  スタックちゃんは、暗号化トンネルの向こう側にある普通のコンピュータです。
- まずラップトップで wg show。ハンドシェイクが済んでいて、スマホの
  ネットワーク上のスタックちゃんのアドレスが見えます。次に 10.10.0.2 へ
  telnet します — これはトンネルの中のアドレスです。ifconfig を打つと両方が
  見えます。スマホのネットワーク側の wlan0 と、トンネルの中の wg0。

  右はトンネルの中: 同じ telnet のやり取りが平文で見えます。もう一度
  wg show すると、転送バイト数が増えています。Mischief managed(いたずら完了)

右にスタックちゃん(カメラか机の上)。

**本番前:** スマホのテザリングを ON(2.4 GHz / 互換性優先)、ラップトップを
