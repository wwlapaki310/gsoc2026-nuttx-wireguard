## 2. 何をやったか

**見出し:** NuttX に VPN がなかった

| | 従来 | 今回 |
|---|---|---|
| 接続手段 | シリアルケーブル | **ネットワーク** |
| 場所 | 機器の前 | **リモート** |
| 経路 | 平文 | **暗号化トンネル** |
| 道具 | 専用 | `ssh` / `telnet` / HTTP **そのまま** |

- WireGuard（VPN プロトコル）を Apache NuttX に移植
- `wg0` = 仮想ネットワークインターフェース
- アプリから見れば **ただの NIC**

> 図案: 左に「PC ─ シリアル ─ ボード」、右に「PC ─ インターネット ─ 暗号化トンネル ─ ボード」

## 3. なぜやったか

**見出し:** 現場に置いたあと、触れない

**きっかけ:** GSoC のテーマ一覧

**業務の 2 つの現場**

| | 何 | なぜ触れない |
|---|---|---|
| **AITRIOS** | エッジ AI プラットフォームの AI カメラ<br>（**ESP32 + NuttX**） | 天井・屋外の高所。異常の兆候だけで人は出せない |
| **人工衛星** | ボトムアップ活動<br>（**SPRESENSE**） | 打ち上げ後は物理アクセス不可 |

→ **ネットワークが唯一のメンテナンス経路**

**そのときの選択肢**

- グローバル IP を晒す → 攻撃対象になる
- 独自プロトコルを作る → 認証も暗号も自作
- ベンダークラウド → ロックイン

> ### 本来は VPN で解決する話。NuttX にはその選択肢がなかった。
> WireGuard は約 4,000 行 — **マイコンに載る**

## 4. どう作ったか

**見出し:** 4 関数だけ置き換える

**移植元:** wireguard-lwip（BSD-3-Clause）— OS 依存が 4 関数に隔離されている

| | 扱い | 規模 |
|---|---|---|
| プロトコル・暗号 | **無改変で流用**（upstream とバイト一致） | 約 3,000 行 |
| OS 依存の 4 関数 | NuttX の POSIX API で実装 | 186 行 |
| lwIP netif グルー | **NuttX 用に書き直し** | 約 2,700 行 |

- NuttX は lwIP ではなく**独自スタック** → netif は流用不可
- `wg0` は `netdev_register()` で登録。**「配線」は UDP ソケット**

> ### 結果: 4 アーキテクチャで**コード変更ゼロ**
> x86_64 / ARM Cortex-A7 / Xtensa LX7 / ARM Cortex-M4F

## 5. いまどこまで

**見出し:** ESP32-S3 実機で動作

**デモ動画:** <https://youtu.be/1kyX2av5WG4>

- トンネル越しに telnet → ボード上で Web サーバ起動 → ブラウザで閲覧
- **USB 未接続。電源アダプタのみ**
- 相手は Windows 公式クライアント = **仕様側の実装との相互運用**

**並行して**

| 対象 | 状態 |
|---|---|

| SPRESENSE | `wg0` 起動まで確認済み。Wi-Fi モジュール確保後に通信検証 |

> 図案: デモ動画のサムネイル、またはブラウザで `http://10.10.0.2/` が開いている画面

## 補足: 想定質問

| Q | A |
|---|---|
| 速度は | ESP32-S3 実機・実 Wi-Fi 経由でトンネル越し TCP 約 **260 KiB/s** |
| なぜ WireGuard か | 実装規模。OpenVPN / IPsec は十万行以上、WireGuard は約 4,000 行。暗号スイート固定でネゴシエーションがない |
| 苦労した点は | 「テストは通るが壊れている」の繰り返し。最悪は **`ping` は 0% ロスで通るのに TCP のデータだけ 1 バイトも届かない**（詳細は本編） |
| 実用になるか | 実行時設定・設定の永続化・複数ピアまで動作。最長連続動作は 4 時間 28 分で、停止原因は Wi-Fi ドライバ側と特定済み |
