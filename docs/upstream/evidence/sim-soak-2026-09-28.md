# T7 soak — sim, 2026-09-28

Run: `scripts/kernel/verify-sim-wg-soak.sh` (defaults: 620 s of forced rekeys,
100 down/up cycles) in the `wgdev` container, against a Linux kernel WireGuard
peer on `tap0`. Requires `CONFIG_STACK_COLORATION=y`, which the script checks.

## What was driven

| Phase | Work | Result |
|---|---|---|
| A | forced rekeys for 620 s — longer than `REJECT_AFTER_TIME × 3` (540 s), so sessions genuinely expire and are rebuilt rather than refreshed | **151 rekeys, 0 failures** |
| B | move both ends to a new port, cycle the interface so NuttX has to dial out to the newly configured endpoint, confirm traffic | **10/10** |
| C | `wg down` / `wg up`, traffic confirmed every 10th cycle | **100 cycles** |

A rekey is forced by dropping and re-adding the peer on the Linux side: it then
has to initiate, and NuttX has to respond and install a new key pair. Every
rekey was confirmed by traffic actually flowing afterwards, not by a log line.

Checks, all passing:

| | |
|---|---|
| the IOB pool is whole at rest | 24/24 |
| no task ever waited for an IOB | `nwait` 0 in every sample |
| live allocations return to the boot count | 116 → 116 |
| heap in use returns to the boot level | 1926816 → 1926816 |
| the `wg_rx` stack high-water does not grow after the first samples | 2536 → 2536 |
| the `wg_rx` stack stays clear of its limit | worst 3.5 % filled |

The interesting part is that the numbers are *identical*, not merely close: the
live allocation count is the leak detector, since a buffer, peer snapshot or
queue entry that is never freed raises it and never lowers it again. `wg_rx`
appears only while the interface is up, which is why the boot and rest rows
have no value for it — and those two rows are byte-for-byte the pre-tunnel
state.

The high-water figure is useful on its own: the receive thread's deepest
observed use across 151 rekeys and 100 lifecycle cycles is **2536 bytes**,
against a `CONFIG_NET_WIREGUARD_RXSTACKSIZE` default of 6144.

## What this does not show

- **Sim, not a board.** The sim's allocator is the host's and its 64-bit frames
  are larger than a 32-bit target's, so the stack figure is conservative in the
  right direction but the heap figures do not transfer. The `FILLED` percentage
  is meaningless here because the sim gives the thread roughly 72 KB rather
  than the configured 6144; only the absolute high-water is comparable.
- **Hours, not days.** Roughly 15 minutes of wall clock. It crosses the
  expiration horizon several times over, which is what makes the rekeys real,
  but it is not an endurance run.
- Rekeys are forced by the peer rather than left to WireGuard's own timers, so
  the *timer* path into rekeying is exercised far less than the responder path.
- No IOB exhaustion, no packet loss, no concurrent load beyond the keepalives:
  the pool never went below full, so throttling and `nwait` behaviour are
  untested.
- Stack high-water for the tasks that matter on real hardware (the Wi-Fi and
  usrsock threads) is not measured here at all.
