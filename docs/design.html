wg0 — NuttX に WireGuard を通す

01 — 動機

「設置したあと、どうやって触るのか」

組み込み機器の一番難しい問題は、作ることではなく、 現場に置いたあとで安全に触り続けることにある。

ファームウェアを更新したい。ログを回収したい。挙動がおかしいから中を見たい。 機器が手元にある間はシリアルケーブルで済むが、設置してしまえばネットワーク越しに触るしかない。 このとき現実に取られている手段は、大きく3つに分かれる。

方式 C が理想なのは以前から明らかだった。問題は実装規模で、OpenVPN や IPsec は 数十万行あり、数百 KB の RAM しかないマイコンには載らない。 WireGuard はここを一段変えた。

IPsec (strongSwan 等)〜 数十万行 IKE ネゴシエーション(可変)載らない

小ささの源は「選ばせない」ことにある。暗号方式を固定してネゴシエーションを排したので、 状態機械が小さく、攻撃面も小さい。トランスポートは UDP 単一ポートのみ。 この設計思想が、そのまま組み込み適性になっている。

02 — 何が広がるか

トンネルが1本通ると、その上は自由になる

wg0 が作るのは「安全な通信機能」ではなく、 安全な IP 経路そのもの。だから上に載るものを選ばない。

ここが VPN と「独自の暗号化プロトコルを作り込む」ことの決定的な差になる。 独自プロトコルは、その中で定義した操作しかできない。 一方トンネルは L3 で成立するので、既存のあらゆる TCP/UDP アプリケーションが、 一行も変更せずにそのまま安全になる。

NuttX 側から見た意味

NuttX は POSIX 準拠で、対応アーキテクチャも広い。そこに VPN が入ると、 次のような運用が「特別な作り込みなし」で成立するようになる。

  • NAT 配下の機器に到達できる — 機器側からトンネルを張るので、 設置先のルータ設定に手を入れる必要がない。工場・現場・顧客先で効く。
  • 機器単位の鍵と到達範囲 — 公開鍵ごとに allowed-ips を割り当てるため、 「この機器はこのサブネットにしか触れない」を暗号レベルで強制できる。
  • クラウド非依存 — 必要なのは自前のサーバ1台。 ベンダーのサービス終了や課金体系の変更に運用が左右されない。
  • ローミングに強い — WireGuard はエンドポイントを受信パケットから学習するため、 機器の IP が変わっても(モバイル回線・Wi-Fi 切替)セッションが継続する。
適用領域の例

遠隔地のセンサーノード、産業機器の保守、エッジ AI カメラの映像・モデル更新、 移動体やロボットのテレメトリ — いずれも「設置後に安全に触り続ける」ことが 運用コストの大半を占める。NuttX が動く先すべてが対象になる。

03 — 設計判断

どの層に実装するか

移植元は lwIP 向けの実装。しかし NuttX は lwIP を使っていない。 ここが本移植の最初の、そして最大の設計判断になった。

ベースにしたのは wireguard-lwip(BSD-3-Clause)。 プロトコルと暗号のコアが OS 非依存に書かれており、 OS 依存はすべて wireguard-platform.h の4関数に隔離されている。 この構造のおかげでコアは1行も変えずに済んだ。

問題はネットワークインターフェース層だった。 NuttX は独自のネットワークスタックを持っており、 lwIP の netif / pbuf / udp_pcb は存在しない。 つまり wireguardif.c は流用できず、書き直すしかなかった。

プラットフォーム層 — 移植に必要だった全て

OS 依存として実装が必要だったのは、次の4関数だけだった。 この隔離の質が、そのまま移植性として現れている (sim / QEMU / Xtensa / ARM Cortex-M4F すべてで無変更)。

設計メモ — なぜ is_under_load は常に false か

cookie 機構は、大量のハンドシェイクを捌くサーバを守るための仕組み。 単一ピアの組み込み機器はその形をしていないため、常に false を返している。 結果として upstream の mac2 / cookie 応答経路は到達不能になり、その分コードが減る。 載せないという判断も設計のうち。

04 — データ経路

暗号化はどこで起きるか

wg0 は「配線が UDP ソケットになっている仮想 NIC」として振る舞う。 送信は NuttX スタックから渡されたパケットを暗号化して UDP で送り出し、 受信は UDP を復号してスタックに注入し直す。 この「注入し直す」点が、後述する実行コンテキストの問題に直結する。

05 — 実行コンテキスト

設計の肝 — ソケットは誰のものか

本移植で最も時間を要した問題は、暗号でもプロトコルでもなく、 「どのタスクからそのソケットが見えるか」だった。

症状はこうだった。実機で ping は 0% packet loss で通る。 しかし同じトンネルで telnet すると、TCP の 3-way ハンドシェイクは成立するのに、 telnetd のバナーが1バイトも届かない。 WireGuard を通さず同一 LAN で telnet すると正常に動く。

原因は、NuttX のファイルディスクリプタがタスクグループ単位でスコープされることにあった。

設計上の制約 — 明示しておくべきこと

psock_*() は NuttX の内部 API であり、 net_lock() / netdev_register() / iob_* と同様、 カーネル空間とリンクされることが前提になる。 したがって本実装は現状 FLAT ビルドを前提としている。 PROTECTED / KERNEL ビルドで動かすには別途の設計が必要で、 これは upstream 提出時に論点になりうる。

同じ根を持つ3つの落とし穴

いずれも「POSIX 準拠だから Linux と同じだろう」という前提が崩れた箇所だった。

06 — プロトコル

ハンドシェイクと鍵の寿命

暗号処理そのものは upstream の実装に委ねているが、 タイマー駆動(いつ再ハンドシェイクするか、いつ keepalive を送るか)は 移植側の責任範囲になる。wg_rx タスクが受信待ちのタイムアウトを利用して この判定を回している。

受信タスクのスタックサイズは当初 3,072 B(根拠のない既定値)だった。 CONFIG_STACK_COLORATION で実測したところピークが 2,896 B、 つまり余裕は 176 バイトしかなかった。 ipv4_input() を自タスクで呼ぶ設計(図 4)の当然の帰結である。

ただし、この計測は最悪ケースではなかった。 上の値から既定値を 4,096 B と決めたが、後日ボードを数時間動かしたあとに取れた クラッシュダンプでは高水位が 3,392 B に達していた。 深いパスはパケットがどの状態の組み合わせで到着するかに依存するため、 短時間の負荷試験では現れない。 現在の既定値は 6,144 B で、3,392 B に対して約 45% の余裕がある。 計測方法と、短時間では足りないことを Kconfig の help に残している。 IPv6 や IP フラグメントを有効にする場合は再測定が要る。

08 — 運用

鍵をビルドに焼かない

設定がビルド時固定だと、ピアを1つ変えるだけで再ビルドと書き込みが要る。 それは開発中の不便で済まず、秘密鍵がビルド成果物に残るという 性質の問題でもある。

そこでコマンド体系を本家 wg(8) に寄せ、設定ファイル形式も 本家と同じ INI 形式にした。独自形式を作らなかったことで、 デスクトップの WireGuard クライアントと設定ファイルがそのまま行き来する。

電源を切っても残す

新しいストレージ API は作っていない。保存はシェルのリダイレクトで足りる。

複数ピア

ピア数は CONFIG_NET_WIREGUARD_MAX_PEERS で決まる。 vendored コードは malloc を避けて構造体内に静的確保するため、これは そのまま RAM との取引になる — ESP32-S3 実測で 1ピアあたり約 904 バイト(1ピア 4,324 B → 8ピア 10,652 B)。 大半は rekey 中に新旧の鍵を並行保持するための3つの keypair。

10 — まとめ

移植して分かったこと

  • 隔離の質が移植性になる。 OS 依存が4関数に閉じていたおかげで、sim・QEMU・Xtensa・ARM Cortex-M4F すべてで プラットフォーム層は無変更のまま動いた。
  • 相手を本物にする。 Linux カーネル実装と Windows 公式クライアントを相手にしたことで、 「動いた」が相互運用性の証明になった。
  • POSIX 準拠は Linux 互換ではない。 SO_RCVTIMEO・detached pthread・fd スコープ — 3つの落とし穴はすべてこの思い込みから出た。
  • ping が通ることは、経路が正しいことの証明にならない。 同期応答と非同期送信では、通るコンテキストが違う。
  • 「たぶん影響は小さい」を実測すると、10 倍だったりする。 暫定のポーリング実装が、実はスループットを律速していた。

そして本題に戻ると — NuttX が VPN を持つということは、 組み込み機器が「設置したら終わり」でなくなるということだった。 トンネルが1本通れば、その上で動くものは選ばない。

Apache NuttX WireGuard port  ·  実測はすべて ESP32-S3(Xtensa LX7 / 16 MB flash / 8 MB PSRAM)実機・実 Wi-Fi 環境による。
