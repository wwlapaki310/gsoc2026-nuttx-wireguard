## 3. Apache NuttX とは

**[スライド]**
- POSIX 準拠の組み込み RTOS(Apache Software Foundation)
- 数十 KB 〜 の小さなマイコンでも動く
- `open()` / `read()` / `socket()` / `pthread` がそのまま使える
- 対応アーキテクチャ: ARM / RISC-V / Xtensa / x86 …

**[話すこと]**
NuttX は Apache Software Foundation で開発されている組み込み向けの RTOS です。特徴は POSIX 準拠であることで、`open` や `socket`、`pthread` といった Linux でおなじみの API がそのまま使えます。「小さいけれど Linux っぽく書ける」というのが売りです。今回それが効いた場面と、逆に「Linux っぽいけど Linux ではない」ことで嵌まった場面の両方があり、後半で話します。

---

## 4. WireGuard とは

**[スライド]**
- モダンな VPN プロトコル(Linux カーネルに 5.6 でマージ)
- 特徴: **とにかく小さい**
  - OpenVPN / IPsec: 数十万行
  - WireGuard: 約 4,000 行
- 暗号スイートが固定(Noise / Curve25519 / ChaCha20-Poly1305 / BLAKE2s)
  - ネゴシエーションがない = 実装が小さい・攻撃面が小さい
- UDP 単一ポートで動く

**[話すこと]**
WireGuard は比較的新しい VPN プロトコルで、Linux カーネル 5.6 でマージされています。何が嬉しいかというと、とにかく実装が小さいことです。OpenVPN や IPsec が数十万行あるのに対し、WireGuard は約 4,000 行です。暗号スイートを固定してネゴシエーションをなくしたのが効いていて、実装が小さいということは、監査しやすく、そして **組み込みに載る** ということです。ここが今回の出発点です。

## 5. なぜ NuttX × WireGuard なのか

**[スライド]**
- 組み込み機器を **現場に置いたあと** どうやって触るか?
  - ファームウェア更新、ログ回収、デバッグ
- 現実解: グローバル IP を晒す / 独自プロトコル / クラウド経由
  - → 安全でない・作り込みが必要・ベンダーロックイン
- NuttX には VPN の選択肢が **なかった**
- WireGuard なら小さいので載る

**[話すこと]**
そもそもなぜ組み込みに VPN が要るのか。実際に機器を現場に設置したあと、ファームウェアを更新したりログを取ったりデバッグしたりする必要が出てきます。そのときの選択肢が、グローバル IP を直接晒すか、独自プロトコルを作り込むか、ベンダーのクラウドに繋ぐか、というのが現実です。どれも嬉しくない。ここに VPN があれば素直に解決するのに、NuttX には選択肢がありませんでした。そして WireGuard は小さいので載る。これが動機です。

## 6. アプローチ: 何をベースにするか

**[スライド]**
- ベース: [wireguard-lwip](https://github.com/smartalock/wireguard-lwip) (BSD-3-Clause)
  - lwIP 向けの WireGuard 実装
  - OS 依存を `wireguard-platform.h` の **4関数**に隔離済み
- 移植方針:
  - プロトコル・暗号コア (`wireguard.c` / `crypto/`) → **無改変で流用**
  - lwIP netif グルー (`wireguardif.c`) → **NuttX 用に書き直し**

**[話すこと]**
ゼロから書くのではなく、wireguard-lwip という lwIP 向けの実装をベースにしました。BSD ライセンスで、NuttX のライセンスポリシーとも相性がいいです。この実装のいいところは、OS 依存の部分が `wireguard-platform.h` の4つの関数に隔離されていることです。なので、プロトコルと暗号のコアはそのまま持ってきて、lwIP に依存しているネットワークインターフェース部分だけを NuttX 用に書き直す、という方針にしました。

## 7. 設計判断: lwIP netif ではなく NuttX netdev として

**[スライド]**

| | lwIP | NuttX |
|---|---|---|
| NIC 抽象 | `struct netif` | `struct net_driver_s` |
| バッファ | `pbuf` | `iob` |
| 登録 | `netif_add()` | `netdev_register()` |

- NuttX は **独自のネットワークスタックを持っている**(lwIP ではない)
- → `wireguardif.c` は使えない。`drivers/net/tun.c` を手本に書き直し
- `wg0` を `NET_LL_TUN` の netdev として登録
- **「配線」は物理 NIC ではなく UDP ソケット**

**[話すこと]**
ここが最初の設計判断です。NuttX は lwIP を使っておらず、独自のネットワークスタックを持っています。NIC の抽象化もバッファ管理も登録 API も全部違うので、`wireguardif.c` はそのまま使えません。そこで NuttX の TUN ドライバを手本にして、`wg0` を仮想 NIC として登録する形で書き直しました。ポイントは、この仮想 NIC の「配線」が物理的なイーサネットではなく **UDP ソケット** だということです。

## 8. データの流れ

**[スライド]**

```
[送信]
アプリ → NuttX TCP/IP → wg0 (netdev)
   → devif_poll() → wg_txpoll()
   → 暗号化 (ChaCha20-Poly1305)
   → sendto() ── UDP ──→ 相手のピア

[受信]
相手のピア ── UDP ──→ recvfrom() (wg_rx タスク)
   → 復号
   → ipv4_input() で NuttX スタックに注入
   → アプリ
```

**[話すこと]**
データの流れはこうなります。送信側は、アプリが `wg0` 宛にパケットを出すと、NuttX のスタックがそれを `wg0` に渡してくるので、暗号化して UDP で相手に送る。受信側は、バックグラウンドのタスクが UDP を待っていて、届いたら復号して、`ipv4_input()` で NuttX のスタックに注入し直す。この「注入し直す」ところが後で効いてきます。

## 11. ここからが本題: 3つの落とし穴

**[スライド]**
- 動くまでに OS 側の前提で3回ハマった
- いずれも **「Linux っぽいけど Linux ではない」** ことに起因
  1. `SO_RCVTIMEO` が効かない
  2. detach した pthread が消える
  3. **`sendto()` が `EBADF` を返す** ← 一番厄介

**[話すこと]**
ここからが今日の本題です。動くまでに3回ハマりました。どれも「POSIX 準拠だから Linux と同じだろう」と思い込んでいたところで足をすくわれています。順番に紹介します。

---

## 12. 落とし穴 1: `SO_RCVTIMEO` が効かない

**[スライド]**
- 設計: `recvfrom()` をタイムアウト付きでブロック → タイムアウトのたびにタイマー処理
- `setsockopt(SO_RCVTIMEO)` は **成功を返す** (`ret=0`)
- しかし `recvfrom()` は **永久にブロックする**
- → タイマーが一度も回らない → 最初のハンドシェイクすら送られない(鶏卵問題)
- **対処**: `poll()` によるタイムアウト待ちに変更

**[話すこと]**
1つ目。受信スレッドは、UDP をタイムアウト付きで待って、タイムアウトするたびにハンドシェイクや keepalive のタイマー処理を回す設計にしていました。`setsockopt` でタイムアウトを設定すると、戻り値は 0 で成功します。ところが `recvfrom` は永久にブロックしました。相手から何か来ない限り戻ってこない。でもこちらからハンドシェイクを送らないと相手は何も送ってこない。完全な鶏卵問題です。`poll()` に変えて解決しました。

---

## 13. 落とし穴 2: detach した pthread が消える

**[スライド]**
- `wg` コマンドが `pthread_create()` + `pthread_detach()` で受信スレッドを起動
- `wg` コマンドが終了すると、**スレッドも動かなくなる**
  - `ps` にすら出てこない
  - `pthread_create()` の直後に `usleep()` を入れると動く → スレッド自体は生成されている
- POSIX 的には detach したスレッドは生成元と無関係に生き続けるはず
- **対処**: `task_create()` で独立したタスクとして起動

**[話すこと]**
2つ目。受信スレッドを `pthread_create` して `pthread_detach` していたんですが、`wg` コマンドが終了した瞬間にスレッドが動かなくなりました。`ps` にも出てきません。面白いのは、`pthread_create` の直後に `usleep` を入れるとスレッド内の `printf` が出ることで、生成自体はされている。POSIX の建前では detach したスレッドは生成元と無関係に生き続けるはずなんですが、そうならなかった。`task_create` で独立したタスクにして解決しました。

---

## 14. 落とし穴 3: ping は通るのに TCP だけ死ぬ

**[スライド]**
- 実機で ping は 0% packet loss で通る ✅
- 同じトンネルで telnet すると:
  - TCP の 3-way ハンドシェイクは **成立する**
  - しかし telnetd のバナーが **1バイトも届かない**
- WireGuard を使わず同一 LAN で telnet → **正常に動く**
- → `wg0` の実装のうち **TCP のデータ送出だけ** が壊れている

**[話すこと]**
3つ目。これが一番厄介でした。実機で ping は完璧に通ります。ところが同じトンネルで telnet すると、TCP の 3-way ハンドシェイクまでは成立するのに、telnetd が出すバナーが1バイトも届かない。切り分けのために WireGuard を使わず同じ LAN で直接 telnet したら、正常に動く。つまり telnetd も TCP スタックも悪くない。`wg0` の実装の、TCP のデータを送る経路だけが壊れている。

## 15. 犯人: `EBADF`

**[スライド]**
- 送信経路にログを仕込んで実機で再現:

```
wg_txpoll: d_len=72 proto=6 (TCP) peer=0x3fc9a720
wg_encrypt_and_send: sendto ret=-1 errno=9   ← EBADF
```

- **成功する送信**: `wg_rx` タスク自身のコンテキスト
  - ハンドシェイク応答、keepalive、ICMP echo reply、TCP の SYN-ACK
- **失敗する送信**: **LPWORK ワーカースレッド**から
  - = 非同期にキューされる **TCP アプリケーションデータすべて**

**[話すこと]**
送信経路にログを仕込んで実機で再現させたところ、`sendto` が `errno=9`、つまり `EBADF`、不正なファイルディスクリプタを返していました。そして成功する送信と失敗する送信がきれいに分かれていた。成功するのは受信タスク自身のコンテキストから出るもの。失敗するのは LPWORK というワーカースレッドから出るもので、これが TCP のアプリケーションデータ全部に相当していました。

---

## 16. 原因: fd はタスクグループにスコープされる

**[スライド]**
- NuttX の **ファイルディスクリプタはタスクグループ単位**
- UDP ソケットの fd を持っているのは `wg_rx` タスク(とその子孫)
- **LPWORK は起動時から存在する独立したシステムタスク** — 親子関係が一切ない
  - → LPWORK の fd テーブルにその fd は存在しない → `EBADF`
- ICMP / SYN-ACK は `ipv4_input()` の中で **同期的に** 返すので `wg_rx` の中で完結 → 通る
- TCP のデータは `devif_poll()` 経由で **非同期** に出る → LPWORK → 死ぬ

**[話すこと]**
原因はこうでした。NuttX のファイルディスクリプタはタスクグループ単位でスコープされます。UDP ソケットの fd を持っているのは受信タスクとその子孫だけ。ところが LPWORK は起動時から存在する独立したシステムタスクで、受信タスクとは親子関係が一切ない。だから LPWORK の fd テーブルにはそのソケットが存在せず、`EBADF` になる。

ping が通ったのは、ICMP の応答が `ipv4_input()` の呼び出しの中で同期的に作られて、受信タスクのコンテキストのまま送り返されるからです。TCP の SYN-ACK も同じ。だからハンドシェイクまでは成立する。でもアプリケーションのデータは非同期にキューされて LPWORK から出るので、そこだけ無言で死ぬ。**「ping が通るから経路は大丈夫」という思い込みが、いちばん時間を溶かしました。**

## 17. 修正: `psock_*()` 内部 API へ

**[スライド]**
- NuttX には **fd テーブルを経由しない** 内部 API がある
  - `psock_socket()` / `psock_bind()` / `psock_sendto()` / `psock_recvfrom()`
  - 実体は `struct socket` — ただのメモリ上の構造体
- ポインタで触るだけなので **どのタスクからでも同じように使える**

```c
- int sock;                        /* fd: タスクグループに縛られる */
+ struct socket psock;             /* どのコンテキストからでも OK */

- sendto(priv->sock, ...);
+ psock_sendto(&priv->psock, ...);
```

- 結果: トンネル越しの telnet / HTTP が動作 → **デモの Web サーバーはこの修正の産物**

**[話すこと]**
修正は、fd テーブルを経由しない内部 API に切り替えることでした。`psock_sendto` などの API があって、これは `struct socket` という構造体を直接ポインタで受け取ります。ただのメモリ上の構造体なので、どのタスクから触っても問題ない。この修正で、さっきデモでお見せした telnet と Web サーバーが動くようになりました。

## 17.5. 修正の代償と、その回収

**[スライド]**
- `psock_*()` に移った代償: **`poll()` も fd ベース**だった
- 暫定対応: 「50ms ごとに覗きに行く」ポーリングループ
  - 「アイドル時に CPU を起こすだけ」と思っていた → **間違い**
  - 届いたパケットが最大 50ms 待たされ、**スループットを律速していた**
- `psock_poll()` + セマフォで本来のブロッキング待機に戻した

| | ポーリング | ブロッキング |
|---|---|---|
| TCP スループット | 24 KiB/s | **260 KiB/s** |
| 負荷時 ping RTT | 370〜1146 ms | **33〜68 ms** |

- 副産物: 7 MB 連続転送中に **rekey が発生して成功**(未検証だった経路)

**[話すこと]**
実はこの修正には代償がありました。`sendto` を内部 API に変えたのはいいのですが、`poll()` も同じく fd ベースなので使えなくなったんです。そこで暫定的に「50ミリ秒ごとに覗きに行く」ポーリングにしました。このとき私は「アイドル時に CPU を無駄に起こすだけだろう」と思っていたんですが、これが間違いでした。パケットが届いてから最大 50 ミリ秒待たされるので、スループット自体が律速されていたんです。

`psock_poll` にコールバックを仕込んでセマフォで待つ形に直したところ、スループットが 24 KB/s から 260 KB/s へ、約10倍になりました。負荷時の ping も 1秒近くかかっていたのが数十ミリ秒になっています。おまけに、7MB を連続で流している最中に鍵の再ネゴシエーション、rekey が発生して成功することも確認できました。これは今まで一度も通っていなかった経路です。

## 18. おまけ: 「なんとなく」を実測に置き換える

**[スライド]**
- 受信タスクのスタックサイズ、デフォルト **3072 バイト** — 根拠なし
- `wg_rx` は `ipv4_input()` を自分のスタックで呼ぶ = **TCP スタックの深さが全部乗る**
- `CONFIG_STACK_COLORATION` で実機計測:

| 状態 | 消費 |
|---|---|
| 起動直後 | 2,864 B |
| TCP 1.2 MB + ping フラッド | **2,896 B** |

- → 3072 では余裕 **176 バイト (94% 使用)**。実質足りていなかった
- デフォルトを **4096** に変更(実測比 約 40% の余裕)+ 計測方法を Kconfig の help に記載

**[話すこと]**
最後にもう一つ。受信タスクのスタックサイズがデフォルト 3072 バイトだったんですが、これは誰も測っていない数字でした。さっき話したとおり、このタスクは `ipv4_input()` を自分のスタックで呼ぶので、TCP スタックの深さが丸ごと乗ります。実機で計測したら、ピークが 2896 バイト。つまり余裕が 176 バイトしかなく、実質足りていませんでした。4096 に変更して、どうやって測ったかを Kconfig のヘルプに書きました。次に触る人が同じことで悩まないように。

## 想定質問と回答

**Q. なぜ lwIP をそのまま NuttX に載せなかったのか?**
NuttX は独自のネットワークスタックを持っていて、そちらが標準です。lwIP を別途載せると二重にスタックを持つことになり、メモリ的にも保守的にも不利です。それに、NuttX ネイティブの netdev として実装しておけば `ifconfig` や既存のアプリがそのまま使えます。

**Q. 性能は?**
ESP32-S3 実機・実 Wi-Fi 経由で、トンネル越しの TCP スループットが約 260 KiB/s です。7 MB の連続転送を問題なく通せています。ただしこれは「明らかなボトルネックを1つ潰した」段階の数字で、体系的なチューニングはしていません。暗号処理がソフトウェア実装のままなので、そこがおそらく次のボトルネックです。

**Q. 暗号処理はソフトウェア?ハードウェアアクセラレータは?**
現状は wireguard-lwip 付属のソフトウェア実装をそのまま使っています。ESP32-S3 には暗号アクセラレータがあるので、そこに載せ替えるのは将来的な最適化として有力です。

**Q. 複数ピアは?**
現状は単一ピアです。ベースにした実装の `WIREGUARD_MAX_PEERS` に依存していて、そこを Kconfig で設定できるようにするのが次のステップです。

**Q. 鍵の管理は?**
現状 Kconfig でビルド時に埋め込む形で、正直これは良くないと認識しています。鍵がビルド成果物に焼き込まれますし、設定を変えるたびに再ビルドが必要です。実行時設定に移すのが優先度の高い改善項目です。

**Q. なぜ ESP32-S3 を選んだのか?**
最初は手元の ESP32-WROOM-32 と Sony Spresense で試したのですが、どちらもハードウェア側の問題(ブートモードに入らない / USB が認識されない)で書き込みまで到達できませんでした。ESP32-S3 は別個体で、こちらは一発で書き込めました。NuttX の Wi-Fi サポートがあることも理由です。

**Q. Raspberry Pi Pico 2 W は使えないのか?**
オンボードの Wi-Fi チップ (CYW43439) のドライバが、NuttX では RP2040 版にしか統合されていません。RP2350 側にも PIO/GPIO の対応関数は揃っているので移植自体は現実的ですが、別のドライバ開発タスクになるので今回はスコープ外としました(調査メモを Issue に残してあります)。
