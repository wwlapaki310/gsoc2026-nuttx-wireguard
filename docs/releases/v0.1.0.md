# v0.1.0 — WireGuard for Apache NuttX, apps 版(FLAT ビルド)の完成

**日付:** 2026-09-18 / **タグ:** `v0.1.0`（このノートを含むコミットを指す）

> **English summary:** First complete release of the WireGuard port for Apache NuttX,
> implemented as an `apps/netutils/wireguard/` component that registers a `wg0`
> `NET_LL_TUN` network device over a UDP socket. Verified on hardware (ESP32-S3 and
> Sony Spresense + iS110B Wi-Fi add-on) against the official Windows WireGuard client
> over real Wi-Fi — headless boot, handshake, telnet and HTTP through the tunnel — on
> NuttX 13.0.1 (default), master (bda22516) and 12.7.0, plus sim and QEMU against the
> Linux kernel WireGuard. This is the last release of the FLAT-only, apps-side design;
> the next line of work moves the netdev into the kernel
> ([docs/upstream/in-kernel-plan.md](../upstream/in-kernel-plan.md)). Known protocol
> deviations found in the pre-migration review are listed under "Known issues" and are
> not fixed in this release.

## これは何か

WireGuard VPN を Apache NuttX のネットワークデバイス `wg0` として実装したもの。アプリからは普通のインターフェースに見え、暗号化された中身は UDP ポート 51820 のソケットが運ぶ。通信相手は既存の WireGuard 実装(Linux カーネルモジュール、Windows 公式クライアント)。

このリリースは **`apps/netutils/wireguard/` に置いた apps 版の完成形**で、FLAT ビルド専用。次は netdev 部分をカーネル(`drivers/net/`)へ移す設計に進むため、apps 版としてはここで凍結する(計画は [in-kernel-plan.md](../upstream/in-kernel-plan.md))。

## 検証済みの環境

| 環境 | アーキテクチャ / Wi-Fi | ピア | 確認したこと |
|---|---|---|---|
| sim | x86_64 / TAP | Linux カーネル WireGuard | ハンドシェイク、疎通、ランタイム設定と保存/復元、2 ピア同時(スクリプト 3 本) |
| QEMU `qemu-armv7a` | ARM Cortex-A7 / virtio-net | Linux カーネル WireGuard | NuttX 自身のスケジューラ上で同じこと(スクリプト) |
| **ESP32-S3**(Freenove devkit) | Xtensa LX7 / オンチップ Wi-Fi(`wlan0` カーネル netdev) | **Windows 公式クライアント** | 実 Wi-Fi 越しのハンドシェイク、トンネル越し telnet・HTTP、7 MB 転送、rekey、電源断からの復帰、ヘッドレス起動(USB なし) |
| **Sony Spresense** + iS110B Wi-Fi Add-on(GS2200M、v1.0C) | ARM Cortex-M4F / usrsock 方式の Wi-Fi ドライバ | **Windows 公式クライアント** | 同上(ESP32 とは別方式のネットワーク裏側で同じ `wg0` コードが動く)、2 枚同時運用 |

NuttX のバージョン: **13.0.1(既定)、master(bda22516、2026-09-17)、12.7.0** の 3 つで、上の全環境を確認。WireGuard 側のソースは 3 つで同一(NuttX 側の差分は Dockerfile がビルド時に吸収)。

実測(ESP32-S3、実 Wi-Fi、Windows 公式クライアント): トンネル越し TCP 約 260 KiB/s、無負荷 RTT 8〜11 ms、最長連続動作 4 時間 28 分(停止原因は ESP32-S3 の Wi-Fi ドライバ側と特定済み)。

## この間に見つけて直したもの(WireGuard 側)

- **TCP のアプリデータだけがトンネルを通らない** — LPWORK ワーカースレッドからの `sendto()` が `EBADF`(fd がタスクグループ単位)。`psock_*()` 内部 API に切り替え。これが FLAT 前提の直接の理由
- `SO_RCVTIMEO` が効かない、detached pthread が生成元タスクの終了で止まる(Phase 3)
- **usrsock 環境で `wg0` 宛の ioctl が横取りされてハンドシェイクが始まらない**(Spresense)— netdev を直接設定する形に修正
- NuttX 本体の `crypto/` と vendored の暗号でシンボル衝突 → `wg_` プレフィックスで名前空間分離
- `/dev/urandom` の既定(xorshift、定数シード)で `wg genkey` が毎回同じ鍵(Spresense)→ その構成で `CRYPTO_RANDOM_POOL` を有効化
- `wg` builtin のスタック既定が `DEFAULT_TASK_STACKSIZE`(2048)に追従して `saveconf` で溢れる → 4096 固定
- `wg_rx` のスタック実測に基づく既定 4096 → 6144、ポーリング解消で約 10 倍の性能改善

## NuttX 本体側で見つけたもの(未提出、ドラフトあり)

- **cxd56(Spresense)が `CONFIG_RTC_HIRES` で起動しない回帰** — 13.0.1 のリリースと master に入っている。修正案付き([rtc-hires-wdog-regression-draft.md](../upstream/rtc-hires-wdog-regression-draft.md)、[#9](https://github.com/wwlapaki310/gsoc2026-nuttx-wireguard/issues/9))
- GS2200M ドライバ/デーモンの ioctl 2 件([gs2200m-usrsock-issue-draft.md](../upstream/gs2200m-usrsock-issue-draft.md)、[#10](https://github.com/wwlapaki310/gsoc2026-nuttx-wireguard/issues/10))
- 13.0.1 / master の esp32s3 defconfig の変化(NxInit、既定スタック 2048、SPIFFS の形式変更)と、13.0 以降の QEMU で `.data` と DTB が衝突する件は、Dockerfile 側で吸収して記録

## 使い方(最短)

```bash
# sim で Linux カーネル WireGuard と疎通(Docker)
docker build --target sim -t nuttx-wireguard:sim .
docker run --rm --cap-add=NET_ADMIN --device=/dev/net/tun \
  -v ${PWD}/scripts:/workspace/scripts:ro --entrypoint bash nuttx-wireguard:sim \
  /workspace/scripts/verify-sim-wg-runtime.sh

# ESP32-S3(実機。Wi-Fi 資格情報はビルド引数で)
docker build --target esp32s3 --build-arg WIFI_SSID=... --build-arg WIFI_PASS=... -t nuttx-wireguard:esp32s3 .
docker create --name x nuttx-wireguard:esp32s3 && docker cp x:/opt/nuttx/nuttx.bin . && docker rm x
python -m esptool -c esp32s3 -p COM7 -b 921600 write_flash -fs detect -fm dio -ff 40m 0x0000 nuttx.bin
```

ボード上:

```
nsh> wg genkey
nsh> wg set private-key <key>
nsh> wg set peer <peer-pubkey> endpoint 192.168.0.216:51820 allowed-ips 10.10.0.1/32
nsh> wg up
nsh> wg saveconf        # 次回起動から rcS が自動で読み込む
```

12.7.0 で使うなら `--build-arg NUTTX_REF=nuttx-12.7.0`。ESP32-S3 を 12.7.0 と 13.x のイメージ間で行き来するときは SPIFFS 領域を消す(`esptool erase_region 0x180000 0x100000`)。詳細は [README.md](../../README.md) と [hardware-verification.md](../development/hardware-verification.md)。

## 制約

- **FLAT ビルド専用。** `netdev_register()`・`psock_*()`・`devif_poll()` 等のカーネル内部 API を `apps/` から呼んでいるため、PROTECTED / KERNEL では動かない。これがカーネル側へ移す理由
- IPv4 のみ。`wg0` は 1 本。ピアの変更は `wg down` 中のみ
- PresharedKey 未対応(`setconf` は `PresharedKey =` 行を無視する)
- upstream(`apache/nuttx-apps`)未提出。この設計のままでは提出しない

## 既知の問題(移行前レビューで判明、このリリースでは未修正)

カーネル移行の計画レビュー(2026-09-18、[in-kernel-plan.md](../upstream/in-kernel-plan.md) §6)で、現行コードに以下のプロトコル逸脱が見つかっている。**信頼できないネットワークに晒す用途には使わないこと。** 修正は v0.1.1(apps 版のうちに直す、計画の S0.5)で行う。

1. 復号成功時に **replay 検査より前に endpoint を更新**しており、keepalive は replay 検査を通らない。認証済みパケット 1 個を別の送信元から再送するだけで、正規ピアの次のパケットまで endpoint を乗っ取れる
2. **cookie reply を捨てている**。負荷中の Linux / wireguard-go サーバ(cookie を要求する側)には繋がらない。応答側の cookie 経路も未実装で、`wireguard_is_under_load()` は常に false
3. vendored `wireguard.c` の initiation レート制限が減算の向きの誤りで無効
4. 秘密鍵のゼロ化漏れ(`wg_initialize()` のスタック、staged 領域、`wg down` 後のデバイス構造体)。`wg showconf` は stdout に秘密鍵を出す。`wg pubkey` は秘密鍵をコマンドライン引数で受ける
5. `CONFIG_NET_WIREGUARD` が乱数バックエンドを強制していない(xorshift 構成でもビルドできる。Dockerfile の sim / QEMU は xorshift のまま)
6. TAI64N は `CLOCK_REALTIME` そのままで、RTC 無し/リセットのボードがハンドシェイクの initiator になる構成では再起動後に相手が initiation を捨てる
7. cryptokey routing が先頭一致(`0.0.0.0/0` のピアが先にあると後続の /32 宛もそちらへ)。replay 窓が 32 パケット
