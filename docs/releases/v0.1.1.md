# v0.1.1 — v0.1.0 の既知の問題(プロトコル逸脱)を修正

**日付:** 2026-09-18 / **タグ:** `v0.1.1` / 前版: [v0.1.0](v0.1.0.md)

> **English summary:** Fixes the protocol deviations listed as known issues in v0.1.0,
> found in the pre-migration security review: replay check now precedes any peer state
> update (endpoint hijack by replayed packet closed), cookie/mac2 path implemented in both
> directions with a load threshold, the vendored initiation rate limit repaired, anti-replay
> window widened 32 → 2048, key material zeroised on down, urandom backend enforced in
> Kconfig, `wg pubkey` reads stdin, cryptokey routing is longest-prefix. New negative-path
> test `scripts/verify-sim-wg-replay.sh` fails on v0.1.0 and passes here. Re-verified on sim,
> QEMU, ESP32-S3 and Spresense (NuttX 13.0.1). Still the apps-side FLAT design; the kernel
> migration is unchanged in scope ([in-kernel-plan.md](../upstream/in-kernel-plan.md)).

## 直したもの(v0.1.0 の「既知の問題」1〜7)

| # | v0.1.0 の問題 | 修正 |
|---|---|---|
| 1 | replay 検査より前に endpoint を更新。keepalive は検査なし | 復号 → **`wireguard_check_replay()`** → その後で endpoint・`last_rx`・keypair 更新(Linux と同じ順序)。keepalive も同じ経路 |
| 2 | cookie reply を捨てる。応答側の cookie 経路なし、`is_under_load` 固定 false | 受信した cookie reply を `wireguard_process_cookie_message()` に渡し、即 mac2 付きで再送。応答側は mac1 → 負荷中なら mac2 検査 → 無ければ cookie reply を返して DH をしない。負荷判定は 1 秒あたりの initiation 数(`CONFIG_NET_WIREGUARD_LOAD_THRESHOLD`、既定 4) |
| 3 | vendored のレート制限が減算逆で無効 | `now - last_initiation_rx` に修正([PATCHES.md](../../nuttx_port/apps/netutils/wireguard/PATCHES.md) #1) |
| 4 | 鍵のゼロ化漏れ、`pubkey` が引数で秘密鍵 | `wg_initialize()` のスタック鍵を `device_init` 直後にゼロ化、`wg down` でデバイス構造体全体をゼロ化、`ifdown` で全ピアの keypair ×3 + handshake を破棄し endpoint を設定値に戻す。`wg pubkey` は stdin から読む(引数形式も残す) |
| 5 | 乱数バックエンドを強制していない | `CONFIG_NET_WIREGUARD` は `DEV_URANDOM_ARCH` か `DEV_URANDOM_RANDOM_POOL` を要求(xorshift / congruential ではビルド不可)。`wg up` 時に `/dev/urandom` から読めることを確認し、ダメなら `-EIO` で拒否。Dockerfile の sim / QEMU も entropy pool に変更 |
| 7 | cryptokey routing が先頭一致、replay 窓 32 | 最長一致に変更。allowed-ips は ip と mask の両方が解釈できたときだけ有効。replay 窓は `CONFIG_NET_WIREGUARD_REPLAY_WINDOW`(既定 2048、PATCHES.md #2) |
| — | `now == 0` を「未設定」の番兵に使う箇所が起動直後と wrap で誤判定 | `wireguard_sys_now()` が 0 を返さない |
| — | 受信側の期限判定に `sending_counter` | `replay_counter` に |

**未修正(v0.1.0 の 6):** TAI64N の単調性(RTC 無し/リセットのボードが initiator になる構成で再起動後に繋がらない)。永続化の設計がカーネル移行と絡むので、[in-kernel-plan.md](../upstream/in-kernel-plan.md) §1.10 で扱う。`wg showconf` が秘密鍵を出す点は `wg(8)` と同じ挙動なので維持(telnet 越しに叩く場合は注意)。

## テスト

新規 [`scripts/verify-sim-wg-replay.sh`](../../scripts/verify-sim-wg-replay.sh)(Linux カーネル WireGuard 相手、sim):

1. Linux → NuttX の transport data パケットを 1 つ捕獲し、別の送信元(10.0.0.9)から 3 回再送 → **endpoint が動かない**こと、その後もトンネルが通ること
2. 正しい mac1 付き・中身がゴミの initiation を閾値 + 4 個送る → **閾値を超えた分だけ cookie reply が返る**こと、本物のピアのトンネルが生きていること

v0.1.0 のイメージでは 1 が `endpoint: 10.0.0.9:40000` になって FAIL、2 は cookie reply 0 で FAIL。この版では両方 PASS。

既存の回帰(`verify-sim-wireguard.sh` / `verify-sim-wg-runtime.sh` / `verify-sim-wg-multipeer.sh` / `verify-qemu-wireguard.sh`)は PASS。ESP32-S3 と Spresense(NuttX 13.0.1)でヘッドレス起動 → Windows クライアントとハンドシェイク 5 秒 → telnet → HTTP 200 を再確認。

## 互換性

- vendored `wireguard.c` / `wireguard.h` は upstream とバイト一致ではなくなった(印付きのパッチ 2 件、[PATCHES.md](../../nuttx_port/apps/netutils/wireguard/PATCHES.md))。`crypto/` はバイト一致のまま
- ピアあたりの RAM が replay 窓の分(既定 768 バイト)増える
- Kconfig の乱数要件により、`/dev/urandom` が xorshift の構成はビルドできなくなる(意図的)
- 設定ファイル・`wg` コマンドの書式・`wg show` の出力は変更なし
